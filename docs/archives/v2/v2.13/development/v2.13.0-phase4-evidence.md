# v2.13 Phase 4 evidence

Phase 4 adds a versioned image edit recipe with a typed reducer (`core/image/ImageEditRecipe.ts`) and a recipe store facade (`core/generations/ImageEditRecipeStore.ts`) that persists recipes through a scoped transaction on the existing `StudioSessionStore` connection in `sessions.db`. Support tier: candidate. The store is not yet wired to the viewer (Phase 5) or to agent commands (Phase 6).

## Scope checked against the plan

- T012: one zod-validated recipe with source identity, dimensions, revision, command history and cursor; four adjustments, stroke and text marks, reset, undo and redo; typed `ImageEditError` codes; stale revision rejected; a new edit after undo drops the redo branch only in the returned recipe, which persistence commits.
- Mark sizes follow the current viewer exactly: the brush slider is 1-64 and text is drawn at four times the brush, so strokes accept 1-64 and text 4-256 (`IMAGE_MARK_SIZE_RANGES`, also reported by `imageEditCapabilities` for Phase 6). The 2026-10-14 draft allowed up to 2048 for both, which would have let a command create marks the UI cannot.
- Limits equal the Phase 1 freeze in `embedding-eval-contract.md`: 8 MiB serialized, 1000 commands, 100000 stroke points, 4096 text characters, 2048 x 2048 and 4,194,304 pixels.
- T013: additive `studio_image_edit_recipes` table with turn/session foreign keys and `ON DELETE CASCADE`; expected-revision compare-and-swap; PNG-only sources resolved server-side under the owned media root, re-hashed on every load, commit and read; data URLs and paths outside the root rejected; an injected owned-image authorizer is checked before and after each write, and a change rolls the transaction back.
- Grant issuance and revocation are not implemented here. The store only accepts an authorizer; the human-confirmed grant and its revocation on run or session end belong to the delivery seams in Phases 5 and 6, as `baseline-and-seams.md` places them.

## Stabilization changes in this phase

- `lib/embedding-eval.mjs`, `scripts/evaluate-local-embeddings.mjs` and their test: Phase 4 edits files inside the frozen Phase 2 evaluation corpus (for example `core/generations/StudioSessionStore.ts`). The evaluator now materializes a changed source from the contract's pinned `baselineHead` with `git show` and records each source's origin in `sourceSnapshots`, so the Phase 2 report stays reproducible without freezing the codebase.
- `modules/coding/evaluation/goldenSnapshot.ts` and its test: disposable golden-task snapshots now run `git init --template=`, so a personal `GIT_TEMPLATE_DIR` (and its hooks) is never copied into or executed inside a snapshot; a new test plants a failing `commit-msg` hook template and asserts neither the marker nor the hook appears.
- `modules/coding/evaluation/goldenTasksYaml.generated.ts`: regenerated by the build (28 task ids).
- `tests/unit/cli/contract.test.ts`: a 65 s test timeout that encloses the CLI's own 60 s child-process deadline.
- `tests/unit/hooks/check-git-control-plane.test.ts`, `tests/unit/scripts/evaluate-local-embeddings.test.ts`: temporary repositories use `git init --template=` so a developer's global hook templates cannot run inside the tests.

## Carried to Phase 7

The full root suite run on 2026-10-14 had one failure: the golden runner's dry-path test in `tests/integration/golden/golden-runner-end-to-end.test.ts` timed out at vitest's 5 s default. Isolated, it passes in about 2.5 s (three runs measured 2026-10-15). It performs the same snapshot copy and cleanup as the sibling mock-live block, which already has a 30 s timeout for the reason the file's own comment gives: Windows parallel workers can push that work past 5 s. The dry-path block was not given the same timeout. Phase 4 did not cause it; the Phase 7 full-suite step owns the fix and a fresh full-suite run.
