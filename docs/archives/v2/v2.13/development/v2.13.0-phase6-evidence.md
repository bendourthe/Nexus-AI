# v2.13 Phase 6 evidence

Phase 6 lets an agent describe, edit, undo, redo, preview and export a persisted Image Studio image through the authenticated local control surface, with access granted per image by a human in the Ask inbox. Agent and viewer share one mutation path and one pixel path. Design and rejected alternatives: [image command contract](image-command-contract.md) (T019). Support tier: candidate.

## What changed

- **Grants (T018).** `POST /nexus/image-edit/access` parks an `image_edit_access` ask in the Ask inbox (the existing headless confirmation owner) and returns a request id. Only a human approval there issues a grant: a random secret bound to the agent's caller id, run id, and the image's session, turn and source hash, valid for one hour. Every later call presents caller id, run id and grant; any mismatch is `FORBIDDEN` (HTTP 403). The app token alone, the viewer's grants and other callers' grants never satisfy an agent call; a cross-caller describe, apply, preview or export is refused before any render request is queued. Grants end on `release`, expiry, session deletion or sidecar exit.
- **Commands (T018).** `describe` returns revision, values, mark count, undo/redo availability, ranges, mark sizes, limits and supported actions. `apply` requires `expectedRevision` and `idempotencyKey`; a 256-entry replay cache returns the stored result for the identical request and `IDEMPOTENCY_CONFLICT` (409) for key reuse with another payload. Undo and redo are `apply` actions. `ImageEditRecipeStore.commit` is the single mutation path for viewer and agents.
- **Render bridge (T019, T020).** The sidecar queues `{requestId, revision, sourceSha256, size, state, pinned PNG}`; the running desktop window polls `studio.image.render.claim` every 500 ms and answers through `studio.image.render.complete`. No claim and answer within 8 s fails with `RENDERER_UNAVAILABLE` (503). A response is accepted only for a live request id, as a PNG whose IHDR size equals the request; stale ids are ignored and forged sizes fail with `RENDER_FAILED`. Pending requests fail on shutdown.
- **One pixel path (T020).** The pure rendering (types, filter, sharpening, `renderAdjusted`, mark painting) moved from `ImageViewer.tsx` into `desktop/src/shared/studio/imageEditRenderer.ts`, re-exported for existing imports. The viewer's export and the bridge both call `renderEditedCanvas` / `renderEditedPng`.
- **Export (T020).** Preview returns PNG bytes and writes nothing. Export writes only under `~/.nexus/generations/exports/`, canonicalized at first use; a linked root or a root replaced by a link or junction is `EXPORT_UNSAFE` and a file that would land elsewhere is removed. Files are created exclusively (`wx`); a name collision is `EXPORT_EXISTS` and nothing is overwritten. The recipe revision and the source hash are re-checked after rendering; a change refuses the export.
- **Seam.** `nexus image-edit access|status|describe|apply|render|release --json <body>` in `core/cli/jsonCli.ts` and `bin/nexus.mjs`, documented in the bundled `nexus` skill. No new built-in coding tool, MCP entry, listener or script evaluation.

## Verification Expectation (functional evidence)

1. **Authenticated route** (real `LoopbackHttpServer` on 127.0.0.1, real `sessions.db` and PNG): wrong token 401; missing fields 400 `schema`; access 202 then a grant only after approval; apply 200 at revision 1; key reuse with another payload 409 `IDEMPOTENCY_CONFLICT`; another caller 403 `FORBIDDEN`; after `release` 403.
2. **Shared state**: an agent edit is visible to the viewer and a viewer undo is visible to the agent (`describe`: revision 2, redo available); agent redo restores the value.
3. **Render and export** with the bridge driven by a simulated renderer: preview returns bytes and writes nothing; the bridge received the pinned source hash and revision; export writes one file under the exports root; a second export of the same revision is `EXPORT_EXISTS` and the file is unchanged; an expected revision that is stale is `REVISION_CONFLICT`; a concurrent viewer commit or a source byte change during the render refuses the export with no file written; replacing the exports root with a junction is `EXPORT_UNSAFE` and nothing lands in the junction target; no renderer gives `RENDERER_UNAVAILABLE` within the deadline; a forged size gives `RENDER_FAILED`; a stale id is not accepted; shutdown fails pending requests. The original PNG hash is unchanged throughout.
4. **Pixels in the WebView engine** (`node desktop/tests/webview/image-edit-pixels.mjs`, headless Edge 155):

```text
previewVsExport:        differing 0, maxDelta 0
viewerVsCommandExport:  differing 0, maxDelta 0   (renderEditedPng, the bridge path)
sharpening:             readback true, differing 464, maxDelta 122
original download:      byte-identical to the source
```

Not observed here: a render request crossing the actual Tauri shell into a live Nexus window. The pieces on each side are proven (route and bridge in Node, the renderer's claim/answer protocol, the renderer's pixels in the WebView engine); the joined path is part of WN-1.

## Limits

- Agent bodies go through the control surface's 1 MiB body cap, so one `apply` can carry roughly 30,000 stroke points; the recipe allows 100,000 in total.
- The 500 ms renderer poll runs whenever the Nexus window is open; it is one local IPC call when idle.

## CI impact

Two IPC methods (`studio.image.render.claim|complete`) bound to feature f003 for `check-command-parity`; new tests under `desktop/tests/`, collected by the existing desktop config. No new dependency, environment variable, artifact or pipeline change; no push, pull request or remote CI.
