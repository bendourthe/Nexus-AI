## Recommendation

Evaluate EmbeddingGemma 2's text/code configuration through the existing local Ollama adapter first. Admit it only if a measured Nexus workload justifies taking the current embedder's job, or a distinct uncovered job. Before changing any index, establish model identity and migration checks. The strongest editor lesson is a durable image-edit session driven by a small shared command surface, with inspection and export available to both people and agents.

The four Craft applications are references for particular engineering patterns, not a reason to turn Nexus into an Adobe replacement. Full vector authoring, RAW development, professional video editing, and native codec replacement do not have a demonstrated Nexus user need here. This ranking is a judgment grounded in `STRATEGY.md`'s solo-builder persona, local operation, single-GPU budget, and competitor-parity non-goal.

Support tiers: existing Nexus implementations cited below are **internal-compatible** evidence from code inspection, with their end-to-end behavior **not proven here**. EmbeddingGemma 2 integration and editor enhancements are **candidate**. Larger creative-editor additions are **future**, not supported commitments.

### Candidate patterns supported by source code

**C1. Persistent image-edit recipe, P2 (medium value, medium effort).** PhotoCraft represents editing through a session and command registry. LightCraft journals catalog operations and merges its own sidecar settings while preserving unrelated metadata. Nexus's `desktop/src/shared/studio/ImageViewer.tsx` holds adjustments, marks and redo in React state and exports flattened PNGs; undo/redo there covers marks, not a durable, complete adjustment history. `core/generations/GenerationIndex.ts` stores content-hash workflow provenance, not the viewer's editable document. Preserve the original asset and save a versioned recipe for the existing adjustments/marks before adding layers. A separate small recipe is sufficient; no Photoshop-sized document model is justified. [PhotoCraft registry](https://github.com/storytold/photocraft/blob/eec4af65513b52084926f3c679fc6ac7821cafaf/crates/engine/src/commands.rs), [LightCraft persistence](https://github.com/storytold/lightcraft/blob/629e39380e296f588c64cd9c0053a8edc3528f36/crates/engine/src/sidecar.rs).

**C2. Shared edit commands and observation, P2 (medium value, medium effort), after C1.** Expose only the edits Nexus already supports, with typed parameters, current values, limits, enabled state, undo/redo, preview and export. UI and agent calls should act on the same session and produce the same result. Nexus's `desktop/sidecar/src/controlSurface/jsonCliRoutes.ts` already exposes logs, media inspection and window capture; extending those existing routes is preferable to installing four MCP servers. `src/tools/ToolCatalog.ts` supplies an existing discoverability pattern. The source lesson is shared editing state, not merely providing another endpoint. [VectorCraft history](https://github.com/storytold/vectorcraft/blob/1b93336bdf6296aa3444c15aa80a4bfcbe5e539e/crates/engine/src/lib.rs), [FilmCraft engine](https://github.com/storytold/filmcraft/blob/61238bf8fc129077fe2b7982550303be49f55a93/crates/engine/src/lib.rs).

**C3. Video trim/split project, P3 (medium value, high effort), deferred.** FilmCraft distinguishes source media, editable timeline state and export. Nexus's `desktop/src/modules/video/TimelinePreviewer.tsx` is a playback/stepping component whose header says it is retained but unmounted; `VideoLabPage.tsx` supplies the active generation/transcript flow. Neither proves an editable multitrack timeline. A bounded trim/split/export workflow could be useful later, but it needs an actual solo-builder use case and an existing media-runtime path before planning. Do not port FilmCraft's codecs or professional interchange stack. [FilmCraft project structure and editing scope](https://github.com/storytold/filmcraft/blob/61238bf8fc129077fe2b7982550303be49f55a93/README.md).

VectorCraft's vector object graph and LightCraft's RAW/color-development stack are genuine external-only capabilities but are not recommended additions now. Drawing a brush mark over a generated image is not vector authoring; image adjustments are not RAW development. No parity claim is made.

## Source 2: EmbeddingGemma 2 comparison

Google announced the model on October 6. It describes local multimodal retrieval and reports a code benchmark increase from 68.76 to 78.68; this is vendor-reported benchmark evidence, not a Nexus measurement. [Announcement](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/).

The model card describes a 740M model with a 270M text component, optional vision/audio encoders, 768-dimensional output, supported 512/256/128-dimensional truncations, and an 8,192-token input budget. It calls for task-specific query/document prefixes, renormalization after truncation, and bfloat16/float32 rather than float16. It names Apache 2.0 but also says deployments must follow a prohibited-use policy. [Official model card](https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2).

The developer guide documents sentence-transformers 6.1.0+, selective encoder loading, and media dictionaries. Configurations loaded from the same checkpoint can share a vector space at the same dimension; that does not make vectors from EmbeddingGemma 1 or MiniLM compatible. [Developer guide](https://developers.googleblog.com/en/embeddinggemma-2-the-developer-guide/).

### Runtime and admission findings

The directly fetched [Ollama listing](https://ollama.com/library/embeddinggemma-2) has text-only `embeddinggemma-2:270m` at 378 MB, larger encoder variants, and a `latest` listing at about 1.3 GB. These are displayed download sizes, not measured RAM/VRAM. Its sample uses `/api/embed`, giving the existing text adapter a plausible evaluation path. Multimodal request support in the installed runtime is not established by that sample.

The listing displays 256K context. The fetched [checkpoint configuration](https://huggingface.co/google/embeddinggemma-2/blob/main/config.json) also has text `max_position_embeddings: 262144`, while the model card specifies an 8K input budget. Positional capacity or runtime metadata does not prove trained retrieval quality at 256K. Keep an 8K evaluation cap until the publisher/runtime distinction is resolved; do not replace the existing 32K long-context job on this evidence.

The local read-only probe returned Ollama **0.32.15** with `embeddinggemma:300m` and `nomic-embed-text:latest` installed. No EmbeddingGemma 2 tag was installed. No weights were pulled and no inference or quality benchmark was run. Compatibility, latency, residency, GPU contention, retrieval gain, and offline operation of this new model are **not proven here**.

**E1. Text/code evaluation, P1 (high value, medium effort).** Use the existing Ollama port, a pinned text variant/digest, separate query/document formatting, and an isolated corpus/index. Compare with the current holder using at least 30 labeled natural-language-to-code/document queries, including paraphrases, hard negatives and no-answer cases. Record recall@5, p50/p95 end-to-end latency, peak RAM/VRAM, cold/warm load cost and non-loopback connections after provisioning. Register the pass thresholds before measuring; a suggested gate is at least five percentage points of recall@5 improvement, no more than 20% p95 latency regression, zero invalid vectors, and fit within the existing hardware budget. These thresholds are proposals, not measured outcomes or an approved product bar.

**E2. Embedding identity and safe migration, P1 (high value, high effort), required before any production switch.** Inventory which index consumes which embedder; persist model/digest, output dimension, normalization and prefix/recipe version beside each index; reject incompatible or non-finite vectors. Never use silent padding/truncation as a migration. Build a separate replacement index, validate it, then switch with rollback to the old index. A dimension change, model change or prefix change requires explicit treatment even if the vector length happens to match. The pruned index also needs its embedding identity and recomputation cache separated by recipe. This is a recommendation arising from the inspected contracts, not an implemented migration.

**E3. Generated-media content search, P3 (medium value, high effort), conditional on E1/E2 and a demonstrated need.** This can claim an uncovered local media-retrieval job rather than silently taking the app-wide text job. Start with generated images and text queries, retaining the existing text/provenance search. Use bounded local assets, hashes, project scope and explicit authorization for any import; avoid indexing whole home folders. Add audio/video only after decoder, sampling, resource and privacy behavior are proven in Nexus. Existing generation hashes and provenance provide asset identity; a new external vector database is unnecessary at this scale.

The Apache/prohibited-use inconsistency is an admission question, not a legal verdict. Resolve the authoritative checkpoint terms before a pre-ticked default. Update the job map in `docs/reference/model-acceptance.md` in the same future change as catalog/tier defaults. E1 evaluation does not admit a second default, retire Nomic continuity, or add a Python runtime. If Ollama cannot serve the required media shape, separately evaluate the documented local Python route against the runtime job map; do not quietly install it as a fourth runtime.

## Security assessment

Nexus's current runtime destinations are local; this research contacted GitHub, Google and Hugging Face/Ollama documentation only. No project source, conversations or secrets were sent to those sites. Future model provisioning can fetch public weights; ordinary inference and retrieval must remain local. No Anthropic API account, cloud embedding account, creative SaaS account, or paid relationship is required by the recommended approaches.

The Craft applications expose broad local editing and file operations. PhotoCraft's security document says authentication and filesystem roots exist but general non-filesystem capability scopes and audit events remain incomplete. VectorCraft's control documentation explicitly says its optional loopback port lacks authentication. FilmCraft/LightCraft bind their inspected control server to loopback, which alone does not establish equivalent authorization. Do not inherit any source control channel's authority model. [PhotoCraft security model](https://github.com/storytold/photocraft/blob/eec4af65513b52084926f3c679fc6ac7821cafaf/book/src/automation/security-model.md), [VectorCraft protocol](https://github.com/storytold/vectorcraft/blob/1b93336bdf6296aa3444c15aa80a4bfcbe5e539e/docs/control-protocol.md).

For Nexus editor commands, enforce session/project ownership, bounded image sizes and operation counts, allowed paths, and explicit overwrite/export policy at the existing side-effect boundary. Keep decoding and expensive processing outside the React event loop. For embeddings, vectors and caches are sensitive derived data; retain project scoping, existing redaction and deletion behavior, and do not fetch arbitrary media URLs supplied by retrieved content. A media index changes what private information is retrievable and needs an explicit corpus scope.

## Prioritized adoption sequence

No net-new skill-native artifact is needed. Within the local/internal candidates, sequence dependencies before their dependent features:

1. **E1, evaluate rather than admit.** Resolve the context/terms questions, map actual embedder consumers, and record a text/code A/B on local hardware. If the gate fails, stop this model adoption. The comparison alone is insufficient to change a default.
2. **E2, only if E1 justifies a switch or a new job.** Add identity checks and an isolated rebuild/rollback path before integrating any new vectors. Preserve codegraph/FTS lookup as the existing retrieval path.
3. **C1, then C2.** Prove that the same image can be edited, reopened after restart, inspected and exported through both the UI and a command, with identical render output and the original bytes preserved. Keep scope at the viewer's existing operations. This independent workstream may be evaluated separately from E1/E2.
4. **E3 and C3 remain deferred.** Reopen media retrieval after a concrete asset-finding need, and video editing after a concrete trim/split need. Neither is required to finish E1/E2 or C1/C2.

Proposed effort bands: E1 is an evaluation, not a release-sized implementation; E2 spans storage consumers and is the largest mandatory integration risk; C1/C2 are a bounded feature; E3/C3 are separate feature plans. Calendar estimates are withheld until actual consumer wiring and reference-hardware results are known. Shared documentation, generation metadata and composition roots can still cause conflicts, so independent workstreams do not imply an automatically safe parallel implementation.

Acceptance evidence for any subsequent plan must include actual inference/editor boundaries, not only mocks: restart/reopen, invalid and mismatched vectors, interrupted rebuild with rollback, malformed recipe/command input, blocked outside-root export, export/preview equality, bounded media resources, and offline behavior after provisioning. Add tests with the feature rather than creating new tests for this prose-only comparison.
