## Checkpoints and authority

Reviewed `AskInbox`, `StudioSessionStore`, `ImageEditRecipeStore`, `imageEditRuntime`, strict request schemas and dispatch, the production renderer client, durable editing hook, viewer recovery controls and image deletion copy.

The checkpoint preparation callback is a trusted process-local argument, not deserialized ask content. After replay and live-waiter validation, each approval attempt receives a fresh private ID. The recipe transaction captures the source-bound full recipe, command cursor and redo tail, including revision zero without creating a live recipe update. Only after the checkpoint is committed and the Ask decision JSON is saved does the waiter resolve approved. A failed checkpoint or decision save gives no live grant; retry can capture a fresh recipe after intervening viewer edits. Stored recovery data has no authority by itself, and a restarted process does not revive an old agent grant.

Checkpoint rows belong to the exact image session and turn and cascade with their history. Lists read at most 50 metadata rows per page, and restoration loads one checkpoint scoped to the same session and turn. No checkpoint eviction or original-media deletion was introduced. Cross-session selection and changed source bytes fail. Restoring uses the current expected revision and saves at current revision plus one, preserving the checkpoint itself.

Only viewer grants can list or restore checkpoints. Agent action parsing and image HTTP operations provide no restore operation. A restore fences request creation, approval preparation, activation and existing grants for the image. Successful restoration advances the authorization generation, denies outstanding requests and removes grants and replay entries. Post-render authorization runs before preview bytes return and before export writes, so a delayed result crossing a restore is refused. These checks cover authority, not just stale UI state.

The viewer uses the production client and strict request schemas, shows approval metadata, confirms replacement, flushes pending edits, locks editing during restoration, and distinguishes success from disk failure or revision conflict. The independent UI test uses an injected transport into actual image operations, SQLite and AskInbox. It is not a native Tauri transport test. Image deletion prompts disclose removal of history, edits and checkpoints with shared originals retained; the Video prompt remains free of this Image-specific notice.
