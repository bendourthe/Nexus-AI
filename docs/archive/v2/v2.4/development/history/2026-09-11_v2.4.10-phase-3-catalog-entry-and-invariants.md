## What the hoists found

This is the part worth reading. The plan predicted that two rules described as catalog-wide were reachable only by hardcoded id. Running them catalog-wide before adding anything confirmed it, twice.

**Placeholder SHA.** Three entries ship all-zero pins: `sana-controlnet-canny`, `sana-controlnet-depth`, `sana-controlnet-pose`. `pin-hf-weights.py --check` independently agrees ("3 unpinned weights file(s), 107 in scope"). They cannot be rotated here, because `Efficient-Large-Model/SANA-ControlNet-*` returns **HTTP 401** unauthenticated, so the helper has nothing to read. They are also not flagged `gated` and `KNOWN_GATED_IDS` is empty, so invariants B and C never caught them either. A user installing these gets no integrity check at all. Recorded as **BG-2** and named in `PLACEHOLDER_SHA_LEGACY_EXEMPT`, so the new rule protects every other entry rather than being softened for all.

**Forbidden benchmark copy.** One hit, and it is a false positive worth the design change it forced: `qwen3-coder:30b` reads "Vendor SWE-bench numbers are not copied here." Naming a suite in order to decline it is the convention working. A bare substring check would have demanded the deletion of an honest sentence. The check now treats a suite name as a violation only when the sentence carrying it holds no disclaimer marker, scoped per sentence so a disclaim-then-assert copy still fails. There is a test for exactly that case.

## Decisions

- **`vramGB: 3`, derived from the incumbent's size-to-VRAM ratio.** `lfm2.5:2.6b` is 1.67 GB against 3 GB; MiniCPM5 is 1.56 GB, so the same ratio gives roughly 2.8 and rounds to 3. Same slot, same quant, 0.11 GB apart, so the incumbent is the right reference. Recorded as a Nexus-side compatibility threshold, not a measurement.
- **Benchmark clause made catalog-wide.** The plan asked for "toolCallingVerified without a toolCallingBenchmark is a validation problem" inside the per-id block. Implemented as `_check_tool_calling_claim` for every entry, additionally requiring `suite`, `date`, and `result`. An entry that does not make the claim is untouched, so the generalization costs nothing.
- **Both order assertions read the real `catalog.json`** rather than extending `model-display-order.fixture.json`. Stated because the plan asked which of the two approaches was taken. The mapping is the budgeted cost; the return is that the assertions track the shipped entry instead of a copy, so editing the entry's `task`, `agentic`, `tags`, or `releaseDate` moves them. No existing fixture row was touched, so the scope guard stays green.

## Regressions found and fixed

Three real regressions, all found by comparing against a measured baseline rather than assumed away, and all fixed rather than suppressed.

The root suite went to **498 failed / 63 files** against the 496/61 baseline:

1. `tests/unit/docs/v2.4.9-model-acceptance.test.ts` -- "minicpm5:2b has no job and no open question". A governance gate requiring every catalog id to hold exactly one job or be named in an open question. Satisfied by adding the opt-in job row, not by weakening the test.
2. `tests/unit/core/registry/modelAliases.test.ts` -- my own Phase 1 assertion. It asserted `runtimeId === "minicpm5:2b"`, correct while the model existed only in the runtime registry. Phase 3 added the catalog row, so the alias now folds to the Ollama pull tag, which is the alias table working as designed. Updated to the correct post-catalog behavior and extended to check both spellings resolve to the same record.

The desktop suite needed its own baseline, measured the same way (revert `catalog.json` and `catalogTabs.test.ts` to HEAD, run, restore):

3. `desktop/tests/coding-models.test.ts` -- "covers each ModelFamily at least once" enumerates the closed `ModelFamily` union and did not know about `minicpm5`. Same class as the `listFamilies` update in Phase 1: an in-scope consequence of extending the union.

**A caution for later phases about the desktop numbers.** That suite is not deterministic on this host. Across four runs of the same tree it reported 36, 37, 38, and 40 failures; the variance is entirely in the sqlite-, video-, and generation-queue-backed files, which are the same better-sqlite3 ABI family as the root suite. A single-run comparison there can manufacture or hide a regression. The reliable signal is whether a SPECIFIC named test fails, which is how regression 3 was identified and confirmed fixed.

Final state: root suite 496 failed / 5333 passed, identical to baseline. Desktop 36 failed / 2107 passed, at the low end of its observed range against a 38-failure baseline reading, with neither `catalogTabs.test.ts` nor `coding-models.test.ts` among the failures.
