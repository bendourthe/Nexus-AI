## What was built

`.github/ISSUE_TEMPLATE/` did not exist. It now holds a GitHub issue **form** (not a Markdown template, so fields can genuinely be required) asking four structured questions before any free text: Nexus version, install source, OS, and GPU. All four are `required: true`, and every one is a field the crash-class report consumes. Nothing was added that nothing reads.

`config.yml` routes questions, feature requests and security reports elsewhere. There is deliberately no feature-request form; proposals are argued in a discussion issue, and a model or runtime proposal is judged against the Phase 1 acceptance bar. `blank_issues_enabled` is left **true** on purpose: forcing every report through the bug form pushes ill-fitting reports into the wrong template or into silence, and the report script counts anything unversioned in its own bucket rather than dropping it, so a blank issue costs accuracy in one bucket instead of losing the report entirely.

## The sample the plan asked for is empty

The plan asked for at most five classes derived from the 50 most recent issues:

```
$ gh issue list --state all --limit 100 --json number --jq 'length'

```

**This repository has no issues at all.** There is no text to cluster, and clustering nothing would have produced five invented classes wearing the authority of a sample. The five classes are instead taken from the repository's own recorded field failures -- the v2.4.x known-gaps log and the defects those cycles fixed -- which is real evidence that is simply not issue-shaped yet. Each class records the cycle it came from: `install-provision`, `model-load`, `gpu-handoff`, `generation-failure`, `data-persistence`. Re-deriving them from real reports once the form has collected some is a known gap with a date-based exit condition.

## The tests caught two real bugs in my own classifier

Both are the over-broad-classifier failure the plan named, and neither was visible by reading the code.

1. **Form boilerplate contaminated every classification.** The form asks "How did you install it?" and most answers are the literal word `Installer`, which matched `install-provision`. Since that class is first in the order, **every form-filed issue** classified as an installer problem regardless of content. Fixed by classifying over the title plus only the narrative sections (`What happened?`, `What did you expect instead?`, `Steps to reproduce`), with a fallback to the whole body for issues that carry no form sections. The GPU field held the same trap, since its answers name hardware.
2. **The regexes were blind to inflection.** `\bfail\b` does not match "fails", so "Video generation fails after ten minutes" fell through to unclassified, and `\bsession(s)? (lost|missing)\b` did not match "sessions **are** missing". Widened to inflected forms with bounded gaps.

The first is the more instructive: it would have produced a confident, precise-looking report in which one class swallowed everything, and the per-class counts the plan insisted on printing are exactly what makes that visible.
