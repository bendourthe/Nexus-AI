### Changes

- `language: ["javascript-typescript"]` became a `matrix.include` with `javascript-typescript` and `python`, both at `build-mode: none`. Source-only extraction is deliberate: the runtimes carry multi-gigabyte ML dependency trees, and installing them to scan them would cost more than the scan and fail closed on any runner without CUDA wheels.
- A `paths-ignore` config excludes `**/.venv/**`, `**/node_modules/**`, `out/**`, `dist/**`. Defensive rather than necessary, because an extractor that finds a vendored venv reports a large number and a meaningless clean.
- `name: Analyze (javascript-typescript)` became `name: Analyze (${{ matrix.language }})`.
- Trigger branches gained `develop`.

### Correction to the plan: the job rename is a no-op for the existing check

The plan states, in bold, that templating the name **"renames the existing TS check, so branch protection must be updated deliberately."** It does not. The old value was the literal `Analyze (javascript-typescript)`, and the template renders exactly that string for the `javascript-typescript` matrix entry. The check name is byte-identical before and after; the only change is that a second check, `Analyze (python)`, now appears.

The warning was worth making and is wrong on this specific literal. Recorded as a Plan delta in the phase session history.

### Trigger-branch decision

The plan required choosing between adding `develop` to the triggers and gathering counts locally with the CodeQL CLI, and recording which. **`develop` was added**, because the CLI was skipped and there is therefore no local path to the count at all. The scan previously ran only on `main` plus a weekly cron, so a plan that publishes to `develop` could never see its own Python results before merge.

## 2.2 -- A sibling job audits what ships to users (T008)

### Sibling, not a matrix dimension

Confirmed against the existing job: `audit-py` is built entirely around a uv project. Its cache key is `hashFiles('scripts/installer/uv.lock')` and it runs `uv export --format requirements-txt`. The runtime sets are plain `requirements.txt` with no lock file, so neither transfers. `audit-runtimes` is a separate job.

### Resolution strategy: RESOLVED, not as written

Decided and recorded, because the two answers differ. The runtime sets carry **no exact pins at all** -- `runtimes/diffusion/requirements.txt` pins nothing (`torch`, `diffusers`, `transformers`, ... bare), and the other two carry only `>=` floors. "As written" therefore has no version for an advisory to match against. Resolving is also what matches a user machine, where the installer builds the venv from wheels resolved at payload-build time. pip-audit resolves each requirement to the latest matching version, which is what a fresh install gets.

### Measured counts

```
$ python -m pip_audit -r runtimes/<set>/requirements.txt --no-deps --progress-spinner off --format json

  ocr       :  21 packages audited,  0 with advisories
  audio     :  94 packages audited,  0 with advisories
  diffusion :  65 packages audited,  0 with advisories
  ---------------------------------------------------
  total     : 180 packages audited,  0 with advisories
```

An early reading of the `ocr` run as a "false clean on unpinned input" was wrong and is corrected here: pip-audit resolved 21 concrete packages with real versions, including transitives (`lxml`, `onnxruntime`, `opencv-python`), so the clean result is a real measurement rather than an empty scan.

### Naming

The plan offered renaming `audit-py` or naming the new job unambiguously. `audit-py` was briefly renamed to `pip-audit (installer venv, gating)` and then **reverted**: renaming churns a check name that branch protection references, for cosmetic gain, which is the same footgun the plan flagged for CodeQL. The new job is unambiguous on its own as `pip-audit (model runtimes)`.

### No live secret was allowlisted

Two representative cases, described rather than quoted:

A note on authoring: the first draft of `.gitleaks.toml` quoted the fixture values in its justifications, and the repository's own pre-write secret-scan hook blocked the write. That is the hook behaving correctly. The descriptions now describe the values instead.

## 2.4 -- Installer smoke on installer paths (T011)

`installer-smoke.yml` ran on `workflow_dispatch` plus a monthly cron. It now also runs on `pull_request` to `main` and `develop`, filtered to `scripts/installer/**` and the workflow file itself.

### CI-minute delta, stated as an increase

Billing multipliers are Linux 1x, Windows 2x, macOS 10x; the ceiling is each job's timeout.

| Matrix | Windows | macOS | Linux | Preflight | Billed minutes/run |
|---|---:|---:|---:|---:|---:|
| Full (cron, dispatch) | 30x2 = 60 | 30x10 = 300 | 30x1 = 30 | 10x1 = 10 | **400** |
| Pull request (macOS excluded) | 60 | -- | 30 | 10 | **100** |

Before: ~400 billed minutes per month (one cron run). After: the same cron, plus ~100 per installer-touching pull request. At roughly four such pull requests a month this **doubles** the workflow's spend. **No claim is made that it costs less.**

macOS is excluded from pull-request runs specifically because its 10x multiplier is 75 percent of a full run on its own; full coverage stays on the monthly cron. If a macOS-only installer regression ever ships, that is the trade to revisit.

## 2.5 -- D2, and the premise that was wrong (T012)

### The premise

D2 is framed in the plan as a decision that "changes branch protection, which is a repository-settings change". **There was no branch protection.**

```
$ gh api "repos/:owner/:repo/branches/develop/protection"
{"message":"Branch not protected","status":"404"}
$ gh api "repos/:owner/:repo/branches/main/protection"
{"message":"Branch not protected","status":"404"}
$ gh api "repos/:owner/:repo/rulesets"
(empty)
```

A public repository with no protection and no rulesets: nothing blocked a merge, so "gating" could only ever have meant "the job turns its workflow run red".

### The decision

**D2, answered 2026-09-10: gate the two checks whose backlog was measured at zero. Leave CodeQL Python reporting-only.**

| Check | Gating? | The count it rests on |
|---|---|---|
| `pip-audit (model runtimes)` | **Yes** | 180 packages, 0 advisories |
| `gitleaks` | **Yes** | 16 findings, 0 residual after a fully justified allowlist, 0 live secrets |
| `Analyze (python)` | No | **Unmeasured.** No local CLI; first count arrives on the integration PR |
| `Analyze (javascript-typescript)` | No | Unchanged from v0.9.0; still `continue-on-error` |
| `installer-smoke` | No | Not a security check; trigger-scope change only |

The reasoning is the measurement, not a policy preference: gating an empty backlog costs nothing today, and it converts any future red into new information. Both gating jobs carry an escape hatch for the failure mode the plan named -- `audit-runtimes` has an `IGNORE_VULNS` list (empty today) so one unfixable upstream ML advisory cannot hold every merge hostage, and `.gitleaks.toml` is extensible only after confirming a value is not live.

CodeQL Python stays reporting-only precisely because its backlog is unmeasured, which is what the Non-Goals table protects against: "Phase 2 lands both non-gating precisely so the backlog can be sized before anyone commits to clearing it."

### Branch protection, applied by operator decision

Separately from D2, the operator chose to apply branch protection now rather than record it as a gap. Applied to **both** `develop` and `main`:

```
required checks: 17 | strict: false | reviews: none | admins enforced: false
force push: false | deletions: false | conversation resolution: true
```

The 17 required checks are every CI job that (a) runs on **every** pull request and (b) was green on the most recent develop run:

`Lint TypeScript (Node 22.x / 24.x)`, `Test TypeScript (Node 22.x / 24.x)`, `Build TypeScript (Node 22.x / 24.x)`, `Coverage gate (80%)`, `nexus-check (repository)`, `check-architecture`, `check-prompts`, `docs/index.md sync check`, `pytest (runtimes/)`, `pip-audit (installer venv)`, `Package VSIX (smoke)`, `init.sh (Linux)`, `init.ps1 (Windows)`, `fast-bench (rendering)`.

Four exclusions, each deliberate, because a wrongly required check locks the repository:

1. **Path-filtered workflows are never required.** `installer-tests.yml`, `installer-smoke.yml` and `shell-build.yml` all carry `pull_request.paths`, so on a pull request that touches nothing in their filter they produce **no check at all** and a required entry would sit pending forever. This is the single most common way to lock a repo.
2. **`npm audit (production deps)` is currently red** and is excluded. Reproduced locally: 8 production vulnerabilities (1 low, 2 moderate, 5 high), and `sharp` via `@huggingface/transformers` carries libvips and libheif advisories with **no fix available**. Requiring it would have blocked the next merge immediately. Recorded as `BG-19`.
3. **`npm audit (dev + prod, non-blocking)`** declares itself non-blocking in its own name.
4. **`Analyze (*)`** runs `continue-on-error: true`, so it reports success even when it finds something; requiring an always-green check is theatre.

`gitleaks` and `pip-audit (model runtimes)` are **gating at the workflow level but not yet required in branch protection**, because neither has executed once. Requiring a check that has never produced a run is the second most common way to lock a repo. They are added after their first green run on the integration pull request; recorded as `QG-2`.

`enforce_admins` is false and no reviews are required, because this is a single-maintainer repository: requiring a review nobody can give would make merging impossible.
