## Goals First and Definition of Done

**The problem this solves.** Migrations run against user databases with no snapshot taken first. A user on a shipped build is one bad migration away from an unrecoverable database, and the project has no way to recover them or to prove the failure was survivable.

**The persona.** The user on a shipped build whose data cannot be reconstructed from anywhere else.

**Definition of Done.** A deliberately corrupted migration, run against a populated database, leaves the original byte-identical to its pre-run state, leaves a snapshot beside it, and stops the app -- with fail-before evidence recorded. Three launches with no migration pending create no snapshots at all.

## Phase 1: The database survives its own migrations

**Goal**: Make a failed migration recoverable and non-destructive, proven by a test that fails before the change and passes after.
**Prerequisites**: The v2.4.9 plan's Phase 1 (the written model and runtime acceptance bar) only. Nothing in snapshot-before-migrate reads a CodeQL result, an inventory entry, or an issue template. **This phase is not optional.** It is the only item protecting users from unrecoverable data loss, and being split into its own release must not be read as making it the first thing cut. D1 resolved to the split precisely so this work gets the version number its behavior change earns, not so it could be dropped.
**Stability Gate**: Each store detects whether a migration is actually pending, snapshots only then, retains the newest three, prunes older, skips above a size ceiling with a logged reason, and refuses to start half-migrated. A regression test fails against pre-change code and passes after.
**Verification Expectation**: *(fully local.)* Against a populated copy of a real database, run a deliberately failing migration and observe: the original file byte-identical to its pre-run state, a snapshot beside it, and the app refusing to start. Then run three successive migrations and observe exactly three snapshots retained with the oldest pruned. **Then run the app three times with no migration pending and observe that no new snapshot is created** -- this is the check that catches the P0 below.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Touches three storage modules on the hot path for every session; the failure mode being defended against is unrecoverable user data loss, and the change itself can cause it if wrong.

> **P0 found in review, and it reshapes this phase.** "Snapshot before any migration runs" means "snapshot on every cold start" for two of the three stores, and retain-three then destroys the very artifact this phase exists to produce.
>
> - `src/storage/MemoryStore.ts:167` is the **only** store with a migration-pending predicate (`if (currentVersion >= MEMORY_SCHEMA_VERSION) return;`).
> - `core/generations/GenerationDatabase.ts:511-524` runs its whole `migrate()` unconditionally on every construction (`CREATE TABLE IF NOT EXISTS` plus `PRAGMA table_info` column adds, then sets `user_version = 4` every time).
> - `src/storage/ChatHistoryStore.ts:44-94` runs all DDL unconditionally; `user_version` only gates the FTS rebuild.
>
> Three ordinary launches after an upgrade would prune the genuine pre-migration snapshot. Sub-task 1.2 therefore adds the predicate **before** any snapshotting, and this is unscoped work the first draft did not surface. It materially increases Phase 1's effort and is part of what D1 weighs.

### Sub-tasks

#### 1.1 -- decision: one shared snapshot helper, or three?

**Objective**: Decide the shape before touching three modules.

**Prompt**:
> A decision sub-task. Resolve before 1.2.
>
> **The question**: does snapshotting live in one shared helper all three stores call, or per store?
>
> **The constraint that actually decides it, missed in the first draft**: a shared helper **cannot take a database path**. `src/storage/MemoryStore.ts:101-114` accepts `dbOrPath: string | Database.Database`, and in the injected-handle branch (used by `MemorySubsystem` for connection sharing) the store never learns a filesystem path and `_ownsDb` is false. `core/generations/GenerationDatabase.ts:502-507` accepts `':memory:'`. So the helper must either derive the file from the open handle (`PRAGMA database_list`) or explicitly no-op on in-memory and borrowed connections -- and the borrowed-connection case needs a stated owner: does `MemorySubsystem` snapshot on the store's behalf?
>
> **Options.** (1) One shared helper. (2) Per-store implementation. (3) Shared snapshot-and-prune, per-store refuse-to-start, because start-up semantics genuinely differ.
>
> **Recommendation: option 3.** Snapshot-and-prune is mechanical and identical; "refuse to start" is not -- a memory store failing may be survivable where a chat history store failing is not. **If option 3 is chosen, refuse-to-start code lives per store, so T027's path is wrong and must be rewritten to the three store files.** T025-T027 paths below reflect the recommendation; rewrite them if 1.1 resolves otherwise.
>
> **Name the helper to avoid a collision.** `core/storage/StorageMigration.ts` already exists and means something entirely different -- the one-shot `~/.gemma-code/` to `~/.nexus/` directory move, with tests at `tests/unit/core/storage/StorageMigration.test.ts`. Prefer `core/storage/preMigrationSnapshot.ts` or `dbSnapshot.ts`. (Its header says "Removed in v1.1.0" while the file is still present; record that as a 6.1 finding.)
>
> Record the decision, the reading of all three modules, and the borrowed-handle owner in `docs/v2/v2.5/development/v2.5.0-migration-durability-evidence.md`.

#### 1.2 -- Migration-pending detection, then snapshot, retain three, prune

**Objective**: Snapshot only when a migration is actually pending, and make the copy consistent.

**Failure modes**: Without a pending predicate, two stores snapshot on every launch and retain-three destroys the real pre-migration copy -- the P0 above. A full disk or unwritable destination means the migration must **not** proceed; it stops and reports, because proceeding is the unrecoverable case this defends against. A naive file copy of a live WAL database yields a torn snapshot or misses the `-wal`/`-shm` sidecars. Above the size ceiling the snapshot is skipped with a logged reason and the migration proceeds -- deliberate, and logged, never silent. Two instances starting at once can race; guard with the migration path's existing lock, or add one and say so.

**Build class**: load-bearing.

**Prompt**:
> **First, add a `needsMigration()` predicate to each store**, reading `user_version` before running DDL:
>
> - `src/storage/MemoryStore.ts:167` already has one -- reuse it.
> - `core/generations/GenerationDatabase.ts:511-524` needs one; today `migrate()` runs unconditionally every construction.
> - `src/storage/ChatHistoryStore.ts:44-94` needs one; today `user_version` gates only the FTS rebuild.
>
> Nothing else in this phase is correct without this. Snapshot **only when the predicate is true**.
>
> Then implement snapshotting per the 1.1 decision. Before a pending migration runs, write a consistent snapshot beside the database named with the current version and an incrementing counter. Retain the newest three; prune older. Above a size ceiling (start at 500 MB as a **named constant**, not a literal) skip the snapshot and log the reason at a level a support reader sees.
>
> **Use `VACUUM INTO '<path>'`, not `db.backup()`.** All three stores open and migrate inside a **synchronous** constructor (`GenerationDatabase.ts:501-525`, `ChatHistoryStore.ts:36-42`, `MemoryStore.ts:101-118`), and better-sqlite3's `backup()` returns a Promise that cannot be awaited there without making construction async and rewriting every call site. `VACUUM INTO` is synchronous and also resolves the WAL sidecar problem -- all three set `journal_mode = WAL`, so a plain copy must not miss `-wal`/`-shm`. Verify the bundled SQLite is >= 3.27. If you conclude the constructors must go async instead, that is a much larger refactor than this phase budgets and must be raised before proceeding.
>
> If the snapshot cannot be written, **do not proceed with the migration.** Stop and report.
>
> Local context: this host's `better-sqlite3` sits on an Electron ABI baseline and 36 vitest failures are a known pre-existing condition, not a regression. Do not `npm rebuild` to chase them; distinguish new failures from that baseline and say which are which.
>
> Acceptance: three launches with no pending migration create **no** snapshots; three successive real migrations leave exactly three snapshots with the oldest pruned; an unwritable destination stops the migration; an oversized database logs the skip; in-memory and borrowed-handle cases behave as 1.1 decided.

- [ ] T026 Snapshot before pending migrations with retention and a size ceiling core/storage/preMigrationSnapshot.ts
- [ ] T027 [P] Wire predicate and snapshotting into the chat history store src/storage/ChatHistoryStore.ts
- [ ] T028 [P] Wire predicate and snapshotting into the memory store src/storage/MemoryStore.ts

#### 1.3 -- Refuse to start half-migrated

**Objective**: Stop the app rather than open a database in an unknown schema state.

**Failure modes**: Refusing to start could brick launch for a user whose database was already partially migrated by an **older** build; the message must name the snapshot path so recovery is possible without support contact, and this pre-existing-state case must be explicitly considered. If the check throws it fails closed (refuse), since failing open is the behavior being removed.

**Build class**: load-bearing.

**Prompt**:
> **The three stores are not equally at risk, and the first draft's generic framing hid that.**
>
> - `core/generations/GenerationDatabase.ts:511-524` already wraps its whole migration in `this._db.transaction(...)`, so DDL rolls back atomically and a half-migrated state is largely unreachable.
> - `src/storage/MemoryStore.ts:201` already writes its completion marker only on success, after the guarded blocks.
> - `src/storage/ChatHistoryStore.ts:44-94` is the store that genuinely can half-apply: multi-statement `exec` plus FTS table and trigger creation plus rebuild, with **no transaction**.
>
> Focus the work there. For the other two, verify and record the existing protection rather than adding redundant machinery.
>
> Where a completion marker is genuinely absent, add one -- a schema-version value written only after a migration fully succeeds. Do not infer completion by inspecting table shape; that guess will be wrong on the migration that matters.
>
> On detecting a partial state, stop with a message naming the snapshot path from 1.2. Do not auto-restore: silently swapping in a backup is its own data-loss story.
>
> Address the pre-existing-partial-state case: a user whose database was half-migrated by an older build now cannot launch. Say what they should do, in the message.
>
> Fail closed. Apply the per-store start-up semantics from 1.1.
>
> Acceptance: an interrupted `ChatHistoryStore` migration leaves the app refusing to start with a message naming the snapshot; a completed migration starts normally; a throwing check refuses; the other two stores' existing protection is verified and recorded.

#### 1.4 -- The fail-before / pass-after regression test

**Objective**: Prove the change does what it claims, against the pre-change code.

**Failure modes**: A test run only against post-change code proves nothing about the defect -- it must be demonstrated failing first, with that failure recorded. A fresh empty database cannot detect data loss; use a populated one. A filesystem stub thorough enough to make a torn copy impossible by construction validates the stub, not the code.

**Build class**: load-bearing. This is what makes Phase 1's claim checkable.

**Prompt**:

>
> Against a **populated** copy of a real database, run a deliberately failing migration and assert: the original file is byte-identical to its pre-run state; a snapshot exists beside it; the store refuses to open.
>
> Assert retention: three successive migrations leave exactly three snapshots, oldest pruned.
>
> **Assert the P0 case explicitly**: three constructions with no pending migration create no snapshots. Without this the regression suite would pass on the bug that motivated the predicate.

> **Demonstrate it failing first.** Stash the Phase 1 changes, run against pre-change code, and record the failure output in `v2.5.0-migration-durability-evidence.md`. Then restore and record the pass. A test only ever seen passing does not establish that it detects the defect.

>
