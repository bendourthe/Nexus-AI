**Project**: Nexus-AI

**Adoption target**: v2.5.1

**Plan Type**: Feature / Adoption
**Created**: 2026-09-15
**Seeded from**: [`v2.5.1-comparison-voicestudio-delta.md`](../comparisons/v2.5.1-comparison-voicestudio-delta.md) (items V1, V2, V4, V5) and [`v2.5.1-comparison-librechat.md`](../comparisons/v2.5.1-comparison-librechat.md) (item LC-2)
**Companion plan**: [`v2.6.0-adoption-chat-surface.md`](../../v2.6/plans/v2.6.0-adoption-chat-surface.md) carries the Chat-pillar items from the same two reports.
**Goal**: Replace the manual packaged-verification checklist with machine-checked gates -- a command-to-capability inventory, a deterministic packaged-bundle smoke that also proves zero outbound connections, and a release artifact-matrix check -- and give the desktop UI its first accessibility tooling.

## Overview

This plan is the **verification half** of a split. An earlier draft combined these gates with four Chat-pillar features; a seven-lens review found that the combination added `feat:` commits to a patch-numbered plan while `semantic-release` would compute a minor bump from those same commits. The Chat work now lives in the companion v2.6.0 plan, and this one contains only `fix:`, `ci:` and `docs:` class work, so the plan's name and the tooling's computed version agree.

The problem is narrow and stated plainly: today "the packaged build works" is a human judgement recorded in `docs/archive/v2/v2.4/development/v2.4.1-operator-checklist.md` with hand-captured screenshots, and "no data leaves the machine" is asserted in the README but measured nowhere. Both are the kind of claim that stays true right up until it quietly is not. This plan converts the deterministic part of each into something CI can fail.

Accessibility rides along for one reason that is worth stating, because it is the only cross-source evidence in either comparison: LibreChat gates accessibility on every UI pull request, and VoiceStudio independently ships a packaged accessibility smoke. Nexus-AI has no accessibility tooling at all -- no `jsx-a11y`, no `axe-core`, no `vitest-axe` anywhere in `package.json`, `desktop/package.json`, `eslint.config.mjs` or `desktop/eslint.config.mjs` -- against 230 files in `desktop/tests/`. It lands here rather than in the Chat plan because Phase 3 reuses its dependency, and because the Chat plan's new surfaces should be born against an existing gate.

## Strategy alignment

Per [`STRATEGY.md`](../../../../STRATEGY.md):

- **Target Problem served**: the local-first guarantee is the product's reason to exist, and this plan is the first work that measures it rather than asserting it.
- **Persona served**: the **maintainer** (secondary persona), explicitly. No phase here changes anything the primary persona sees. That is deliberate and is why this plan is separable from v2.6.0.
- **Key Metrics moved**: **M3** (zero non-loopback connections, currently unmeasured -- Phase 3 makes it a test), **M1** and **M2** indirectly (a packaged smoke catches install-shaped breakage earlier than a rehearsal), and **M4** (the artifact gate removes one class of field-reported defect entirely).

## Blocking decisions

### D1 -- Plan shape. **RESOLVED 2026-09-15: split.**

Phases delivering user-facing capability moved to `v2.6.0-adoption-chat-surface.md`. This plan keeps only verification work. Resolved because `semantic-release` derives the published version from commit types, so a `feat:` commit in a v2.5.1-named plan publishes v2.6.0 regardless of the plan's name. The v2.4.9 plan set the precedent by splitting for the same reason.

### D2 -- Accessibility gating severity. **RESOLVED 2026-09-15: full gate plus baseline.**

`jsx-a11y` lands non-gating repository-wide AND gating on changed files, so the existing backlog does not block while new surfaces are born compliant. The axe baseline is keyed on `(route, rule id, target selector)` triples, not on a count. Gates sub-task **1.2**.

### D3 -- Packaged-smoke driving mechanism. **UNRESOLVED -- gates sub-tasks 3.2 onward.** Owned by sub-task 3.1.

Driving a packaged Tauri window needs either WebDriver via `tauri-driver` (which has no macOS support) or a test hook compiled into the bundle. The choice is the difference between a two-day task and a multi-week platform exercise, and discovering it inside the harness is the expensive way to find out. Sub-task 3.1 is a spike that settles it before anything is built.

### D4 -- Where the release artifact check gates. **UNRESOLVED -- gates sub-task 3.4.** Owned by sub-task 3.4.

`semantic-release.yml` runs on push to `main` and performs publication; `release.yml` triggers on tag push and attaches assets. A check added to `release.yml` therefore runs after the GitHub Release already exists. The earlier draft named this problem in prose and then did not avoid it.

## Goals First and Definition of Done

**Target problem**: Packaged-build fitness and the zero-outbound guarantee are both human judgements today. A registered command can lose its user-visible surface with nothing to catch it. A release can publish with a platform artifact missing and the first report comes from a user.

**Persona**: the maintainer deciding whether a build ships.

**Definition of done**, each observable and each owned by a named sub-task:

## Phase 1: The accessibility gate

**Goal**: Give the desktop UI its first accessibility tooling, with a baseline that cannot be satisfied by coincidence.
**Prerequisites**: None.
**Stability Gate**: A deliberately violating fixture fails the lint rule set; the axe baseline exists as `(route, rule, selector)` triples over the four pillar routes; a newly introduced violation fails even when the total count drops.
**Verification Expectation**: Run `npx eslint desktop/src --format stylish` and observe named `jsx-a11y` rule findings with a recorded count. Then add a violation to one route, run the axe smoke, and observe it fail naming the new `(route, rule, selector)` triple; remove it and observe a pass. Delegate the procedure to [[functional-verification]]. A clean lint run on first enable is a red flag, not a pass: it almost always means the plugin is not wired into the flat config.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Mechanically simple, but flat-config wiring and a non-fungible baseline are both easy to get subtly wrong in ways that produce a gate which passes for the wrong reason.

#### 1.2 -- Add `jsx-a11y` to the desktop ESLint flat config

**Objective**: Give the desktop UI static accessibility linting, in a way that fails loudly if the rules ever stop being loaded.

**Failure modes**: On a file the parser cannot read, the run surfaces a parse error rather than silently skipping it, because a skipped file and a clean file are indistinguishable in a summary count. If the plugin fails to resolve, the run fails rather than passing with the rules absent -- asserted by the fixture below, not assumed. Do NOT add `dequelabs/axe-linter-action` or any `AXE_LINTER_API_KEY`: the vendor form is rejected under the MCP Registry Policy, and this is the local reverse-engineered equivalent.

## Phase 2: Command parity enforcement

**Goal**: Make it impossible for a registered command to exist without either a named user-visible capability or a justified exemption, and impossible for the gate to pass by finding nothing.
**Prerequisites**: Phase 1.
**Stability Gate**: `node scripts/check-command-parity.mjs` exits non-zero for an unmapped command, for a zero-command enumeration, and for a command count below the committed snapshot; and exits zero on the working tree.
**Verification Expectation**: Add a throwaway command to the sidecar registry and observe the checker name it and exit non-zero. Then rename the registration idiom so enumeration matches nothing, and observe the checker exit non-zero on the floor assertion rather than reporting a clean tree. Delegate the procedure to [[functional-verification]]. The second case is the important one: a gate that is green because it found nothing is the failure this phase exists to prevent.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Enumeration spans Rust macros, a sidecar registry and TypeScript call sites; getting the source wrong yields a checker that is green for the wrong reason, which is worse than no checker.

### Sub-tasks

#### 2.1 -- decision: which registry does the checker enumerate?

**Objective**: Bound the enumeration problem before writing a parser, because "enumerate every registration site" spans three languages and one of them hides registrations behind a macro.

**Prompt**:
> The registration sites span Rust (`#[tauri::command]` attributes plus the `generate_handler!` list in `desktop/src-tauri`), the sidecar method registry, and TypeScript `invoke` call sites. A Rust macro-aware parser is a project; a regex heuristic will silently miss conditionally-compiled and macro-generated commands, which is the "green for the wrong reason" outcome this phase exists to prevent. Decide and record: either (a) scope this cycle to the sidecar wire boundary only, which known gap NI-3 shows is the dangerous one, or (b) cover all three with a proven enumeration. Whichever is chosen, prove the enumeration against a known command count obtained by hand before the checker is written, and record both numbers in `docs/v2/v2.5/development/v2.5.1-phase2-evidence.md`. **Recommended: (a)**, because one proven registry beats three guessed ones and the scope can widen next cycle.

#### 2.2 -- Build the command-parity checker as its own module

**Objective**: Bind every registered command to a named capability or a justified exemption, without entangling it with the existing README-matching checker.

**Failure modes**: When the registry cannot be parsed, the checker exits non-zero with the parse error rather than reporting zero unmapped commands, because an empty parse and a clean tree are indistinguishable in a count. **When enumeration returns zero commands, or a count below the committed snapshot, the checker fails regardless of findings** -- this is the floor assertion, and it is the difference between a gate and a decoration. When one command is claimed by two capabilities, the conflict is reported rather than resolved by first match. When a capability names an evidence path that no longer exists, that is a finding, not a silent skip.

**Build class**: load-bearing.

**Prompt**:
> Write `scripts/check-command-parity.mjs` as a NEW module with its own exit code. Do not extend `scripts/check-feature-drift.mjs`: that checker's entire contract is "every entry's name appears verbatim in a bounded README region, in both directions", driven by a hard-coded REGIONS map, and `feature_list.json` requires a `region` on every entry that must resolve to a README heading. A sidecar method has no README name, so folding commands into that file forces either a checker failure or command names pushed into user-facing prose. Keep the command-to-capability map in its own file whose capability entries reference `feature_list.json` feature ids by id. Let an aggregate runner invoke both checkers so a README heading rename cannot fail the command gate and vice versa.
> Implement a first-class **exempt** category with a mandatory reason string, for health checks, readiness probes, telemetry and window management, which have no user-visible capability. Without it the inventory fills with invented capability names to make the gate green. Report exempt counts so a growth trend is visible.
> Implement the floor assertion: commit a snapshot of the discovered command count and fail when the live count is zero or below it.
> Record explicitly in the phase evidence that this checker does NOT close known gap **NI-3**: NI-3 is a value list duplicated across four declaration sites, and a command-to-capability mapping has no visibility into type-union copies. State NI-3 as an adjacent gap this phase leaves open.
> Implement clean-room: VoiceStudio's `tests/test_electron_parity_inventory.py` is AGPL and must not be copied.

- [x] T008 Write the command-parity checker with floor and exemption support scripts/check-command-parity.mjs
- [x] T009 Add the command-to-capability map referencing feature ids configs/command-capabilities.json

#### 2.3 -- Wire the gate so path scoping cannot defeat it

**Objective**: Make the gate catch the one commit class it exists for: a command added in a file nobody thought to include in a path filter.

**Failure modes**: When the checker crashes, the CI job fails rather than being treated as a pass. When the job runs on a checkout lacking the registration sites, it reports the missing input rather than zero findings.

**Prompt**:
> Add the command-parity checker to `.github/workflows/ci.yml`. **Do not path-scope this job**, or route it through the always-resolving aggregate required check. A path-filtered required check on GitHub reports as skipped and branch protection resolves it green, so a command registered in a file the filter does not enumerate merges unchecked -- and a commit that changes which files count as registration sites is exactly the commit this gate exists to catch. The checker is a fast Node script, so the cost of running it unconditionally is negligible against that failure mode.
> Add a test that a command added in a brand-new file still fails CI.
> This is a CI/CD change inside a non-CI/CD phase, which the plan lifecycle normally forbids: it is permitted here only because the gate IS this phase's deliverable, and that exception is recorded rather than assumed.

## Phase 3: Packaged-bundle verification and release artifact matrix

**Goal**: Prove the packaged bundle mounts, stays offline, and is the same bytes that ship.
**Prerequisites**: Phases 1 and 2.
**Stability Gate**: The packaged smoke fails on a mounted-but-empty shell; it records the SHA-256 of the bundle it launched and observes zero non-loopback connections; the release artifact check fails on a missing artifact and on a digest mismatch.
**Verification Expectation**: Build the bundle, inject a throwing component behind the error boundary so the app mounts but renders an empty container, run the smoke, and observe it fail naming the missing route-owned selector. Then run the artifact check against a manifest with one artifact removed and observe it name the missing artifact, and against a manifest whose digest differs from the smoked bundle and observe the mismatch. Delegate the procedure to [[functional-verification]].
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: The driving mechanism is unproven on two of three platforms, packaged-app harnesses are the classic source of CI flake, and the digest-identity binding touches the release path.

### Sub-tasks

#### 3.1 -- decision: how is the packaged window driven?

**Objective**: Settle D3 before any harness exists, because the answer determines whether this phase is small or large.

**Prompt**:
> Resolve blocking decision D3. Driving a packaged Tauri window requires either WebDriver via `tauri-driver` (which has no macOS support) or a test hook compiled into the bundle behind a build flag. Spike both far enough to launch the built bundle and read one route-owned element on Windows, then state what each costs on Linux and macOS. If the answer is "not automatable on macOS", record that as an owned known gap with a next step rather than discovering it inside the harness. Record the decision, the spike output, and the per-platform cost in `docs/v2/v2.5/development/v2.5.1-phase3-evidence.md`. Sub-tasks 3.2 and 3.3 do not start until this is resolved.

#### 3.2 -- Classify the operator checklist

**Objective**: Draw the line between what CI can own and what stays a human judgement, before writing assertions.

**Prompt**:
> Read `docs/archive/v2/v2.4/development/v2.4.1-operator-checklist.md` and classify every item as (a) deterministic and automatable, (b) GPU-dependent, (c) visually subjective, or (d) install-environment-dependent. Only class (a) is in scope for 3.3. The seeding comparison recommends a starting set of: bundle mounts, four pillar routes load, settings opens, sidecar handshake completes. #### 3.3 -- Build the packaged smoke with offline and identity assertions
