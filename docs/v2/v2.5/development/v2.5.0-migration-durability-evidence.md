# Migration durability evidence

## 1.1 Decision

Option 3: one shared snapshot helper, refuse-to-start per store.

`core/storage/preMigrationSnapshot.ts` owns `VACUUM INTO`, the 500 MB ceiling (`SNAPSHOT_SIZE_CEILING_BYTES`), and retain-three pruning. It no-ops when `PRAGMA database_list` has no main file (`:memory:` or a borrowed handle).

Borrowed-handle owner: the `MemoryStore` constructor that opened the path (`_ownsDb === true`). `MemorySubsystem` shares that connection and does not snapshot again.

`GenerationDatabase` already migrates inside a transaction. `MemoryStore` writes `user_version` only after its column adds. `ChatHistoryStore` is the store that can stop halfway, so it writes `*.migration-pending` and `assertNotHalfMigrated` refuses the next open, naming the newest snapshot. It does not copy the snapshot back.

`core/storage/StorageMigration.ts` is still the gemma-code directory move. Its "Removed in v1.1.0" header is stale. Not fixed here.
