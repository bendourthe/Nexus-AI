**Goal**: Ship MiniCPM5-2B as a fully wired agentic model -- catalog row, coding-runtime registration, and a measured tool-call format -- and, if and only if a local transcript proves it calls tools, promote it to the low-VRAM agentic default on BOTH the installer and desktop Settings so CPU-only and sub-4 GB users stop being routed to a revenue-capped license.

## Goals First and Definition of Done

**The problem this solves.** Nexus routes every CPU-only and sub-4 GB-GPU user to `lfm2.5:2.6b` as their agentic model. It is the only LLM in the catalog under a license that caps free commercial use at USD 10M annual revenue. Those users have the least hardware freedom to pick something else, and today they are given no alternative that fits.

**The persona.** A user installing Nexus on a laptop with no discrete GPU or a sub-4 GB card, who wants agentic coding to work at all.

**Definition of Done, phrased from that user's seat.** On a fresh install on a 3 GB host, the pre-ticked agentic model is MiniCPM5-2B, the user runs an agentic coding task end to end, and at least one real tool call completes, with the transcript recorded as evidence.

That definition is conditional by design. Phase 2 may find the model does not reliably emit parseable tool calls through Ollama. That is a legitimate outcome, not a failure: in that case the Definition of Done becomes "the negative result is recorded with transcripts, the entry does not claim agentic capability, and no user is routed to it." Phase 5's Goal review must accept that branch as a pass.

## The two-surface tier problem (read this before Phase 4)

The seeding comparison claimed display position is a pure function of a row's `tags` and `releaseDate`, identical on both surfaces. That is **wrong for the installer**, and the correction is the reason this plan is shaped the way it is.

Both surfaces share the comparator. They do not share its tier input.

- **Desktop Settings** reads the catalog row's own tags: `modelDisplayPolicy.ts` `modelDisplayTier` returns `recommended` when `row.tags` contains it.
- **The installer** discards them. `scripts/installer/src/nexus_installer/pages/typed_catalog.py` `_catalog_model_sort_row` builds the sort row with `tags: list[str] = []`, then appends `"required"` from `model.is_required` or `"recommended"` from membership in the `recommended.json` tier defaults. The catalog row's `tags` never reach the comparator.

Consequence: tagging `minicpm5:2b` as `recommended` in `catalog.json` alone promotes it in Settings and does nothing in the installer, where `lfm2.5:2.6b` would keep both the Recommended pill and the pre-tick. That is a user-visible contradiction between two surfaces about the same decision.

The resolution taken here, by decision: Phase 4 changes `recommended.json` as well, so both surfaces agree and the license benefit actually reaches the routed users. This is a first-install behavior change on low-VRAM hosts and is treated as a field-testing item, gated behind the Phase 2 tool-call evidence.

## Overview

MiniCPM5-2B is Apache-2.0, 1.56 GB at Q4_K_M, 128K context, released 2026-09-07, and built on stock `LlamaForCausalLM` so no custom kernel or minimum-Ollama-version negotiation is needed. It targets the sub-4 GB agentic slot.

Delivery spans two registries, not one. `core/registry/catalog.json` is the display and download roster. `core/registry/ModelCatalog.ts` (mirrored by `models.json`, kept in sync by `tests/unit/core/registry/catalog.test.ts`) is the coding-runtime roster carrying `promptFormat`, `toolFormat`, and sampling per model. `lfm2.5:2.6b` exists in both. A catalog-only entry would ship as an agentic model whose family falls through `modelAliases.ts` `familyFormats` to a `llama3-json` default, so its tool parser would be silently wrong. Phase 1 therefore registers the model in the runtime before anything else touches it.

The phase order is evidence first, capability second, product surface third. Nothing is written into the catalog until the model has been proven to resolve and to call tools, so a negative result costs a skipped phase rather than a revert.

**Shippable slices.** Phases 1 and 2 alone are a complete, useful outcome: the model is registered, probed, and the result recorded, with no user-visible change. Phase 3 adds the catalog row un-promoted. Phase 4 is the promotion. Stopping after any of the three is legitimate.

## Phase 2: Tool-call probe across every parser, and the decision

**Goal**: Measure what the model actually emits, test it against every existing parser rather than one, and record the promote-or-not decision on evidence. Satisfies comparison gate G1.

**Prerequisites**: Phase 1.
**Stability Gate**: The evidence file contains at least three raw transcripts and a per-parser verdict covering every member of `TOOL_FORMAT_NAMES`, plus a recorded decision. This gate is satisfied by a negative result as much as a positive one.
**Verification Expectation**: Run the Nexus agentic harness against `minicpm5:2b` with a tool-requiring prompt and observe, in the captured transcript, either a parsed tool-call span (pass) or raw unparsed output (fail). Quote the transcript either way; a tool-calling claim without a transcript does not satisfy this gate.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Genuine unknown with a correctness-critical outcome; the vendor documents tool calls against SGLang rather than Ollama, and a wrong call here routes low-VRAM users to a model that cannot call tools.

### Sub-tasks

#### 2.1 -- Probe the emitted format against all five parsers

**Objective**: Capture real output and test it against every existing option before concluding anything.

**Failure modes**: If the harness errors before reaching the model, the failure is Nexus-side rather than model-side, so the probe first confirms the Phase 1 plain completion still succeeds. If output is nondeterministic across runs, one transcript is not evidence, so the same prompt runs at least three times and every transcript is recorded. If the model emits nothing tool-shaped at all, that is a recorded result, not a reason to retry until something appears.

**Build class**: load-bearing. These transcripts are the evidence every later decision rests on.

**Prompt**:
> First confirm a plain, non-tool completion still succeeds, so a harness-side failure stays distinguishable from a model-side one.
>
> Then run a tool-requiring prompt against the locally pulled `minicpm5:2b` at least three times and capture every raw transcript verbatim.
>
> Run those transcripts through EVERY parser in `TOOL_FORMAT_NAMES` (`modules/coding/llm/ToolCallFormat.ts:430`), not just `gemma4-xml`. There are five. Report a per-parser verdict. Note the prior expectation and why it is only an expectation: `gemma4-xml` matches a Gemma-specific `<|tool_call|>` sentinel, so for an XML-style emitter on stock `LlamaForCausalLM` the likelier match is the existing `qwen-json`, which accepts the common `<tool_call>{json}</tool_call>` envelope, or `llama3-json` for a bare-JSON body.
>
> Append `## Tool-call probe` to the evidence file with all transcripts quoted verbatim, the observed format described precisely, and the five-way verdict table. Do not summarize the transcripts away.
>
> Acceptance: at least three quoted transcripts and an unambiguous verdict for each of the five parsers.

#### 2.2 -- decision: promote, add a grammar parser, or stop

**Objective**: Resolve the one branch whose answer changes what gets built.

**Prompt**:
> This is a decision record, not an implementation slice. Do not start 2.3, and do not start Phase 3 or Phase 4, until it is resolved and written down.
>
> **The question**: given the five-way verdict from 2.1, does `minicpm5:2b` proceed to a promoted agentic entry, and does it need a new parser to get there?
>
> **The options**:
> 1. *An existing parser accepts the format.* Name which one, correct the Phase 1 placeholder `toolFormat` to it, and proceed to Phase 3 and Phase 4. Cost: none. This is the likeliest good outcome and the one 2.1 is designed to detect.
> 2. *Add one new parser, named after the grammar.* Justified only when the format is stable across all three transcripts and no existing parser accepts it. Name it after the wire grammar it parses, NOT after the model: every existing key (`gemma4-xml`, `llama3-json`, `qwen-json`, `deepseek-json`, `lfm-pythonic`) names a grammar family shared across models, and a per-model key starts a union that grows one model at a time. **Hard stop condition**: if the wiring requires touching anything beyond `ToolCallFormat.ts` (its `STRATEGIES` record and the hand-maintained `TOOL_FORMAT_NAMES` array), the `ToolFormatName` union in `ModelCatalog.ts`, and their tests, that is out of budget and resolves this decision to option 3 instead. The comparable LFM adoption also needed a `HarnessSelector` profile and an A/B run; if this one does too, it is a bigger piece of work than this cycle has room for.
> 3. *Stop: do not ship an agentic entry.* The right answer when the model does not reliably emit parseable tool calls, or the format is unstable across runs, or option 2 hits its stop condition. Record it with the transcripts as evidence.

> **What settles it**: the three transcripts and the five-way verdict. Do not choose option 2 to avoid recording a negative result.
>
> **The true cost of option 3, stated plainly.** It is NOT "ship a plain untagged catalog row". A row with `task: agentic` and `agentic: true` whose recorded evidence says it cannot call tools would sort FIRST among untagged compatible Agentic rows in Settings, because its release date is the newest in the catalog. The most prominent unticked agentic option would be the one known not to work. So under option 3 the choice is: ship it as `task: chat` with card copy that makes no agentic claim, or do not ship a catalog row at all this cycle and keep only the Phase 1 runtime registration plus the recorded evidence. Pick one explicitly and say which.
>
> **What it unblocks**: 2.3 runs only under option 2. Phase 3 runs under options 1 and 2, and under option 3 only in its reduced `task: chat` form. Phase 4 runs only under options 1 and 2.
>
> Record the decision, its rationale, and the evidence it rests on under `## Parser decision` in the evidence file. Under option 3, also record a known gap via [[known-gaps-tracker]] classified `DF` (deferred), naming the transcript evidence and the condition under which this would be revisited.
