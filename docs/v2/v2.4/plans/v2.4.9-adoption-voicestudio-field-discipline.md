## Blocking decisions

These are not implementation slices. Each changes what this plan is, and none can be settled from the codebase alone.

### D1 -- Does Phase 5 belong in a patch release at all?

**The question.** v2.4.9 is a patch number. Phase 5 adds a user-visible refuse-to-start path, and (per the P0 below) needs a new `needsMigration()` predicate in two stores plus a completion marker written into existing user databases. `semantic-release` computes the version from commit types on `main`, and this work produces a `feat`, not a `fix`. The plan would therefore compute a minor while claiming to be v2.4.9.

**Options.**

1. **Split.** Phases 1-4 ship as v2.4.9 (all additive, no product behavior change, which is what a patch number means). Phase 5 becomes its own minor. Consequence: A11 (the updater) is gated on A5, so deferring Phase 5 also defers A11 further.
2. **Retarget the whole plan** to the next minor and let all six phases ship together.
3. **Keep as written** and reconcile the version at publication. Rejected by the reviewer as discovering the collision at 6.10 rather than deciding it at Phase 1.

**Recommendation: option 1.** It matches what the version numbers already mean, and Phases 1-4 are genuinely shippable without Phase 5. But this is a scope decision the owner makes, not the implementer.

**Until D1 is answered, Phase 5 stays in this plan.** If D1 resolves to option 1, move Phase 5 verbatim into its own plan file and renumber Phase 6.

## Goals First and Definition of Done

**The problem this solves.** Nexus-AI has strong CI breadth (19 workflows) and strong release documentation, but almost nothing that carries information *back* from a shipped build. `feature_list.json` claims v0.8.0 while `package.json` says 2.4.1 and the release line is at v2.4.8, and no job reads the file. `codeql.yml` scans `javascript-typescript` only, across 304 tracked Python files that include the entire PyQt installer and all three model runtimes. `pip-audit` covers `scripts/installer` and not the three runtime requirement sets that actually reach user machines. There are no issue templates, so a bug report does not say which build it came from. And migrations run against user databases with no snapshot taken first. Every one of those is a place where a field problem either cannot be measured or cannot be recovered from.

**The persona.** Two of them, wanting different things. The **operator** running field tests before a v2.4 release, who currently has to judge "field testing passed" rather than measure it. And the **user on a shipped build** whose database is one bad migration away from being unrecoverable.

**Definition of Done, phrased from those seats.**

1. A bug filed against Nexus states its build version because the form required it.
2. `scripts/crash-class-report.mjs` runs, bucketizes correctly against fixtures, and reports its unknown-version count truthfully. (Not "the top failure class is a number" -- see the honesty note below.)
3. A CI run fails when a feature named in `README.md` no longer exists in the tree.
4. CodeQL reports Python results with a non-zero scanned-file count.
5. A deliberately corrupted migration, run against a populated database, leaves the original intact and stops the app -- with fail-before evidence recorded.

**Clause 2 is deliberately weaker than the first draft's.** Every issue that exists today predates the form, so the first run of the crash-class report will put essentially everything in the unknown bucket. A Definition of Done that promised per-version measurement would be satisfiable only trivially, and the real measurement arrives weeks later in a different release. Phase 6.2 records "first non-empty crash-class report" as a known gap with a date-based exit condition.

**Slice-awareness.** If the release stops after Phase N, clauses owned by later phases are recorded as **deferred scope, not misses**. Phase 6.5 and 6.7 verify only the clauses whose owning phase landed. Clause ownership: 1 and 2 -> Phase 4; 3 -> Phase 3; 4 -> Phase 2; 5 -> Phase 5.

**What this plan is not.** It is not a security remediation cycle. Phases 2 and 3 turn *visibility* on; the findings they surface are triaged and recorded, not necessarily fixed in this release.

## Overview

Five delivery slices plus a terminal wrap-up phase, ordered so the cheapest and least invasive land first and the one that touches running code lands last.

Phases 1 and 2 change no product behavior: one writes two documents, the other adds CI coverage in reporting mode. Phase 3 makes an existing dead artifact true and then enforces it. Phase 4 gives field reports a shape. Phase 5 is the only phase that modifies code on the session hot path, and it carries the plan's only fail-before/pass-after regression requirement.

**Dependencies.** A6 (issue templates) must land before A7 (crash-class report) has real data. A5 (snapshot) must land before A11 (updater, out of scope) is safe. A5 and A7 are **independent** -- the crash report reads issue bodies, not snapshots. The seeding comparison's first draft drew a spurious `A5 -> A7` edge; it has been corrected there.

**Shippable slices.** Phase 1 alone is a complete outcome. So are 1-2, 1-3, and 1-4. Phase 6 is slice-aware by construction (see Definition of Done).

**Reverse-engineer-first ordering.** Per comparison Section 5.4, `skill-native` items (Phase 1) precede `re-full` items (Phases 2-5); the single `re-partial` item (A11) is out of scope. This plan adds no new outbound call, no new runtime dependency, and no third-party data processor. It does require **the GitHub token an operator already holds**, for the `gh`-based crash-class report in 4.2 -- that is not a new credential, but the first draft's "zero credentials" phrasing was too strong and is corrected here.

#### 1.2 -- The repo-local standards critic

**Objective**: Add an agent that reviews against Nexus-AI's own documented standards and is structurally unable to approve a release.

**Failure modes**: Asked to approve a push, release, or merge, it states plainly that it cannot consent on the owner's behalf and gives its technical verdict instead. If a standards file (`CLAUDE.md`, `AGENTS.md`, `docs/reference/model-acceptance.md`) is missing or unreadable, it reports which and reviews against the remainder rather than silently reviewing against nothing. If it finds nothing, it accounts for what it examined; an unaccounted "looks good" is a failed review. If two standards conflict, it names both and does not silently pick one.

**Build class**: load-bearing. This is what makes 1.1's bar enforceable by something other than memory.

**Prompt**:
> Create `.claude/agents/nexus-standards-judge.md`, a repo-local reviewer agent carrying **this project's** documented standards -- `CLAUDE.md`, `AGENTS.md`, `docs/reference/model-acceptance.md` (from 1.1), and the branching and plan-lifecycle rules. It is a critic, not an approver.
>
> Two properties are load-bearing and must appear in the definition itself:
>
> 1. **It never authorizes an irreversible or outward-facing action** -- publishing a release, pushing to a protected branch, deleting data, merging a PR. It may say "this meets the bar"; it may not say "go ahead".
> 2. **Its job is to find what is wrong.** A review returning "looks good" has usually not been done. Assume the author has a blind spot and go looking.
>
> Balance with fairness: a finding it cannot substantiate is noise, and noise trains readers to ignore it. Every finding names a concrete failure -- specific input or state, and the wrong result.
>
> Give it `Bash, Read, Grep, Glob` and no write tools. Set a model tier in frontmatter.
>
> Write from described behavior, not by copying VoiceStudio's `owner-judge.md`; that source is AGPL and this repository is MIT.
>
> Acceptance: invoked against the pinned v2.4.8 range, it produces a substantiated finding or an explicit account of what it examined.

#### 2.2 -- A sibling job audits what ships to users

**Objective**: Audit the three runtime requirement sets that reach user machines.

**Failure modes**: An ML dependency with a known advisory and no upstream fix must be recorded, not made a merge blocker -- an unfixable advisory blocking every merge trains the team to bypass the job. An unparseable or missing requirements file fails loudly naming the file rather than skipping silently. Two runtime sets pinning conflicting versions of one package is reported as a finding, not resolved.

**Build class**: load-bearing.

**Prompt**:
> Add runtime dependency auditing for `runtimes/audio/requirements.txt`, `runtimes/diffusion/requirements.txt`, and `runtimes/ocr/requirements.txt`.
>
> **This is a sibling job, not a matrix dimension on the existing one.** The existing `audit-py` job (`.github/workflows/ci.yml:509-539`, named `pip-audit (installer venv)`) is built entirely around a uv project: its cache key is `hashFiles('scripts/installer/uv.lock')` and it runs `uv export --no-hashes --no-annotate --format requirements-txt --no-emit-project`. ## Phase 5: The database survives its own migrations

**Goal**: Make a failed migration recoverable and non-destructive, proven by a test that fails before the change and passes after.
**Prerequisites**: **Phase 1 only.** Sequenced last by risk preference, not by dependency -- nothing in snapshot-before-migrate reads a CodeQL result, an inventory entry, or an issue template. **This phase is not optional.** It is the only item protecting users from unrecoverable data loss, and its position last must not be read as making it the first thing cut. See D1 for whether it belongs in this release at all.
**Stability Gate**: Each store detects whether a migration is actually pending, snapshots only then, retains the newest three, prunes older, skips above a size ceiling with a logged reason, and refuses to start half-migrated. A regression test fails against pre-change code and passes after.
**Verification Expectation**: *(fully local.)* Against a populated copy of a real database, run a deliberately failing migration and observe: the original file byte-identical to its pre-run state, a snapshot beside it, and the app refusing to start. Then run three successive migrations and observe exactly three snapshots retained with the oldest pruned. **Then run the app three times with no migration pending and observe that no new snapshot is created** -- this is the check that catches the P0 below.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Touches three storage modules on the hot path for every session; the failure mode being defended against is unrecoverable user data loss, and the change itself can cause it if wrong.

#### 5.2 -- Migration-pending detection, then snapshot, retain three, prune

**Objective**: Snapshot only when a migration is actually pending, and make the copy consistent.

**Failure modes**: Without a pending predicate, two stores snapshot on every launch and retain-three destroys the real pre-migration copy -- the P0 above. A full disk or unwritable destination means the migration must **not** proceed; it stops and reports, because proceeding is the unrecoverable case this defends against. A naive file copy of a live WAL database yields a torn snapshot or misses the `-wal`/`-shm` sidecars. Above the size ceiling the snapshot is skipped with a logged reason and the migration proceeds -- deliberate, and logged, never silent. Two instances starting at once can race; guard with the migration path's existing lock, or add one and say so.

**Build class**: load-bearing.

**Prompt**:
> **First, add a `needsMigration()` predicate to each store**, reading `user_version` before running DDL:
>
> - `src/storage/MemoryStore.ts:167` already has one -- reuse it.
> - `core/generations/GenerationDatabase.ts:511-524` needs one; today `migrate()` runs unconditionally every construction.
> - `src/storage/ChatHistoryStore.ts:44-94` needs one; today `user_version` gates only the FTS rebuild.
>
> Nothing else in this phase is correct without this. Snapshot **only when the predicate is true**.
>
> Then implement snapshotting per the 5.1 decision. Before a pending migration runs, write a consistent snapshot beside the database named with the current version and an incrementing counter. Retain the newest three; prune older. Above a size ceiling (start at 500 MB as a **named constant**, not a literal) skip the snapshot and log the reason at a level a support reader sees.
>
> **Use `VACUUM INTO '<path>'`, not `db.backup()`.** All three stores open and migrate inside a **synchronous** constructor (`GenerationDatabase.ts:501-525`, `ChatHistoryStore.ts:36-42`, `MemoryStore.ts:101-118`), and better-sqlite3's `backup()` returns a Promise that cannot be awaited there without making construction async and rewriting every call site. `VACUUM INTO` is synchronous and also resolves the WAL sidecar problem -- all three set `journal_mode = WAL`, so a plain copy must not miss `-wal`/`-shm`. Verify the bundled SQLite is >= 3.27. If you conclude the constructors must go async instead, that is a much larger refactor than this phase budgets and must be raised before proceeding.
>
> If the snapshot cannot be written, **do not proceed with the migration.** Stop and report.
>
> Local context: this host's `better-sqlite3` sits on an Electron ABI baseline and 36 vitest failures are a known pre-existing condition, not a regression. Do not `npm rebuild` to chase them; distinguish new failures from that baseline and say which are which.
>
> Acceptance: three launches with no pending migration create **no** snapshots; three successive real migrations leave exactly three snapshots with the oldest pruned; an unwritable destination stops the migration; an oversized database logs the skip; in-memory and borrowed-handle cases behave as 5.1 decided.
