### `weights.files[].path` -- which source, and why

**Decision: the repository filename as published, `MiniCPM5-2B-Q4_K_M.gguf`.**

### `promptFormat` -- a real decision, stated

**Chosen: `qwen`.** This is not implicit reuse. MiniCPM5's vendor `chat_template.jinja`
renders turns as `<|im_start|>{role}\n...<|im_end|>`, which is ChatML. `ollama show` on the
pulled blob independently lists `<|im_start|>` and `<|im_end|>` among its stop tokens. The
repo's `qwen` PromptFormat (`modules/coding/llm/PromptFormat.ts:94`) emits exactly
`<|im_start|>${role}\n${content}<|im_end|>` and closes with `<|im_start|>assistant\n`, so it
is the correct existing member of the closed `PromptFormatName` union for this model.

No new `PromptFormatName` member was added. The plan's 2.2 stop condition names
`PromptFormat.ts` as an out-of-budget site, and no change there is needed.

### `toolFormat` -- placeholder, and why it is very likely wrong

**Set to `qwen-json` as the Phase 1 placeholder**, per the plan's instruction to pick an
existing member of `ToolFormatName` and let Phase 2 confirm or change it. No new format name
was invented here.

It is recorded now, before Phase 2 runs, that two independent first-party sources already
predict **no existing parser will accept this model's output**:

1. The vendor `chat_template.jinja` renders tool calls as nested XML with named attributes:

   ```
   <function name="function-name"><param name="param-name">param-value</param></function>
   ```

   with CDATA wrapping for values containing `<`, `&`, or newlines, and a `<tool_sep>`
   convention for multiple calls.

2. The model card states it plainly: "MiniCPM5-2B emits XML-style tool calls and SGLang's
   built-in `minicpm5` parser converts them to OpenAI-compatible `tool_calls` natively",
   with `--tool-call-parser minicpm5`. A dedicated vendor parser exists precisely because
   the grammar is its own.

Measured against the five parsers Nexus ships: `gemma4-xml` matches a `<|tool_call|>`
sentinel wrapping JSON; `qwen-json` matches `<tool_call>{json}</tool_call>`; `llama3-json`
matches a bare JSON object; `deepseek-json` matches the DeepSeek envelope; `lfm-pythonic`
matches a pythonic call list. None of the five accepts `<function name="..."><param
name="...">...</param></function>`.

The placeholder is therefore expected to be corrected in Phase 2, and the `qwen-json` value
was chosen only because it is the closest XML-enveloped member and the plan forbids inventing
a name before the probe. **The plan's stated prior that `qwen-json` is the likely match is
contradicted by this evidence**; that is recorded here rather than discovered later, and it
is carried into the Phase 1 session history as a plan delta.

The `familyFormats` branch matters for exactly this reason: `minicpm5` matches none of the
earlier prefix branches, so without it the family falls through to the final
`{ promptFormat: "llama3", toolFormat: "llama3-json" }` return at `modelAliases.ts:105` and
the model runs on a silently wrong parser. The new test asserts `toolFormat !== "llama3-json"`
rather than a fixed value, so it survives the Phase 2 correction while still catching removal
of the branch.
