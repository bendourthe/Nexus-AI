### `promptFormat` -- a real decision, stated

**Chosen: `qwen`.** This is not implicit reuse. MiniCPM5's vendor `chat_template.jinja`
renders turns as `<|im_start|>{role}\n...<|im_end|>`, which is ChatML. `ollama show` on the
pulled blob independently lists `<|im_start|>` and `<|im_end|>` among its stop tokens. The
repo's `qwen` PromptFormat (`modules/coding/llm/PromptFormat.ts:94`) emits exactly
`<|im_start|>${role}\n${content}<|im_end|>` and closes with `<|im_start|>assistant\n`, so it
is the correct existing member of the closed `PromptFormatName` union for this model.

No new `PromptFormatName` member was added. The plan's 2.2 stop condition names
`PromptFormat.ts` as an out-of-budget site, and no change there is needed.

### `toolFormat` -- placeholder, and why it is very likely wrong

**Set to `qwen-json` as the Phase 1 placeholder**, per the plan's instruction to pick an
existing member of `ToolFormatName` and let Phase 2 confirm or change it. No new format name
was invented here.

It is recorded now, before Phase 2 runs, that two independent first-party sources already
predict **no existing parser will accept this model's output**:

1. The vendor `chat_template.jinja` renders tool calls as nested XML with named attributes:

   ```
   <function name="function-name"><param name="param-name">param-value</param></function>
   ```

   with CDATA wrapping for values containing `<`, `&`, or newlines, and a `<tool_sep>`
   convention for multiple calls.

2. The model card states it plainly: "MiniCPM5-2B emits XML-style tool calls and SGLang's
   built-in `minicpm5` parser converts them to OpenAI-compatible `tool_calls` natively",
   with `--tool-call-parser minicpm5`. A dedicated vendor parser exists precisely because
   the grammar is its own.

Measured against the five parsers Nexus ships: `gemma4-xml` matches a `<|tool_call|>`
sentinel wrapping JSON; `qwen-json` matches `<tool_call>{json}</tool_call>`; `llama3-json`
matches a bare JSON object; `deepseek-json` matches the DeepSeek envelope; `lfm-pythonic`
matches a pythonic call list. None of the five accepts `<function name="..."><param
name="...">...</param></function>`.

The placeholder is therefore expected to be corrected in Phase 2, and the `qwen-json` value
was chosen only because it is the closest XML-enveloped member and the plan forbids inventing
a name before the probe. **The plan's stated prior that `qwen-json` is the likely match is
contradicted by this evidence**; that is recorded here rather than discovered later, and it
is carried into the Phase 1 session history as a plan delta.

The `familyFormats` branch matters for exactly this reason: `minicpm5` matches none of the
earlier prefix branches, so without it the family falls through to the final
`{ promptFormat: "llama3", toolFormat: "llama3-json" }` return at `modelAliases.ts:105` and
the model runs on a silently wrong parser. The new test asserts `toolFormat !== "llama3-json"`
rather than a fixed value, so it survives the Phase 2 correction while still catching removal
of the branch.

## Tool-call probe

Sub-task 2.1. Measures what the model actually emits and tests it against every parser Nexus ships, before concluding anything. Satisfies comparison gate G1.

### Harness-side control

The plan requires a plain completion to still succeed first, so a harness-side failure stays distinguishable from a model-side one. Re-confirmed at the start of this phase:

```
prompt:   "In one sentence, what is the capital of France?"
response: 'The capital of France is Paris.'   done_reason: stop
```

The harness reaches the model. Any tool-call miss below is therefore model-side or runtime-side, not a broken probe.

### Probe method

`/api/generate` with `raw: true` and a hand-rendered ChatML prompt, NOT `/api/chat` with the `tools` argument. Two reasons, both load-bearing:

1. Nexus's coding runtime renders its own prompt (`PromptFormat.ts`) and parses RAW model text (`ToolCallFormat.ts`). It does not consume Ollama's structured `tool_calls`. Raw text is the only thing that answers decision 2.2.
2. Ollama's bundled template for this GGUF has no tools support at all. The template blob is 204 bytes and handles only `.System`, `.Prompt`, and `.Response`:

   ```
   {{ if .System }}<s><|im_start|>system
   {{ .System }}<|im_end|>
   {{ end }}{{ if .Prompt }}<|im_start|>user
   {{ .Prompt }}<|im_end|>
   {{ end }}<|im_start|>assistant
   <think>

   </think>

   {{ .Response }}<|im_end|>
   ```

   There is no `{{ if .Tools }}` branch, so tool definitions passed to `/api/chat` are never rendered into the prompt. Confirmed empirically: `/api/chat` with a `get_weather` tool returned `tool_calls: null` and prose declining to answer, because the model was never shown the tool.

The tool-definition block was copied verbatim from the vendor `chat_template.jinja`, so the model sees the framing it was trained on. Inventing our own framing would make a negative result meaningless.

Twelve transcripts were captured: four prompt shapes (single call, single call variant, multi-call, and a deliberate no-call control) at three seeds each, exceeding the three the plan requires.

### Raw transcripts, quoted verbatim

Single tool call, all three seeds identical:

```
 name="get_weather"> name="city">Paris
```

Single call, second prompt (`/etc/hosts`), seeds 2 and 3:

```
 name="read_file"> name="path">/etc/hosts
```

Seed 1 of that prompt refused instead of calling, which is a model-behavior data point, not a format one:

```
I cannot directly access or read files on the user's system, including /etc/hosts, as I
operate without direct file system access. To see the contents of /etc/hosts, you would
need to use a command like `cat /etc/hosts` on the system where that file exists. ...
```

Multi-call, all three seeds identical (the `\n` is a real newline in the response string):

```
 name="get_weather"> name="city">Tokyo name="unit">celsius
 name="read_file"> name="path">/tmp/notes.txt
```

No-call control, correctly emitting no tool-shaped output:

```
Hello, hello, hello.        /        Hello.
```

### The observed format, described precisely

The transcripts are the vendor grammar **with every structural tag removed**. Expected, per `chat_template.jinja`:

```
<function name="get_weather"><param name="city">Paris</param></function>
```

Observed:

```
 name="get_weather"> name="city">Paris
```

`<function`, `</function>`, `<param`, and `</param>` are all absent. Everything else, the attribute text, the values, and their order, is intact and correct.

### Root cause, proven rather than inferred

`tokenizer_config.json` for `openbmb/MiniCPM5-2B` declares all four tags as **special tokens**:

```
id=18  content='<function'    special=True
id=19  content='</function>'  special=True
id=20  content='<param'       special=True
id=21  content='</param>'     special=True
```

Ollama's detokenizer skips special tokens when building the `response` string. The model emits correct, well-formed tool calls; the delimiters are destroyed on the way out.

**Controlled experiment.** The model was asked to echo two ordinary pseudo-tags and two special ones on one line:

```
prompt:   Echo these four items on one line, separated by spaces, nothing else:
          <banana> <function <param </xyz>
response: '<banana>   </xyz>'
```

`<banana>` and `</xyz>` survive. `<function` and `<param` vanish, leaving exactly the whitespace that separated them. This isolates the mechanism: it is detokenization, not prompting, not sampling, and not a malformed model.

**No escape hatch exists at this Ollama version.** A top-level `"special": true` on `/api/generate` was tested against Ollama 0.32.15 and changed nothing (`'<banana>   </xyz>'` again). `raw: true` governs prompt templating, not output detokenization. The stop tokens in the params blob (`<s>`, `<|im_start|>`, `<|im_end|>`, `<think>`, `<|im_start|>user`) do not include the function tags, so stop-sequence truncation is excluded as an explanation.

## Parser decision

Sub-task 2.2. Decision record. Resolved before any Phase 3 or Phase 4 work began.

### The question

Given the five-way verdict, does `minicpm5:2b` proceed to a promoted agentic entry, and does it need a new parser to get there?

### Decision: option 3 -- do not ship an agentic entry

Sub-form chosen, explicitly, as the plan requires: **ship it as `task: chat` with card copy that makes no agentic claim.** Not "no catalog row at all".

### Why not option 1

No existing parser accepts the format. Nine tool-calling transcripts, five parsers, zero matches. This is not a close call.

### Why not option 2

Option 2 permits adding one parser named after the wire grammar, and on the surface its preconditions look met: the format is stable across all three transcripts and no existing parser accepts it. It fails on the substance.

**A parser for the documented grammar would be dead code.** A `minicpm-xml` strategy matching `<function name="...">` can never fire, because those tokens are removed before any Nexus code sees the string. It would pass its own fixtures (written from the vendor grammar) and return zero on every real transcript. That is the worst available outcome: a green test suite asserting a capability the product does not have.

**A parser for the observed, stripped text would not be a grammar parser.** It would have to reconstruct calls from ` name="x">` fragments with no start delimiter, no end delimiter, and no call boundary. Concretely, in

```
 name="get_weather"> name="city">Tokyo name="unit">celsius
 name="read_file"> name="path">/tmp/notes.txt
```

nothing marks where the `get_weather` call ends and `read_file` begins except a newline the grammar never promised, and nothing marks where the value `Tokyo` ends except the next ` name="`. Any parameter value containing the literal ` name="` would silently corrupt the parse, and ordinary prose could be mistaken for a call. The plan's own failure-mode requirement for 2.3, that a malformed call return no span rather than a partially-populated one, cannot be met when the delimiters that define "malformed" are gone.

**It would also violate the naming rule.** Every existing key names a grammar family shared across models. A heuristic over tag-stripped output names an artifact of one detokenizer in one runtime version, not a grammar. It is exactly the per-model key the plan warns starts a union that grows one model at a time.

**The hard stop condition is independently tripped.** The only correct fixes live outside the permitted three sites:

- Change Ollama's detokenization. Not in this repository.
- Move Nexus to `/api/chat` and consume Ollama's structured `tool_calls`. That is an `OllamaClient` / `HarnessSelector` change, explicitly named as out of budget. It would also not work today: Ollama's bundled template for this GGUF has no tools branch, so the model is never shown the tools at all.

The plan says a stop-condition trip "resolves this decision to option 3 instead". It does.

### Why `task: chat` rather than no row at all

The plan requires this sub-choice to be made explicitly, because a `task: agentic` row with `agentic: true` would sort FIRST among untagged compatible Agentic rows (its release date is the newest in the catalog), making the most prominent unticked agentic option the one known not to work.

`task: chat` with `agentic: false` avoids that entirely: the row does not appear on the Agentic tab. What remains is honest and useful on its own terms, for the same low-VRAM persona the plan was written for: Apache-2.0, 1.56 GB, 128K context confirmed by local generate, coherent output, CPU-capable, no revenue cap. A shipped row also makes the Phase 1 runtime registration reachable rather than leaving a registered model no user can find.

What it does NOT do is satisfy the plan's Goal, which was the agentic slot. That is stated plainly rather than papered over.

### What this unblocks and blocks

- Phase 4 (promotion on both surfaces): **SKIPPED ENTIRELY**. `catalog.json` `tags` stays `[]` and `recommended.json` is not touched. Low-VRAM users continue to be routed to `lfm2.5:2.6b`.
- `toolCallingVerified`: `false`, with no `toolCallingBenchmark` object. No placeholder.
