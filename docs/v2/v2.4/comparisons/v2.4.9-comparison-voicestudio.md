## Section 1: Executive Summary

VoiceStudio is an unusually close structural analogue to Nexus-AI. Both are local-first **Tauri 2 desktop shells** wrapping **Python model runtimes**, both auto-detect GPU compute, both ship multi-platform installers, both keep user data in SQLite outside the app bundle, and both are governed by a dense owner-authored `CLAUDE.md`. They differ only in domain (voice vs. chat/coding/image/video). That similarity makes the gaps unusually transferable: this is not a comparison against a tool from another category, it is a comparison against a peer that has been through more field-feedback cycles.

Nexus-AI is ahead on **CI breadth** (19 workflows vs. 8, including CodeQL, Scorecard, commitlint, coverage-diff, semantic-release, and four dedicated installer workflows), on **security config as a single source of truth** (`nexus.security.toml` with a generator and a drift gate), and on **release documentation discipline** (per-version `docs/v2/v2.X/` trees with plans, known-gaps, and comparisons).

VoiceStudio is ahead on the machinery that connects a shipped build back to the repository: a **canonical feature inventory that CI enforces**, a **written acceptance bar for new model engines**, **database snapshots before migration**, **stale-build deflection in bug reports** with a **crash-class recurrence report** that measures whether the top failure class is actually shrinking, and **Stable/Preview update channels**.

**11 adoption candidates** and **7 strengths to preserve** were identified. The four highest-value items are all cheap and all reinforce the field-testing gate that currently blocks the v2.4 release: enforce the feature inventory, write the model acceptance bar, snapshot the database before migrating, and add issue templates that stamp the build version.

**Overall recommendation: selectively adopt.** Take the field-feedback and inventory-enforcement machinery. Do not take the analytics stack, the marketing scripts, or any source code (license conflict, Risk R1).

## Section 3: Dimension-by-Dimension Comparison

Legend: `+` external-only (adoption candidate) - `=` current-only (strength to preserve) - `~` both, different approach - `.` equivalent

### 1. Project Identity

- `.` Both carry a strong README, a CHANGELOG, and an owner-authored `CLAUDE.md` + `AGENTS.md` pair.
- `=` Nexus-AI has `SECURITY.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md` **and** `CONTRIBUTING-BEGINNERS.md`. VoiceStudio has no `SECURITY.md`.
- `+` VoiceStudio maintains a translated README (`README_CN.md`) and `LICENSE-NOTICE.md` for bundled-model terms. Nexus-AI ships model runtimes with upstream licenses and has no equivalent notice file.

### 2. Technology Stack

- `.` Near-identical shells (Tauri 2 + React + Vite + Tailwind).
- `~` VoiceStudio uses bun + uv + turbo as a monorepo toolchain; Nexus-AI uses npm with workspace-style directories. Both work; no adoption case.
- `+` `deps:check` via `taze -r --maturity-period 7` (`package.json`) refuses dependency bumps younger than 7 days -- a cheap supply-chain cooling-off period. Nexus-AI pins CI actions by SHA (good) but has no maturity window on runtime dependency upgrades.

### 3. AI Assistant Configuration

- `=` Nexus-AI is far richer here: `.claude/`, `.agents/`, `.codex/`, `.nexus/`, hooks in `.husky/`, and the Nexus-Hub skill catalog.
- `+` `.claude/agents/owner-judge.md` is a repo-local **standards critic**: it carries the owner's documented standards, is explicitly barred from authorizing "an irreversible or outward-facing action", and states that "a review that returns 'looks good' has usually not been done", citing two real bugs that agreeable reviews let through. Nexus-AI's repo-local agents are executors (`pr-manager`, `taskmaster`), not a project-specific critic.
- `+` `skills-lock.json` pins externally-sourced skills by SHA-256 content hash (`fastapi-python`, `vite` from `mindrally/skills`). Nexus-AI consumes Nexus-Hub skills with no equivalent integrity pin.

### 4. Project Structure

- `.` Both are deep, domain-partitioned monorepos.
- `=` Nexus-AI's `docs/v2/v2.X/{plans,comparisons,known-gaps}` lifespan-based tree is more disciplined than VoiceStudio's flat `docs/`.
- `.` `docs/STRUCTURE.md` gives a single navigable map of the tree; Nexus-AI's `ARCHITECTURE.md` plus `docs/index.md` covers the same ground. Equivalent.

### 5. Skills and Capabilities

- `+` **`docs/features.yaml` is a canonical, machine-checked feature inventory.** It lists user-facing features, TTS engine ids, and ASR engine ids, and each entry can require a verbatim README string and an existing doc file.
- `=` Nexus-AI **has** `feature_list.json` -- but it is stamped `"version": "v0.8.0"` with `testedAt: 2026-05-06` while the project ships 2.4.1, and a grep across `.github/workflows`, `scripts/*.mjs`, and `package.json` returns **zero references** to it. It is a dead artifact.

### 6. Commands and Automation

- `~` Both have large `scripts/` directories (VoiceStudio 60+, Nexus-AI 40+).
- `+` `scripts/crash_class_report.py` measures recurrence of the project's #1 lifetime failure class ("the backend died or never came up", roughly 1 in 5 of all issues ever filed), **filtered to reports from a given version**, because 6 in 10 sampled reports historically came from already-obsolete builds. Nexus-AI has no equivalent field-failure metric.
- `=` Nexus-AI's `npm run security:gen` / `security:check` generator-plus-drift-gate around `nexus.security.toml` has no VoiceStudio counterpart.

### 7. CI/CD and Hooks

- `=` Nexus-AI runs 19 workflows including CodeQL, OpenSSF Scorecard, commitlint, coverage-diff, semantic-release, golden-tasks, and four installer workflows.
- `+` `.github/workflows/docs-drift.yml`: a daily job diffs `features.yaml` against README, docs, and the engine registries and maintains **one rolling issue** labelled `docs-drift`, updating it in place and closing it automatically when clean. No issue spam.
- `~` **Installer smoke triggers.** VoiceStudio's `install-smoke.yml` fires on a `paths` filter over `scripts/install.sh` / `install.ps1` -- it runs exactly when an installer changes. Nexus-AI's `installer-smoke.yml` is `workflow_dispatch` plus a **monthly** cron, so an installer edit can merge with no smoke run for up to 30 days. VoiceStudio's approach covers the case that matters (a changed installer) instead of a calendar. It does **not** cost less: the Nexus job runs four jobs at a 30-minute timeout across Windows, macOS, and Linux, and its header records that the monthly throttle exists specifically to consume no minutes under an Actions budget freeze. Adopting a path trigger is a coverage improvement bought with CI minutes, and the minute delta has to be stated before it is adopted, not assumed away.
- `+` No dedicated **secret-scanning gate**. VoiceStudio runs `gitleaks` as a hard-fail merge blocker (full-history on push to `main`, PR-diff on pull requests). Nexus-AI has no `gitleaks` / `trufflehog` / `detect-secrets` anywhere in `.github/workflows/` or `.husky/`.
- `+` **CodeQL language coverage.** Nexus-AI's `codeql.yml` sets `language: ["javascript-typescript"]` only (line 38), against 304 tracked Python files that include the entire PyQt installer and the three model runtimes. It also triggers only on `main`, and its job name is the literal string `Analyze (javascript-typescript)` rather than a template over the matrix, so adding a language yields two identically named checks. VoiceStudio runs CodeQL over Python **and** JS/TS, plus `bandit` (SARIF, non-gating).
- `+` **`pip-audit` scope.** Nexus-AI does run `pip-audit --strict`, but only over `scripts/installer` (`ci.yml:509-539`, job name literally `pip-audit (installer venv)`). The three sets that actually reach user machines -- `runtimes/audio/requirements.txt`, `runtimes/diffusion/requirements.txt`, `runtimes/ocr/requirements.txt` -- are unaudited.
- `.` Both keep LLM-judge evals **non-gating and scheduled**: VoiceStudio's `evals.yml` (weekly, `continue-on-error`) and Nexus-AI's `golden-tasks.yml` (weekly Sunday cron plus dispatch) reached the same conclusion independently. No action.

### 8. Documentation

- `=` Nexus-AI's per-version release trees, `known-gaps.md`, and prior comparison reports are stronger.
- `+` `docs/engine-acceptance.md` defines a **job map**: every engine in the tree owns at least one named job, a job has exactly one holder, and a proposal must either take a job from its incumbent with numbers or claim an uncovered job. "It benchmarks well is not a job." Nexus-AI's recent history is a sequence of model adoptions -- Unsloth, Qwen3-8B, Gaussian Splatting (v2.4.0), Qwen/Video2X/OpenWorker (v2.3.0), Sana (v2.4.4), diffusionstudio (v2.5.0 planned) -- with no written bar any of them had to clear.
- `+` `docs/competitive-analysis.md` and `docs/ROADMAP.md` are living, spec-numbered documents that CI comments reference by name (for example "Spec 9a / parity program Wave 0.1"), so a workflow explains itself by pointing at the decision that created it.

### 9. Testing Strategy

- `~` Both are heavily tested. VoiceStudio: 498 Python test files, 35 TS test files, Playwright, and a `smoke-test.sh` with `--skip-build` / `--keep-data` / `--keep-models` variants.
- `=` Nexus-AI has coverage-diff gating and golden-task evals.
- `+` VoiceStudio's smoke-test **upgrade** mode (`smoke-test:upgrade` = `--keep-data --skip-build`) explicitly exercises the install-over-existing-data path. Nexus-AI has a `desktop-prod:upgrade` equivalent in scripts, but it is not wired into any workflow.

### 10. Security Posture

- `=` Nexus-AI: `nexus.security.toml` SSOT plus generator plus drift gate, Scorecard, SHA-pinned actions, `npm audit --omit=dev`, `SECURITY.md`.
- `+` VoiceStudio: gitleaks hard-fail gate with a `.gitleaks.toml` config, CodeQL over both languages, bandit SARIF, and a test asserting that the one committed analytics token may appear in exactly two files (`tests/test_no_committed_analytics_token.py`) -- an allowlist enforced as a test rather than as a convention.
- `+` **Database snapshot before migration.** On first launch of an updated build, VoiceStudio writes a consistent snapshot next to the database before any migration runs, keeps the newest 3, prunes older ones, skips the snapshot above 500 MB with a log line, and **refuses to start on a half-migrated database** rather than guessing. Nexus-AI has `core/memory/migrations/` and `core/storage/migrations/` with migration code in `core/generations/GenerationDatabase.ts`, `src/storage/ChatHistoryStore.ts`, and `src/storage/MemoryStore.ts`; a grep for `backup` across those files returns nothing.

### 11. Developer Experience

- `~` Both have rich dev scripts. VoiceStudio's `predesktop` preflight plus `clear-dev-ports.mjs` is close to Nexus-AI's `dev-setup.sh` / `init.sh`.
- `+` **No issue templates in Nexus-AI.** `.github/ISSUE_TEMPLATE/` does not exist. VoiceStudio stamps a `**Build status:**` line into every bug-report body (`OUTDATED` / `current at filing time` / absent) via opt-in prefilled-URL reporting, which is exactly what makes its crash-class report trustworthy.
- `+` **No auto-updater in Nexus-AI.** `desktop/src-tauri/tauri.conf.json` has no `updater` key and no endpoints. VoiceStudio ships a signed updater with Stable and Preview channels, both minisign-signed against the same key, with no accounts and no extra network calls.

## Section 8: Risks and Conflicts

**R1 -- License conflict (critical).** VoiceStudio is **AGPL-3.0-only**; Nexus-AI is **MIT**. Copying VoiceStudio source into Nexus-AI would impose AGPL obligations on a codebase that does not carry them. Every item in Section 7 must be implemented **clean-room from the described behavior**, not by copying files, functions, or workflow YAML from the clone. The scratchpad clone must be deleted after this comparison. Items A1, A2, A5, and A6 are behavioral patterns and carry no copyright concern; A3, A4, A7, and A8 must be written fresh against Nexus-AI's own tree.

**R2 -- A5 modifies existing storage code.** Pre-migration snapshotting touches three storage modules on the hot path for every session, which is higher risk than the additive items. It requires a fail-before/pass-after regression test proving that a corrupted or half-applied migration leaves the original database intact and the app refusing to start.

**R3 -- A3 conflicts with the current `feature_list.json`.** The existing file is stamped v0.8.0 and describes a surface (4-layer memory, 6-stage compaction) from a much earlier architecture. Reviving it means rewriting nearly all of it. Treat it as replacement, not repair, and decide deliberately whether the `verificationCommand` field survives -- a checker that shells out to test commands is far slower than one that only checks paths and strings.

**R4 -- A9 will surface findings.** Turning CodeQL on for 304 previously unscanned Python files, and auditing three ML requirement sets that pull `torch` and its transitive tree, will produce a first-run backlog. Land it non-gating for one cycle, triage, then gate. Do not let a red first run become a reason to revert the coverage.

Two mechanical obstacles sit in front of this and were missed on the first pass. `codeql.yml` triggers only on `main`, so a branch that publishes to `develop` never produces the finding count the adoption decision needs; the trigger branches have to change, or the counts have to be gathered locally with the CodeQL CLI. And the runtime `pip-audit` extension is a **sibling job**, not a matrix dimension on the existing one: the current job is built around `uv export` against `scripts/installer/uv.lock`, and the three runtime sets are plain unlocked `requirements.txt` files with no lockfile, so neither the cache key nor the export step transfers.

**R5 -- A8 full-history scan.** A first full-history gitleaks run on an established repo commonly flags historical test fixtures and false positives. Budget triage time and build the `.gitleaks.toml` allowlist before making the job blocking.

**R6 -- A10 reduces cadence coverage.** Moving from a monthly cron to a `paths` trigger means an installer that breaks because of a change *outside* the installer files gets no smoke run. Mitigate by widening the paths filter to include the installer's Python sources and the Tauri bundle config, not just the two entrypoint scripts.

## Section 8.5: Post-Review Corrections

Four claims in the first draft of this report were wrong and were corrected on 2026-09-09 after the plan-review lenses checked them against the tree. They are recorded rather than silently overwritten, because the adoption plan was drafted against the originals.

| Claim as first written | Correction | How it was caught |
