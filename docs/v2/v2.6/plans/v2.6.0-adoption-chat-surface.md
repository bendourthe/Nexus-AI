# Plan -- Chat Surface Adoption

**Project**: Nexus-AI
**Version**: v2.6.0
**Adoption target**: v2.6.0
**Slug**: adoption-chat-surface
**Plan Type**: Feature / Adoption
**Created**: 2026-09-15
**Seeded from**: [`v2.5.1-comparison-librechat.md`](../../v2.5/comparisons/v2.5.1-comparison-librechat.md) (items LC-1, LC-3, LC-4, LC-5, LC-6)
**Companion plan**: [`v2.5.1-adoption-packaged-verification-and-accessibility.md`](../../v2.5/plans/v2.5.1-adoption-packaged-verification-and-accessibility.md), which must be merged first.
**Goal**: Close the four verified Chat-pillar gaps -- conversation forking, Mermaid artifact rendering with versioning and export, a context-pressure readout, and user-initiated compaction -- without widening the artifact sanitisation boundary or putting existing chat history at risk.

## Overview

This is the **Chat half** of a split. The seeding comparison found four gaps in the Chatbot pillar, each verified against the tree rather than assumed: no conversation forking anywhere under `desktop/src/shared/chat` or `desktop/src/modules`; an artifact host (`desktop/src/components/InteractiveArtifact.tsx`, 264 lines) that by its own header supports only a `<form data-nexus-artifact="true">` payload, with no Mermaid rendering anywhere in `desktop/src` or `core/`; and context compaction that is automatic-only, with no user-initiated path.

It carries a `feat:` commit profile, which is why it is v2.6.0 rather than a patch on the verification plan: `semantic-release` derives the published version from commit types, so feature work in a patch-named plan publishes a minor anyway.

Two things make this plan harder than its feature list suggests, and both were found by review rather than by drafting. The artifact work touches a documented security boundary whose current configuration is **incompatible** with what Mermaid emits, so the cheap path is guard erosion. And the forking work changes a storage schema that currently has **no migration mechanism at all**, on a store holding the user's entire chat history.

## Strategy alignment

Per [`STRATEGY.md`](../../../../STRATEGY.md):

- **Target Problem served**: the Chatbot Explorer is the daily-use surface and the entry point to the other pillars; its gaps are affordances the primary persona hits repeatedly.
- **Persona served**: the **solo builder** (primary persona). Every phase here changes something they see, which is the opposite of the companion v2.5.1 plan.
- **Key Metrics moved**: **M5** primarily (a shipped capability is used by the maintainer in real work within two release cycles, or is removed). M3 is protected rather than moved -- Phase 3 and Phase 4 both add assertions defending the zero-outbound guarantee against a new dependency and a new export path.
- **Open dependency**: STRATEGY.md section 4 ranks the Chat pillar **second of four**, and that ranking is marked PROPOSED and unconfirmed. Sub-task 1.1 resolves it. If Chat ranks lower, forking in particular should be dropped rather than sequenced: it is a prompt-exploration affordance whose demand in a multi-tenant hosted chat product does not automatically transfer to a single-user local studio.

## Blocking decisions

### D1 -- Does the Chat pillar rank high enough to justify this plan? **UNRESOLVED -- gates every phase.** Owned by sub-task 1.1.

The seeding comparison establishes that LibreChat has these features and Nexus-AI does not. It does not establish that the Nexus user wants them. This is the review finding that produced STRATEGY.md, and it must be answered before code is written rather than after.

### D2 -- Fork data model: session-per-branch, or in-session message tree? **UNRESOLVED -- gates Phase 2.** Owned by sub-task 2.1.

The two models have opposite consequences. A branch as a new session row carrying `forked_from_message_id` + `forked_from_session_id` reuses every existing session-keyed reader. An in-session message tree makes `messages` a tree and changes every reader that currently orders by timestamp. An earlier draft implied both at once.

### D3 -- Export privilege: reuse the existing download path, or add a scoped save capability? **RESOLVED 2026-09-15: add a scoped save capability.**

The owner chose full versioning plus SVG and PNG export, which requires a write path. The decision is recorded here with its constraint because the naive implementation is dangerous: `desktop/src-tauri/capabilities/default.json` currently grants only `dialog:allow-open`, and `desktop/src-tauri/Cargo.toml` carries `tauri-plugin-dialog` with **no** `tauri-plugin-fs`, so the renderer has no write capability at all today. The path of least resistance is adding `tauri-plugin-fs` with a broad `fs:allow-write-file` and a `$HOME/**` scope, which permanently widens the shell far beyond diagram export. Phase 4 adds `dialog:allow-save` plus a single narrow Rust command that writes only to a path returned by that same save dialog within the same invocation, accepting no renderer-supplied path, and adds no general `fs` write scope.

## Phase 2: Conversation forking

**Goal**: Let a user branch a thread from any message, with both branches persisted, navigable, and no risk to existing history.
**Prerequisites**: Phase 1, **and `v2.5.0-migration-durability` merged and green on `develop`**.
**Stability Gate**: A thread branches from any message; both branches and the active branch survive a restart; a pre-plan database opens and reads correctly; a newer-schema database is refused; two concurrent instances cannot both apply the migration.
**Verification Expectation**: Open a chat with at least four turns, branch from the second message, send a different message on the branch, restart the app, and observe both branches present with divergent content, the branch point intact, and the previously active branch still active. Then open a database copied from before this plan and observe it read correctly, and open one whose `user_version` is higher than the binary's and observe a refusal message rather than a silent downgrade. Delegate the procedure to [[functional-verification]].
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: A schema change on the storage hot path, over the user's entire chat history, in a store that currently has no migration mechanism.

### Sub-tasks

#### 2.1 -- decision: fork data model

**Objective**: Settle D2 before any schema is written, because the two models change different sets of readers.

**Prompt**:
> Resolve blocking decision D2 by reading `src/storage/ChatHistoryStore.ts` first. Choose either (a) **branch = new session row** carrying `forked_from_message_id` and `forked_from_session_id`, which reuses every existing session-keyed reader and the existing folder organizer, or (b) **branch = in-session message tree**, in which case enumerate every reader that currently orders by timestamp and must instead resolve a root-to-leaf path.
> Whichever is chosen, the design must include a **persisted active-leaf pointer**. A parent-message relation alone cannot express which branch is currently being viewed, so that state would live only in React state and be lost on restart, contradicting this phase's own Verification Expectation. Name where the pointer is stored.
> Also specify: a maximum branch depth as a number, a cycle check on write (a parent pointing at its own descendant must be rejected), iterative rather than recursive traversal, and the `ON DELETE` behaviour for the parent relation. **Do not use `ON DELETE CASCADE`**: `messages` already cascades from `sessions`, and a self-referencing cascade means deleting one message silently removes every descendant branch. Choose restrict or re-parent and say which.
> **Recommended: (a)**, because it changes the fewest readers and the organizer is already session-scoped. Record the decision in `docs/v2/v2.6/development/v2.6.0-phase2-evidence.md`.

#### 2.2 -- Apply the schema change on the migration-durability ladder

**Objective**: Add the branch relation without putting a single existing thread at risk.

**Failure modes**: A database written before this plan opens and reads as an unbranched thread rather than failing, because unreadable history is a data-loss event from the user's perspective. A database written by a **newer** build is refused with a "written by a newer version" message rather than being stamped down -- today `currentVersion !== SCHEMA_VERSION` treats newer exactly like older, rebuilds FTS and writes the version back down, which corrupts history on any rollback. An interrupted migration leaves the original intact and the app refuses to start, detected by a pending-version marker written before the change and cleared after, inside an explicit transaction. Two concurrent instances cannot both apply it: the store opens in WAL mode with no single-instance lock, so a second launch races `_initSchema` and one side gets `SQLITE_BUSY` or a duplicate-column error.

**Build class**: load-bearing.

**Prompt**:
> Implement the decided model in `src/storage/ChatHistoryStore.ts`. **Do not build a migration ladder here**: `v2.5.0-migration-durability` owns that, and this phase is hard-gated on it being merged and green. Confirm the observable precondition first (the snapshot helper exists at its named path and is covered by a test) and record it; if it is absent, stop and report rather than building a second mechanism.
> Note what the store looks like today so the gap is explicit: `_initSchema` runs `CREATE TABLE IF NOT EXISTS` unconditionally, and `PRAGMA user_version` only gates an FTS rebuild and is set AFTER that rebuild. There is no transactional apply and no half-migrated state to detect.
> Take an **unconditional pre-migration copy** owned by this sub-task, using the v2.5.0 snapshot mechanism, plus a **verified-restore test**: restore the copy, reopen, and read the original threads.
> Add the **downgrade guard**: if the database's version is greater than the binary's `SCHEMA_VERSION`, refuse to open and surface a clear message.
> Serialise the migration with `BEGIN IMMEDIATE` or an OS-level single-instance lock, and write the pending-version marker before and clear it after.

## Phase 3: Mermaid rendering behind a shared, hardened sanitiser

**Goal**: Render Mermaid diagrams from untrusted model output with the artifact security boundary provably unchanged.
**Prerequisites**: Phase 2.
**Stability Gate**: A Mermaid fence renders with readable labels; `FORBID_TAGS` in the shared sanitiser is byte-identical before and after this phase; a named corpus of SVG and MathML vectors is stripped; a `click ... href` directive produces no anchor and no navigation.
**Verification Expectation**: Send a message containing a Mermaid fence and observe the diagram render with readable labels. Then send the attack corpus (a `<script>`, an `<iframe>`, a `<foreignObject>`, an `<animate attributeName="href">`, a `<set attributeName="xlink:href">`, a `<use href>`, an SVG event attribute, and a `click A href "https://example.invalid"` directive) and observe every one neutralised with no navigation. Delegate the procedure to [[functional-verification]]. The negative case is the important half: a renderer that draws diagrams and also executes content is a regression, not a feature.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Untrusted model output crossing a documented security boundary whose current configuration is incompatible with the thing being rendered.

### Sub-tasks

#### 3.1 -- Extract the sanitiser into one shared module

**Objective**: Make the security boundary a single importable thing before a second consumer exists.

**Failure modes**: If extraction changes behaviour, the guard tests fail rather than the change passing review. If a caller imports DOMPurify directly instead of the shared module, a lint rule flags it.

**Build class**: load-bearing.

**Prompt**:
> The sanitiser is currently a private function inside `desktop/src/components/InteractiveArtifact.tsx`, calling `DOMPurify.sanitize(html, { FORBID_TAGS: ["style","iframe","object","embed","link","meta","base"] })`. Phase 3 adds a second consumer in a different directory. Extract the DOMPurify call and its configuration into one exported module and have both the artifact host and the chat message surface import it. Do not let a second `FORBID_TAGS` list come into existence: that is a second source of truth for a security boundary, which is known gap NI-3's defect class on much higher-stakes ground. Add a lint rule or a test forbidding direct `DOMPurify` imports outside the shared module. The guard tests in 3.3 assert against the shared module, not per call site.

#### 3.2 -- Render Mermaid with a locked-down configuration and an SVG profile

**Objective**: Render diagrams without touching the HTML profile's `FORBID_TAGS` list.

**Failure modes**: Invalid syntax renders as inline text, never a thrown error that blanks the message. When the library is unavailable or slow to initialise, the fence renders as a code block rather than hanging. A payload containing both a valid fence and an attack vector renders the diagram and neutralises the vector; neither outcome suppresses the other. Input over the size or complexity cap renders as a code block with a "render diagram" control rather than being parsed.

**Build class**: load-bearing.

**Prompt**:
> Add Mermaid rendering to the chat message surface as a **composed child component**, not inline in `MessageBubble.tsx`.
> Two constraints that an earlier draft got factually wrong and that must not be rediscovered during implementation. First, the existing `FORBID_TAGS` list **already forbids `style`**, and Mermaid emits its theme CSS as an SVG-embedded `<style>` element. Do NOT remove `style` from that list. Initialise Mermaid with `htmlLabels: false` and deliver diagram styling from an application-owned stylesheet scoped to the diagram container. Second, route Mermaid output through a **separate SVG-profile sanitise** (`USE_PROFILES: { svg: true, svgFilters: true }`) with `foreignObject`, `use`, `animate`, `set`, `script` and handler attributes explicitly forbidden; the HTML profile's defaults permit the SVG namespace, which is exactly the surface newly being rendered.
> Initialise Mermaid with `securityLevel: 'strict'` and **disable the `click` directive entirely**, then post-strip `<a>`, `href` and `xlink:href` from the rendered SVG. Mermaid supports `click <node> href "<url>"`, and the shell's CSP (`desktop/src-tauri/tauri.conf.json`) sets `default-src 'self'` and `connect-src 'self' ipc:` but declares no `frame-src`, `form-action` or navigation restriction, so a top-level navigation driven by model output is not otherwise blocked.
> Add **render-cost caps as explicit numbers**: a maximum fence byte length and a maximum node and edge count, both checked before parse, plus a render timeout after which the fence falls back to a code block. Mermaid layout is synchronous on the main thread and superlinear in edge count, so a few hundred KB of valid graph text hangs the whole window with no cancel path. Render off the main thread or behind an explicit control for payloads over the cap.
> Bundle Mermaid locally; no CDN fetch, and no icon-pack registry that resolves remotely on demand.
> Make "the diagram renders with readable labels" a stated acceptance criterion, so a silently degraded render does not pass.

## Phase 5: Context pressure and reversible compaction

**Goal**: Show the user where the context window is going, and let them relieve it without losing anything they cannot get back.
**Prerequisites**: Phase 4.
**Stability Gate**: The readout satisfies `sum(known) + unaccounted = total` with `unaccounted` visible whenever any input is unknown; a user-initiated compaction reduces the total, preserves recent turns byte-identically, is rejected while an automatic pre-compact or a streaming turn is in flight, and is reversible.
**Verification Expectation**: Open a long thread, observe the breakdown and confirm the displayed parts plus `unaccounted` equal the stated total. Trigger a compaction, observe the total drop with the most recent turns byte-identical, then undo it and observe the original thread restored. Then attempt a compaction during a streaming turn and observe it declined with a stated reason. Delegate the procedure to [[functional-verification]].
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Mostly presentation over counts the product already computes, but the mutual-exclusion and reversibility requirements touch a lifecycle path whose current contract does not support them.

**Objective**: Find the service that actually summarises and commits, because an earlier draft named a module that cannot do it.
