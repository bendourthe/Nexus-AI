## Overview

The seeding comparison answered a direct product question: can Nexus AI Studio support the DavidAU Qwen3.8-27B uncensored GGUF? No, and the blockers are upstream of Nexus. Serving is Ollama-only at `http://127.0.0.1:11434` with no llama.cpp path, so the model's vision needs a separate `mmproj` projector Ollama does not support, and its MTP head is driven by llama.cpp flags Ollama does not expose.

That verdict is correct but currently unfindable. It is spread across three documents that use one name for three different models: the v2.3.0 record covers Flash-Next (125B total, 6B active), the v2.4.0 comparison noted in passing that the 27B dense model needs its own treatment, and the v2.6.0 comparison supplies it. The request that triggered this work described a 27B dense model as an "8B vision model", which is the failure the v2.4.0 report recorded as trapdoor 7, recurring within weeks of being written down.

This plan lands the verdict where it will stay current, and makes it enforceable.

**Placement.** [`docs/reference/model-acceptance.md`](../../../reference/model-acceptance.md) is a living reference, introduced in v2.4.9, that already owns model-admission policy and is already enforced by `tests/unit/docs/v2.4.9-model-acceptance.test.ts` and the catalog invariant tests. It frames the catalog as a **job map**: an entry is accepted only if it takes a named job from its current holder with measured numbers from this project's own hardware, or claims a job nobody holds. "It benchmarks well" is explicitly not a job. That frame is sharper than a six-gate restatement, because it names the actual question: Qwen3.8-27B would contest the **24 GB coding-specialist fallback** job currently held by `qwen3-coder:30b`. The Qwen3.8 verdict therefore extends that document rather than starting a competing one. A first draft of this plan created a release-scoped admission record instead, which would have reproduced the exact drift this plan exists to cure.

**Enforcement.** A prose warning has now failed twice, so the family gets a catalog invariant. The pattern is deliberately narrow, and the reason is instructive: `Qwen3-8B` is a real model with an official Ollama tag (`qwen3:8b`). A naive family pattern covering the `qwen38` spelling also matches `qwen3:8b`, so a guard built to stop one confusion would mechanically commit it. The verified pattern carries a negative lookahead for a bare size suffix and was tested against all 375 catalog string fields with zero false positives.

**Scope disclosure.** The comparison's Q27-4 reads "Record the 'Qwen3.8 is not 8B' naming trap in the admission record", with no invariants branch; its Section 7 P0 targets the identity section alone. The catalog invariant in Phase 2 is therefore a deliberate extension beyond the comparison's adoption table, approved on the grounds that two recurrences within weeks is evidence prose is insufficient. **Phase 2 in its entirety (T005 through T007) is the cut line**: stopping after Phase 1 ships the comparison's full adoption table with nothing half-built.

Nothing here adds a catalog row, a model download, a runtime, a dependency, an outbound call, or a credential. Both the DavidAU artifact and a llama.cpp serving path were classified `drop-outright` for this release in the comparison's Section 6.3.

No phase except the last pushes, opens a pull request, or starts remote CI. Each earlier phase ends with automated tests, session history, and one local commit. Package metadata stays at its current value until `/update release`.

## Architecture Decisions

**AD-1: The verdict extends the living acceptance bar; the release tree holds only evidence.** `docs/reference/model-acceptance.md` is marked "living reference", is already the declared home for "every proposal to add a model, a model variant, or a Python runtime", and already has mechanical enforcement. An admitted-ids list, a reopening trigger, and a watchlist status are all things designed to change after v2.6 closes, so by the project's lifespan placement rule they belong in a living root. The v2.6 tree gets an evidence file recording what this cycle observed, which is exactly the kind of document that stops changing.

**AD-2: The reopening trigger has two paths, not one conjunction.** A first draft required both an official Ollama tag and a unified multimodal build. That is wrong: Qwen3.8-27B is a dense text model whose vision is an add-on, and a text-only official tag would be admissible on precisely the terms `qwen3-coder:30b` already holds its 24 GB job. Requiring vision would permanently block a legitimate path. Path (i) reopens for text-only use; path (ii) additionally reopens vision. Both are phrased as observables ("the library tag lists vision among its capabilities") rather than inferences about `mmproj`, because the library page is what a future session can actually read.

**AD-3: A Qwen3.8-specific guard now, with NI-2 explicitly not paid down.** The guard is a deny-by-default family match with an empty allowlist. Two honest qualifications. First, the precedent is partial: `KNOWN_BROKEN_OLLAMA_REFS` is a substring list and `PLACEHOLDER_SHA_LEGACY_EXEMPT` is an *exemption* list that narrows an existing rule and shrinks toward empty, whereas `QWEN38_ADMITTED_IDS` is an *admission* list that widens a new rule and grows. The module-level-named-list shape is the precedent; the polarity is inverted, and a reader should not carry the wrong mental model across. Second, this adds a sixth family-shaped block and moves NI-2's exit condition further away. Converting the five existing `_check_*_entry` functions into a declarative table is the better end state and was considered, but it is a refactor of shipping validation with its own risk profile, unrelated to recording one model verdict. NI-2 is re-recorded in Phase 3 with this plan named as having widened it.

**AD-4: The guard lives only in the installer validation module, and that is sufficient.** `core/registry/catalog.json` is a single shared artifact: the installer validates it, `core/registry/modelAliases.ts` imports it, and `desktop/sidecar/esbuild.config.mjs` bundles it. `.github/workflows/installer-tests.yml` path-filters on that file for both push and pull_request, so any catalog edit runs the Python guard and the desktop consumption path is covered transitively. There is no unguarded second path. Note the blast radius is wider than tests alone: `validate_catalog` is also called by `scripts/installer/build/check-catalog.py` and by `scripts/installer/build/nexus-installer.spec`, which raises `SystemExit` on any problem, so the invariant becomes a hard gate inside the Windows, Linux, and macOS installer builds and `release.yml`. This plan changes no catalog row, so those stay green, but Phase 3 reconciles all three consumers rather than the pytest path alone.

**AD-5: The code frozenset is authoritative; the document mirrors it.** Two hand-synced lists with no mechanical link would reintroduce the drift this plan exists to fix. `QWEN38_ADMITTED_IDS` is the single source of truth. A test asserts every id in it appears verbatim in `docs/reference/model-acceptance.md`, so the mirror cannot silently diverge.

## Phase 2: Narrowed Fail-Closed Catalog Guard

**Goal**: A verified deny-by-default pattern catches the Qwen3.8 family across ids and source urls regardless of protocol, spares the unrelated real Qwen3-8B, and names the living reference in its failure message.
**Prerequisites**: Phase 1 (the failure message cites the section T002 creates).
**Stability Gate**: `validate_catalog` returns a problem for a synthetic Qwen3.8 entry not on the allowlist, returns none for the shipped catalog, and returns none for synthetic `qwen3:8b` and `Qwen/Qwen3-8B` entries. Adding a Qwen3.8 row without an allowlist entry fails CI and the installer build gate.
**Verification Expectation**: Run `python -m pytest scripts/installer/tests/test_catalog_invariants.py -q` and observe the suite green, with the new tests passing (a passing test asserts the guard *rejects* the synthetic catalog; the suite itself must not be red). Then run `python scripts/installer/build/check-catalog.py` against the unmodified shipped catalog and observe exit zero. Exercise via [[functional-verification]].
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Low architectural risk but high correctness sensitivity: the pattern must thread between two model families whose names differ by one separator, and the invariant becomes a hard gate in three installer builds and `release.yml`.

#### 2.1 -- Add the narrowed Qwen3.8 family invariant

**Objective**: Make the living reference load-bearing by failing CI on any unadmitted Qwen3.8 catalog row.

**Build class**: load-bearing.

**Prompt**:
