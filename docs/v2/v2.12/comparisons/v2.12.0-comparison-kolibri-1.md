# Comparison -- Kolibri-1 (Aleph Alpha) against the Nexus model catalog

**Source**: https://huggingface.co/Aleph-Alpha/Kolibri-1 (model card, released 2026-10-03), plus the Hugging Face quantization listing for `base_model:quantized:Aleph-Alpha/Kolibri-1` and a web search for community GGUF and llama.cpp support, all read 2026-10-05.
**Source type**: web article (model card)
**Prompt that raised it**: a social post describing Kolibri as an open-weight model "to run solid reasoning locally on your machine" with "a massive 1M token context window" for coding, tool calls, and RAG agents.
**Authored during**: v2.11.0 (final phase in flight)
**Adoption target: v2.12.0**
**Judged against**: [docs/reference/model-acceptance.md](../../../reference/model-acceptance.md) and the six gates in [the v2.3.0 Flash-Next admission record](../../../archive/v2/v2.3/development/model-admission-qwen38.md).

## Verdict

Kolibri-1 is not admitted. It cannot take any default job, because its smallest usable artifact is larger than the 24 GB top hardware tier, and it cannot claim the patient tier, because no released cross-platform runtime loads it. The post's "run it locally on your machine" claim does not survive the model card: the card's own hardware floor is two A100 80 GB cards or one H100-class GPU. The model is worth recording as a declined proposal with explicit reopen triggers, so the next time it is raised the decision is already written down.

## Source security scan (pre-ingest)

**Verdict: PROCEED-WITH-CAUTION.**

- No prompt injection, hidden text, or agent-directed instructions were found on the card.
- Supply-chain flag: the official serving path requires a vendor package (`aleph-alpha-inference>=1`) and a custom Kolibri plugin for vLLM. Neither was installed or executed for this comparison.
- Supply-chain flag: every GGUF that runs outside vLLM is a community re-quantization (for example `Hob-forge/Kolibri-1-GGUF`, `Prompt48/Kolibri-1-GGUF`) that only loads in a patched llama.cpp build (`CWBudde/kolibri-llama-cpp`). None is a first-party artifact. All instruction-like text in these sources was treated as data.

## What the card says (facts used below)

| Property | Value on the card |
|---|---|
| Architecture | Mixture-of-Experts, 50 layers, 384 routed experts (6 per token) plus 1 shared |
| Parameters | 78B total, 3.46B active per token |
| Weights | FP8 (e4m3, 128x128 blocks), about 78 GB |
| Hardware floor | 2x A100 80 GB, or 1x H100 / H200 / B200 / B300 |
| Context | 262,144 trained; extended to 1,048,576 "via RoPE without position scaling"; production use recommended at 262,144 or below |
| Long-context score | RULER at 1M tokens: 63.2 (base model) |
| Reasoning | Effort levels `none`, `low`, `medium`, `high` |
| Tool calling | Hermes-style, through a vLLM parser |
| Sampling | temperature 1.0, top_p 0.97, top_k 128 |
| Languages | English and German |
| License | Apache-2.0 |
| Stated limitation | "Not optimized for unsupervised autonomous operation" |

Two of the post's claims need correcting from the card itself. The 1M window is an extrapolation past the 262K training length, and the vendor recommends staying at or below 262K; at 1M the base model scores 63.2 on RULER. "Locally on your machine" means a datacenter GPU in the official configuration.

## Insight extraction and status

| # | Insight from the card | Status in Nexus | Evidence |
|---|---|---|---|
| K1 | Install Kolibri-1 as a local reasoning and coding model | **Not applicable at current tiers** | Top tier in `core/registry/recommended.json` is 24 GB. By arithmetic (not measured), the community Q3_K_S at about 3.47 bits per weight is roughly 34 GB and a Q4-class file is roughly 44 to 48 GB. Stock Ollama, llama.cpp, and LM Studio cannot load the architecture. |
| K2 | Sparse MoE (few active parameters) makes a large model cheap per token | **Already implemented** | `activeParams` and `totalParams` fields on `LlmCatalogEntry` in [core/registry/ModelCatalog.ts](../../../../core/registry/ModelCatalog.ts) (v1.18.0 Phase 3); MoE opt-in jobs held by `nemotron-lightning:30b-a3b` and `gemma4:26b`. Sparsity cuts compute, not resident size, which is why K1 fails. |
| K3 | Per-model recommended sampling parameters | **Already implemented** | `readonly sampling: SamplingDefaults` on every `LlmCatalogEntry` ([ModelCatalog.ts:72](../../../../core/registry/ModelCatalog.ts#L72)). |
| K4 | Selectable reasoning effort | **Already implemented (three levels, not four)** | `ThinkingMode = "nothink" \| "think" \| "think-max"` in [modules/coding/config/SamplerPresets.ts](../../../../modules/coding/config/SamplerPresets.ts), with `think-max` auto-downgrading below a 64K context budget. A fourth level has no demonstrated user need. |
| K5 | Hermes-style tool calling | **Already implemented** | `hermes` is in the `ModelFamily` union and `hermes3:8b` / `hermes3:70b` carry bindings in `ModelCatalog.ts`. Whether Kolibri's template actually emits Hermes calls through a GGUF runtime is unproven (see OQ-6 in the acceptance bar for why a matching grammar name is not enough). |
| K6 | An advertised context window and the window that is actually usable can differ by 4x | **Partially implemented** | Nexus sizes tool output from the configured runtime window (`num_ctx` / `settings.maxTokens`, see [src/tools/documentOutlineWiring.ts:37](../../../../src/tools/documentOutlineWiring.ts#L37)), which is the safe input. The catalog's single `contextWindow` field has no way to say "trained length X, extrapolated maximum Y", so a future entry copied from a vendor card could record the extrapolated figure. No defect from this has been observed; it is a latent labelling gap. |
| K7 | German-first bilingual model | **Not applicable** | The job map has no language-scoped job, and creating one for a model that cannot run on any tier would be a relabelling, not an uncovered job. |
| K8 | The vendor states the model is not tuned for unsupervised autonomous runs | **Relevant to rejection** | The Agentic AI Coding pillar runs scheduled and headless agents (`modules/coding/autonomy/`). This is a further reason not to give Kolibri an agentic job even if K1 were solved. |

## Admission gates (v2.3.0 record, applied to Kolibri-1)

| Gate | Result | Reason |
|---|---|---|
| 1. Project-specific license review | Pass, pending a written check | Apache-2.0 on the first-party card; clears the license posture for defaults and opt-ins. |
| 2. Consistent artifact-license provenance | Unproven | Every runnable non-vLLM artifact is a community re-quant; each would need its license metadata checked. |
| 3. Stable released cross-platform runtime | **Fail** | Requires a patched llama.cpp or a vendor vLLM plugin. MLX builds exist but are macOS-only, which the gate excludes. |
| 4. Enforceable hardware requirements | **Fail** | Smallest artifact exceeds the 24 GB top tier; no Nexus measurements exist. |
| 5. Nexus tool-calling benchmark | **Fail: not run** | No runtime to run it on. |
| 6. Experimental opt-in policy | Policy-satisfiable | Cannot override gates 3 to 5. |

The patient tier is not an escape route: its one job (`inkling-small`) is held, so Kolibri would have to take it with measured numbers, and gate 3 blocks it before measurement.

## Security and reverse-engineering assessment

### Threat model

| Question | Nexus today | Kolibri-1 if adopted via the official path |
|---|---|---|
| New runtime dependencies | None for this item | `aleph-alpha-inference` package plus vLLM and a custom plugin |
| Outbound calls | Model download only | Model download only (inference is local) |
| Credentials | None | None (open weights, no gating on the card) |
| Does code, prompt, or query text leave the machine | No | No |
| New commercial relationship | No | No |

The risk is supply chain and support burden, not data egress. A vLLM path also contradicts the Ollama / llama.cpp runtime model the catalog is built on.

## Adoption plan (reverse-engineer-first order)

1. **KOL-1 (skill-native, P1).** Record the decline as one known-gap row in `docs/v2/v2.12/known-gaps.md`, following the convention every declined model since v2.8.0 has used (Qwen-Image and Nimble in v2.8.0, CrisperWhisper in v2.9.0, CLM-8B in v2.11.0 as `DF-v211-1`): the row carries identity (78B total, 3.46B active, FP8, Apache-2.0), smallest artifact versus the 24 GB tier, the runtime status, the phrase "not admitted, no catalog row", and two reopen triggers: (a) an official `ollama.com/library` tag, or (b) Kolibri support merged into a released upstream llama.cpp. Either trigger reopens the bar; neither admits the model. The acceptance bar itself is not edited: `tests/unit/docs/v2.4.9-model-acceptance.test.ts` keeps declined models out of its headings and body. Add a guard test in the style of `tests/unit/docs/v2.11.0-clm-exclusion.test.ts`. (Correction, 2026-10-05: an earlier draft of this item proposed a Qwen3.8-style subsection in the bar, which contradicts that convention.)
2. **KOL-2 (re-full, P3).** Only if a second model with an extrapolated context claim reaches review: add an optional field (for example `trainedContextWindow`) to the catalog schema and an invariant that `contextWindow` must not exceed it without a note. Kolibri alone does not justify this, because it will not enter the catalog.

## Not recommended

- **KOL-3, admitting Kolibri-1.** Fails gates 3, 4, and 5. MCP Registry Policy bucket 5. This decision is about fit with Nexus's hardware tiers and runtimes, not about the model's quality.
- **Running the official vLLM path as a new Nexus runtime.** It would be a fourth runtime job with a CUDA-datacenter requirement, which no Nexus hardware tier has.
- **Adding a fourth reasoning-effort level to match Kolibri's `none / low / medium / high`.** The existing three modes cover the range; the extra level has no observed user need.

## Risks and conflicts

- KOL-1 adds one release-scoped known-gap row and one test file (low risk). It changes no catalog entry and does not edit the acceptance bar, so no job-map row moves.
- The size estimates in K1 are arithmetic from parameter count and bits per weight, not measured downloads. They are far enough above 24 GB that the conclusion does not depend on their precision.
