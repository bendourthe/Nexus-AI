**Goal**: In both the desktop app and the VS Code extension, the document tools (`document_outline`, `document_read_section`, and `parse_document`) size their output from the room left in the model's context window rather than a fixed share; native Ollama tool calls and their results travel as tool-role history in both agent loops; both loops compact old tool results before the window overflows; the desktop app has a Settings switch for the outline tools; and one smoke run on a question set with at least 20 cross-section questions is scored against a decision rule fixed before the run. The outline flag stays off in v2.12.0. The plan also carries the Kolibri-1 decline record, the declined-models index, and its guard test (absorbed Phase 1).

## Overview

v2.11.0 shipped two local tools that let an agent read a long document by section. Its smoke test showed the tools do something nothing else on this machine does: past page 50 of a 65-page manual they answered 3 to 4 of 10 questions, where `parse_document` and BM25 retrieval answered none. Overall scores stayed low (about 8 of 24) for one main reason: tool results pile up in the model's 16,384-token window until the model forgets the question. `parse_document` fails the same way after a single read, so every user who asks the coding agent about a large document meets this today (DF-v211-7).

This plan fixes that failure at its cause, in both channels. Tools learn how much of the window is already used, from the prompt token count the backend returns on every turn plus what earlier tools in the same turn already returned, and size their output from what is left. Native tool calls and results move from text pasted into user turns to the tool-role messages the models were trained on (WN-v211-5), in one history per loop. Both loops then compact old tool results through one shared function that works on that final message shape. The desktop app gets the Settings switch the extension already has (DF-v211-4). A larger generated manual and an expanded question set support one smoke run, scored against a bar fixed in this plan before the run starts, which decides whether the three repeats the promotion review needs are worth scheduling in v2.13.0.

Phase 1 is the absorbed Kolibri-1 seed (a decline record, a living declined-models index, and a guard test), plus two lines of v2.11 housekeeping folded into the same commit. PPTX and XLSX outlines (DF-v211-6) are deferred by the maintainer's choice.

**Cut-line**: Phase 3 (tool-role history) starts with a one-hour check that Ollama 0.32.15 actually shows tool-role results to gemma4 and qwen3.5. If it does not, Phase 3 becomes a known gap, Phase 4 builds compaction on today's message shape, and the plan continues. Phase 6 depends only on phases 2 and 4.

## Goals First

**Target problem**: A solo builder who asks the local coding agent about a long document gets an answer that depends on how much text the tools happened to dump into a fixed-size window. After one large `parse_document` read, or about four outline section reads, the model forgets the question. The outline tools cannot be judged for promotion until that is fixed, and their M5 review is due at v2.13.0 (DF-v211-2).

**Persona**: The solo builder (`STRATEGY.md` section 2, primary) for phases 2 to 6. The maintainer (secondary) for Phase 1 and the evaluation.

**Pillar**: Agentic AI Coding, rank 1 in `STRATEGY.md` section 4. The Chat pillar does not change.

**Definition of done**:
1. The seed's Definition of Done (`docs/v2/v2.12/plans/v2.12.0-adoption-kolibri-1.md`, items 1 to 5) holds, and the seed's Status line names this plan.
2. In both channels, each document tool's output budget is computed per call from a per-turn ledger: the window size minus the last turn's prompt tokens (Ollama `prompt_eval_count`, or OpenAI-shaped `usage.prompt_tokens` when the backend sends it) minus the estimated tokens of tool results already returned earlier in the same turn, with a floor and the existing fixed shares as a ceiling. When no count is known, every tool, including `parse_document`, falls back to a fixed share of the window. A test in each channel shows a later read in a fuller conversation, and a second read in the same turn, each get a smaller budget than the same read in an empty one. The extension's `parse_document`, which has no output cap today, gets one.
3. For native Ollama calls, both `AgentLoop` (through `ConversationManager`) and `HeadlessAgentSession` keep one history in which a call is an assistant message carrying `tool_calls`, followed by one `tool`-role message per result whose content is byte-identical to today's `formatToolResult(...)` envelope. Persisted chat history keeps today's row format (the tool result stored as the same user-role envelope), so `ChatHistoryStore` needs no migration and a resumed session behaves as today. Text-parsed calls, and the LM Studio and OpenAI-compatible clients, keep today's shape.
4. Both loops compact through one shared function that elides older tool results by loop-owned position (never by scanning content), keeps every assistant call paired with its results, and never removes the system prompt, the task message, or the most recent tool result. `ContextCompactor`'s strategies (`ToolResultClearing`, `SlidingWindow`, `EmergencyTrim`) understand the tool role. An adversarial test shows a document that imitates the result envelope cannot make compaction drop the task.
5. The desktop Settings page has an outline-tools switch (and its summaries switch) wired to `coding.documentOutline.status` and `setEnabled`, tested like the existing `parse_document` switch.
6. `docs/v2/v2.12/development/outline-eval.md` holds one run of arms A (`parse_document`) and C (outline tools) on qwen3.5:9b and gemma4:12b over the expanded set, plus an anchor run of the same arms on the v2.11 24-question set, scored against the decision rule in Phase 6 that was copied into that file and committed before the run started. The outline flag stays off in v2.12.0.
7. The final phase asks the maintainer for one real-use entry (M5) with a named DEVLOG template.

**User-outcome target**: on the v2.11 24-question set, arm A's "error or no answer" count at least halves against v2.11's run, on both models. This is reported separately from the promotion decision, because every `parse_document` user benefits from it whether or not the outline tools are promoted.

**Key metric**: STRATEGY M5 applies to the outline tools (DF-v211-2, review at v2.13.0): this plan produces the decision-rule result and asks for the real-use entry the review needs. M2 (every pillar within budget on the reference GPU) is not measured by this plan; it removes one known way tool output overflows the window. M3 is protected: the window size comes from the existing loopback `/api/ps` probe and the prompt counts from responses already received, so no new network path is added; the Tier 3 deep pass checks this.

**Non-goals** (each with its reason):
- no PPTX or XLSX outlines: deferred by the maintainer (DF-v211-6 stays open).
- no three-repeat promotion run and no flag promotion: one run only, by the maintainer's choice; the decision rule decides whether the repeats are scheduled in v2.13.0.
- no `ChatHistoryStore` schema migration: tool-role turns are saved in today's row format (Definition of done 3).
- no tool-role history for the LM Studio and OpenAI-compatible clients: the evaluation and today's failure are Ollama-only; recorded as a known gap in Phase 3.
- no new model, catalog row, or acceptance-bar job: the evaluation reuses qwen3.5:9b and gemma4:12b.
- no change to screening, redaction, or the untrusted-content wrapper: v2.11's deep pass hardened them, and tool-role content reuses the same envelope bytes.
- no widening of the core role unions (`core/chat/`): tool-role messages are mapped at the `modules/coding` boundary.
- no publication of the release in this plan: it ends with integration into `develop` and an installer for field testing; the release follows once field testing passes.

## Phase 2: Window-aware tool output

**Goal**: Every document tool sizes its output per call from a per-turn ledger of the room left in the active model's window, in both channels.
**Prerequisites**: Phase 1.
**Stability Gate**: In both channels a test shows the same `document_read_section` (and `parse_document`) call returns less text when the conversation's last prompt used most of the window than when it used none, and the second of two reads in one turn returns less than the first, never below the floor and never above today's fixed share; with no count known, every tool, including the extension's `parse_document`, is capped at its fixed share.
**Verification Expectation**: First, with qwen3.5:9b loaded at a 16,384-token window, send three growing chat requests to Ollama 0.32.15 and observe that `prompt_eval_count` grows with the whole prompt, not only the uncached suffix; record the three values. Then run one headless agent session that asks about `manual-60p.pdf` past page 50 with the outline flag on, log each tool call's budget, and observe the budgets fall as the conversation grows and within a turn, and the session's last prompt stay below the window. **Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Changes how every coding turn's tool output is sized in both channels' agent loops; an error starves tools or still overflows the window.

### Sub-tasks

#### 2.1 -- Per-turn ledger in both loops

**Objective**: Make an up-to-date estimate of the tokens already in the window available to every tool call, in both loops.

**Prompt**:
> Create `modules/coding/runtime/outputBudget.ts`, a module with no dependency on either loop, holding a small `TurnLedger`: it starts each turn from the last known prompt token count (or, before the first turn or when the backend gives none, an estimate from the characters of the messages about to be sent), and `record(chars)` adds the estimated tokens of each tool result returned in the current turn. In `modules/coding/runtime/HeadlessAgentSession.ts`, read `prompt_eval_count` from the final (`done`) chunk of each turn (already parsed by `LLMStreamChunkSchema`; `core/chat/sessionContextUsage.ts` treats it as a snapshot of the whole prompt, not a value to sum) and feed the ledger. In `src/tools/AgentLoop.ts`, capture the same value in `_streamOneTurn` from the `done` chunk (not from `sharedInferenceMetrics().lastFor`, which is shared across sessions). In the LM Studio and headless OpenAI clients, map `usage.prompt_tokens` to the same field when the stream sends it, and leave it absent otherwise. Both loops pass the budget to each tool call as a per-call value (through `HeadlessToolContext` and the extension handlers' deps); no tool reads it from a value captured when the tool or the cached outline core was created. Treat a count within 64 tokens of the window as "possibly truncated by the backend" and report it to the ledger as full. Add unit tests in `tests/unit/runtime/HeadlessAgentSession.test.ts` and `tests/unit/tools/AgentLoop.test.ts` with scripted clients that report `prompt_eval_count`, and a `tests/unit/runtime/outputBudget.test.ts`.

**Failure modes**: A backend that omits the count leaves the ledger on its character estimate. A turn that errors before `done` keeps the previous value. A value larger than the window is clamped to the window. If the Verification Expectation's first check shows the count covers only the uncached suffix, the ledger uses the character estimate whenever it is larger, and the deviation is recorded in the session history.
