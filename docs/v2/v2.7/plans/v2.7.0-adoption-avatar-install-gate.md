**Goal**: On a diffusion-pro host, talking-head video is offered only when the official LongCat Avatar 1.5 weights are installed; a capable host that lacks those weights can still attach a photo and audio, and is told to install the weights instead of being routed into an ordinary image-to-video job. Installing the weights and confirming does not by itself produce a sampled talking-head while DF-8 is open. The Empero Qwen3.8-35B-A3B distill is recorded as not admitted, either as a subsection of the living acceptance bar or as a v2.7.0 known-gap row that says so, and never as a catalog row.

## Overview

The seeding comparison kept two items and dropped the other five sources. LongCat-Video's talking-head mode is already hardware-gated: `avatarAvailable` in `core/video/avatarGate.ts` requires `diffusion-pro` and at least 20 GB VRAM, and `assertAvatarAllowed` also requires an explicit local-generation confirm and the official `meituan-longcat` repo. The Photo + audio control and the attachment router do not check that `longcat-video-avatar-1.5` is installed. `desktop/tests/VideoLabPage.test.tsx` proves the hole: `videoModels()` installs only Wan 2.1, and "runs audio2video on a confirmed diffusion-pro host" still submits `audio2video`.

`desktop/src/modules/video/intent.ts` infers the mode from attachments. When `avatarEnabled` is false, a photo plus an audio track falls through to `image2video`. The page also uses that same hardware flag to decide whether the composer accepts audio. Phase 1 splits the two: hardware still accepts audio, and a pure refusal runs before intent on a capable host that lacks the registry row. Below `diffusion-pro`, today's behavior stays: the talking-head path stays hidden, and a photo still routes to image-to-video.

Phase 2 is the comparison's documentation item, for the maintainer rather than for someone generating video. It adds one exclusion subsection to `docs/reference/model-acceptance.md` only after the v2.6.0 plan has already written the Qwen3.8 family section there. If that section is absent, Phase 2 records a known gap that names the distill as not admitted, and does not open a second admission write-up. No phase adds a catalog row, a runtime, a weight download, or a LongCat inference import. Live sampling remains `docs/v2/v2.0/known-gaps.md` DF-8.

Reverse-engineering order in the comparison puts the note before the gate. The gate does not depend on the note, and the note depends on a different plan's edit of the same living reference. This plan therefore ships the gate first.

## Goals First

**Target problem**: A person generating video locally can be offered a talking-head run the machine cannot perform, because the weights are not on disk. That is the same failure as offering a mode the GPU cannot run. Nexus exists so local generation is honest about what the host can actually do (`STRATEGY.md` section 1).

**Persona**: Phase 1 serves the solo builder on one consumer GPU (`STRATEGY.md` section 2). They pick models and expect a control that is on screen to be a path the app will attempt. Phase 2 serves the maintainer (`STRATEGY.md` section 2, secondary), who has to refuse the next community Qwen3.8 request without confusing it with the 27B.

**Definition of done**: A diffusion-pro render without an installed official avatar row accepts a photo plus audio and persists an install refusal, with no `image2video` and no `audio2video` request. The same host with that row installed and the confirm switch checked submits `audio2video`. A below-tier host shows no talking-head control. The distill is named as not admitted in the acceptance bar or in `docs/v2/v2.7/known-gaps.md`. No catalog row is added. DF-8 stays open.

**Key metric**: The pass/fail observation is the definition of done above, not STRATEGY M2. M2 is an operator checklist that each pillar runs within budget on a reference GPU. This plan does not measure that. It also does not claim M5 (a shipped capability used in real work within two release cycles, or removed). DF-8 means a confirmed submit can still hit a stub, so this plan does not make a talking-head clip the maintainer can use. STRATEGY section 4 ranks Video last, and that rank is marked proposed and unconfirmed, so it does not veto a plan the owner just asked to write.

**Non-goals** (from `STRATEGY.md` section 6 and the comparison's Section 9): no hosted generation, no PrismML or Bonsai runtime, no MLX or Kev decision server, no parallel-decoding / RLCD engine, no Empero catalog row, no base LongCat text-to-video or interactive checkpoint, no multi-stream avatar audio, no re-plan of DF-8, no on-disk weight probe beyond the models list the app already uses.

#### 1.1 -- Add avatarOffered so hardware and install are both required

**Objective**: Keep `avatarAvailable` as the hardware predicate and add an offer predicate that also requires the official weights.

**Failure modes**: A missing or non-boolean `installed` argument is not installed (the offer is false). A model list that has not loaded is not installed. A row with `installed: true` and a missing, empty, `catalog-only`, or `external` source is not installed. Hardware true and installed false is not offered; hardware false and installed true is not offered. Both true is offered. Do not treat any other video id as the avatar weights. `avatarInstallRefusal` returns null when hardware is false, when the offer is true, or when the composer has no audio; it returns the install sentence when hardware is true, the offer is false, and an audio attachment is present (with or without a photo).

**Build class**: load-bearing. These predicates are the rule the page, the form, and the tests share.

**Prompt**:
> Extend `core/video/avatarGate.ts` without weakening the existing hardware gate. Keep `avatarAvailable(tierId, vramGB)` as the hardware predicate: true only for `diffusion-pro` and VRAM at least `AVATAR_MIN_VRAM_GB` (20). Add `avatarOffered(tierId, vramGB, installed: boolean): boolean` that is true only when `avatarAvailable` is true and `installed` is true. Add a pure helper that reads the raw models list (not the owned-and-filtered studio feed) and returns whether `OFFICIAL_AVATAR_MODEL_ID` (`longcat-video-avatar-1.5`) is installed. The matching row must have `installed === true` and `source === "registry"`. An absent list, a missing row, `installed` not strictly true, a missing or empty source, `catalog-only`, or `external` returns false. Do not require the row to be the selected model. If the row type has a repo field, it must start with `meituan-longcat/`; if it has no repo field, the id plus `source === "registry"` is the list check, and submit still passes `OFFICIAL_AVATAR_REPO` into `assertAvatarAllowed`. Add `avatarInstallRefusal(...)` returning the install sentence or null, with the cases in the failure-modes line. The sentence names `longcat-video-avatar-1.5` and Settings > Models. Unit-test both helpers next to the existing avatar gate tests. Do not vendor LongCat inference code and do not edit `core/registry/catalog.json`. On-disk existence beyond this list is out of scope (parked; DF-8 owns inference).

#### 1.2 -- Wire the offer into Video Lab routing and the submit residency check

**Objective**: Keep hardware and offer as two page-level bits. Hardware still accepts audio. Offer drives the controls and `audio2video`. A capable host without weights is refused before intent can fall through.

**Failure modes**: While `modelsClient.list()` has not resolved, the offer is false and `avatarInstallRefusal` is null until attachments exist; the composer may still accept audio once hardware is known. If the list later shows a registry row, the confirm control may appear, unchecked. If the user had checked it and the row then disappears, clear `confirmLocalAvatar` and any `audio2video` mode value, and the next submit refuses. A below-tier host never takes the avatar path. Residency and the GPU-busy check for a photo-plus-audio turn on a hardware-capable host use `longcat-video-avatar-1.5`, not the selected Wan id. Do not call `inferVideoIntent` on that turn until the install refusal has returned null.

**Build class**: load-bearing.

**Prompt**:
> `desktop/src/modules/video/VideoLabPage.tsx` today uses one `canAvatar` from `avatarAvailable(diffusionTier, vramGB)` for three different jobs: `MediaComposer` `accept` and placeholder (around the composer near the bottom of the page), `VideoPromptForm`'s `avatarAvailable` prop, and `inferVideoIntent`'s `avatarEnabled`. Split them. `hardwareAllowsAvatar = avatarAvailable(...)` keeps the composer `accept` on audio (`chatComposerAccept({ allowImages: true, allowAudio: true })`) and the talking-head placeholder. `offered = avatarOffered(...)` is what the form and `avatarEnabled` receive. Compute `installed` from the raw `modelsClient.list()` result via the Phase 1.1 helper, not from `installedModelsForType` (that feed drops rows the user does not own).
>
> In `handleSubmit`, before the GPU-busy check and before `residency.request`, and before `inferVideoIntent`: if `avatarInstallRefusal` returns a sentence, patch and persist it and return. Do not start `image2video` or `audio2video`. When the refusal is null and the turn has photo plus audio and `offered` is true, the busy check and `residency.request` use `targetModelId` `longcat-video-avatar-1.5` and that row's installed bit, not `selectedModelId`. Then call `assertAvatarAllowed` with `modelId: OFFICIAL_AVATAR_MODEL_ID`, `weightRepo: OFFICIAL_AVATAR_REPO`, and `confirmed: values.confirmLocalAvatar`. Do not set `confirmed` to true in code. `intent.ts` stays as it is: `avatarEnabled: false` still falls through to `image2video`, which is why the page refusal is mandatory and runs first.
>
> When `offered` flips from true to false, set `confirmLocalAvatar` back to false and reset a stored mode of `audio2video` so a later reinstall does not skip the checkbox. Below `diffusion-pro` or under 20 GB, do not add the install refusal: a photo still routes to `image2video` as today. Do not import LongCat Python, do not change DF-8, and do not add a catalog row. A successful `audio2video` submit may still hit the stub. Do not add copy that claims a sampled clip.
