# DeepSeek, decision-model evaluations and Reylo comparison

Adoption target: v2.17.0

**Target confirmation**: owner selected v2.17.0 on 2026-10-23. **Baseline**: `develop`, `efaa651dd447cc6c0efdad359bc5457118e5906a`, package 2.15.0. **Scope**: four supplied sources, with DeepInfer and Project Maya primary documentation added to verify the supplied claims. **Status**: assessment and prioritized adoption proposal, no implementation or model qualification. Source snapshots and scan receipts are in [source receipts](v2.17.0-source-receipts.json).

## Recommendation

Adopt a bounded, offline evaluation method before adding another evaluator model. Keep existing deterministic checks and held-out protections. Defer Reylo until its compiler and packaging requirements can be justified. Do not add DeepInfer or the Maya model to the installer or default catalog on this evidence.

| Source | Nexus disposition | Support tier in Nexus | Main reason |
|---|---|---|---|
| DeepSeek V4.1 Flash Maya GGUF | Decline default admission; conditional patient-tier research only | Candidate | A real community artifact and offload engine exist, but there is no local fit, latency, quality or tool-call qualification |
| DeepInfer and deepseek-recipe | Drop engine adoption; retain recipe as a protocol reference | Future engine / candidate reference | Datacenter engine requirements do not fit the product; protocol conversion does not establish inference parity |
| Decision-model eval cookbook | Adopt the method conditionally | Candidate | Useful for a narrow subjective failure mode if local human labels and model scores exist |
| Reylo | Defer package migration; reuse current SQLite tests | Candidate | SQLite support exists, but beta compiler execution and build/runtime compatibility need proof |

These are recommendations, not new supported capabilities. The existing paths below were inspected, not exercised in this assessment. The strategy grounds the work in the solo builder and maintainer personas, local-only operation, and M4 shipping confidence; an evaluator must demonstrate actual maintainer use under M5. See [STRATEGY.md](../../../../../STRATEGY.md), [model acceptance](../../../../reference/model-acceptance.md) and the [v2.16 plan](../../v2.16/plans/v2.16.0-adoption-humanizer-handwired-nemotron-deepseek.md).

## Source verification

### Maya GGUF

The headline's approximately 339 GB is Maya-S's six GGUF shards: the pinned file listing sums to 339,477,953,988 bytes. The current card lists 347.5 GB with its drafter, and Maya-XS at 280.9 GB including its drafter. Full model-in-memory figures are 178.2 and 115.3 GB; the 161.3 GB Engram tables are SSD-backed. These are different quantities, not GPU memory requirements. The card's next-token agreement measurements are publisher results, not Nexus coding-quality scores. [Pinned model card](https://huggingface.co/peasantsmith/DeepSeek-V4.1-Flash-1017-Maya-GGUF/blob/d1fc01009f21e26157acb6858c315d0365483b72/README.md).

[Project Maya](https://github.com/mw00/project-maya) documents a dedicated `maya-ds4` engine, RAM/SSD expert streaming, Windows/Linux paths, and loopback API compatibility. Its general Windows support is qualified as experimental. Streaming can use less memory than a full in-memory configuration, so neither file size nor the 128 GB configuration establishes a minimum RAM requirement. Its headline performance examples mix models and hardware; they do not prove this DeepSeek quant's performance on the reference laptop.

Nexus already has an opt-in patient tier with longer timeouts and user-registered offload adapters. The implementation explicitly says it does not bundle that runtime: [patientTier.ts](../../../../../core/registry/patientTier.ts). Its existing frontier MoE job is occupied by `inkling-small`, per [model acceptance](../../../../reference/model-acceptance.md). A Maya trial therefore has to justify a replacement or a genuinely uncovered job. An available GGUF changes the evidence behind the earlier [DeepSeek comparison](../../v2.16/comparisons/v2.16.0-comparison-humanizer-handwired-nemotron-deepseek.md); it does not itself establish stock Ollama compatibility or justify a new default.

**Reopen condition**: a maintainer-owned offload use case, adequate disk budget, and a bounded trial through an existing local adapter, measuring cold/warm latency, peak RAM/VRAM, disk traffic, task outcomes and native parallel tool-call round trips against the current job holder. Verify every shard, drafter and additional asset. Treat speculative decoding as an A/B on that host. No model weights were downloaded here.

### DeepInfer and recipe

[DeepInfer's pinned README](https://github.com/deepseek-ai/DeepInfer/blob/9bd9cf243fc53ef9afbf8f04d391d989117d6ab9/README.md) identifies the production framework but describes this release as offline inference. A complete service still needs KV-cache infrastructure, disaggregated serving and replica load balancing. Supported accelerators are NVIDIA SM100 and Huawei Ascend 950; prerequisites include Linux, GCC 13+, Python 3.12 and CUDA 13 or CANN 9.2. Structured decoding and distributed execution are documented. Its license is Apache-2.0. This is not a supported Windows/RTX 3080 Ti Laptop backend.

The quoted DSpark result is substantiated, with a narrower scope than the summary implies: the [deployment Q&A](https://github.com/deepseek-ai/DeepInfer/blob/9bd9cf243fc53ef9afbf8f04d391d989117d6ab9/doc/inference_deployment_qa.md) derives about 30% fewer draft-token verifications and 4-7% estimated throughput improvement from EP64/DP64 benchmark data at roughly 60 concurrent sequences per rank. Its table also shows a loss at low concurrency. This is a production operating-point comparison, not a consumer single-request guarantee.

[deepseek-recipe](https://github.com/deepseek-ai/deepseek-recipe/tree/935817c66f5d6e64838f419692545f06787e485f) is Rust libraries with Python bindings for conversation conversion, prompt rendering, token encoding and streamed output parsing. The caller supplies inference, HTTP transport and tool execution. JSON Schema prompt conversion does not itself enforce constrained decoding. Its image URL fetcher permits arbitrary destinations unless the caller supplies a filter. The [license](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/LICENSE) and workspace manifest are MIT, correcting the supplied statement that both projects are Apache-2.0. Formatting compatibility does not guarantee identical generated answers.

Nexus already implements native tool calls and ordered history through [headlessOpenAiClient.ts](../../../../../modules/coding/llm/headlessOpenAiClient.ts), [openAiToolCalls.ts](../../../../../modules/coding/llm/openAiToolCalls.ts) and [toolHistory.ts](../../../../../modules/coding/llm/toolHistory.ts). Its older `deepseek` prompt/JSON parser names target DeepSeek Coder conventions: [PromptFormat.ts](../../../../../modules/coding/llm/PromptFormat.ts), [ToolCallFormat.ts](../../../../../modules/coding/llm/ToolCallFormat.ts). Those names do not prove V4.1 wire compatibility. Recipe is a useful future reference for split-chunk parsing, tool IDs, reasoning separation and context accounting, but no current failing V4.1 integration was reproduced to justify adding its Rust/Python stack.

**Reopen condition**: an admitted local model needs these protocol semantics and an existing client cannot express them. Reuse the provider-neutral LLM port and existing parsing tests first. Do not route a new runtime through an MCP server or let protocol conversion execute tools.

### Evaluation cookbook

The [cookbook](https://hamel.dev/blog/posts/decision-model-evals/) reports a 100-trace apartment-leasing experiment. Its actionable lessons are task-specific precision/recall requirements, threshold selection on training folds, validation on common held-out folds, saved-score reuse, cost comparison, calibration checks with Brier scores, and narrow judges per failure mode. Platt scaling is optional and can worsen results. The named models' ranking is not evidence for Nexus tasks; the article leaves latency outside its experiment.

| Insight | Nexus status | Evidence and gap |
|---|---|---|
| Explicit pass/fail criteria | Already implemented | [goldenCriteria.ts](../../../../../modules/coding/evaluation/goldenCriteria.ts), [GoldenTaskRunner.ts](../../../../../modules/coding/evaluation/GoldenTaskRunner.ts) evaluate task criteria |
| Held-out separation | Already implemented | [goldenSplit.ts](../../../../../modules/coding/evaluation/goldenSplit.ts) keeps test tasks out of optimizer-visible data |
| Failure-specific scored judges and minimum precision/recall | Not found in inspected evaluation paths | Existing [validationGate.ts](../../../../../modules/coding/evaluation/validationGate.ts) compares task pass rates; it is not a probability classifier |
| Threshold tuning on saved predictions | Missing in inspected evaluation paths | Existing [localCatalogEval.ts](../../../../../modules/coding/evaluation/localCatalogEval.ts) records task outcomes, not labeled probability rows |
| Calibration and Brier comparison | Missing in inspected evaluation paths | [evalGate.ts](../../../../../core/tuning/evalGate.ts) compares adapter/base scores with a regression tolerance; that tolerance is not a decision threshold |
| Cost/quality comparison | Partly implemented | [evaluate-local-rewrites.mjs](../../../../../scripts/evaluate-local-rewrites.mjs) already records request identity, token counts, durations and missing/error outcomes; classifier-quality analysis is separate |

The inspected evaluation directories had no probability-calibration or precision/recall implementation. A wider keyword search found unrelated document and hardware calibration prose, not the proposed evaluator. This is a scoped observation, not proof that no analogous code exists anywhere. [Earlier Jev/Laya/Kev decisions](../../../../archive/v2/v2.10/comparisons/v2.10.0-comparison-system-one-models.md) and [declined proposals](../../../../reference/declined-models.md) remain intact. No hosted judge, API key or new evaluator checkpoint is recommended.

### Reylo

[Reylo's pinned README](https://github.com/colinhacks/reylo/blob/c8eddb9bf0a89603b35b7b34b4bb3aeccf5bc4d2/README.md) documents `.sql` imports with schema-derived types, Postgres/MySQL/SQLite support, TypeScript 7.1 beta, Node 24+, a development database, content mappers and `--runExternalCode`. This corrects any assumption that Reylo is Postgres-only or works as an ordinary dependency on Nexus's current compiler. Its license is MIT.

The [esbuild plugin](https://github.com/colinhacks/reylo/blob/c8eddb9bf0a89603b35b7b34b4bb3aeccf5bc4d2/src/esbuild.ts) turns SQL imports into JavaScript at build time. Therefore its Node tooling requirement does not automatically force the same minimum into a compiled sidecar; that output must be inspected and exercised. The [SQLite engine](https://github.com/colinhacks/reylo/blob/c8eddb9bf0a89603b35b7b34b4bb3aeccf5bc4d2/engine/sqlite/csrc/reylo_sqlite.c) prepares against an in-memory schema replay, and [driver tests](https://github.com/colinhacks/reylo/blob/c8eddb9bf0a89603b35b7b34b4bb3aeccf5bc4d2/tests/sqlite-drivers.test.ts) cover driver-version mismatches. Upstream tests were inspected, not run here.

Nexus's [package.json](../../../../../package.json) declares TypeScript `^5.4.0` and Node 20+; the installed compiler observed here is 5.9.3. The [sidecar build](../../../../../desktop/sidecar/esbuild.config.mjs) targets Node 20/CJS and provisions native SQLite for installer Node 22.11.0, also pinned in [versions.lock.json](../../../../../scripts/installer/build/versions.lock.json). The host's Node 24.13.0 does not prove packaged compatibility. Root Node16 module resolution, desktop Vite, the VSIX build and native addon packaging all need their own evidence before migration.

There is a real duplicated-contract surface: [ChatHistoryStore.ts](../../../../../src/storage/ChatHistoryStore.ts) manually declares `SessionRow`/`MessageRow` and casts prepared-query results; [SqliteGraphStore.ts](../../../../../core/codegraph/store/SqliteGraphStore.ts) similarly casts selected rows. These are maintenance risks, not a demonstrated current bug. Existing [ChatHistoryStore tests](../../../../../tests/unit/storage/ChatHistoryStore.test.ts) and [graph-store tests](../../../../../tests/unit/core/codegraph/SqliteGraphStore.test.ts) already exercise real temporary databases. Keep query ownership in existing stores, not the renderer. A whole-project SQL extraction or a homegrown SQL type parser is not justified.

**Reopen condition**: stable compiler support or an independently justified toolchain upgrade, a reproducible disposable schema fixture, and one changed query that demonstrates useful editor/compiler failure detection. Then prove the generated query on shipped Node 22, the VSIX host, sidecar CJS bundle and native SQLite version. Start with one store-owned query, never a user's actual database.

## Security assessment

### Source-security gate

The four supplied pages were fetched to temporary storage and scanned before content analysis. All initially returned CLEAR under the heuristic used. Subsequent source archives were scanned before file inspection: recipe 136 text files, DeepInfer 336, Reylo 3,480. Recipe and DeepInfer returned CLEAR. Reylo returned PROCEED-WITH-CAUTION. The supplemental Maya README and pinned model card returned CLEAR. No source was BLOCKED.

The Reylo findings were expected compiler-execution instructions such as `tsc --noEmit --runExternalCode`, and `.github/workflows/test.yml` line 250's `sudo rm -rf ~/postgres-debs/partial ~/postgres-debs/lock`. The former expands the build's execution boundary; the latter is scoped upstream CI cleanup, not a command to run locally. Neither was executed. Its AGENTS and skill files were not adopted as instructions.

The scan covered UTF-8 text files up to 2 MB and selected downloaded pages, using patterns for instruction overrides, destructive commands and install/build execution. Nonfiles, oversized and binary content were skipped; submodule contents and dependencies were not fetched or audited. Absence of a pattern match is not a security guarantee. Source archives were read without running their code, package hooks, notebook cells or installers. No private project content was uploaded; only public-source URLs were requested.

## Prioritized adoption sequence

The ordering is skill-native first, then local implementation/reuse. These are bounded planning inputs, not an authorized phased implementation plan.

1. **A1, evaluation decision record** (about half a day of preparation plus maintainer labeling, estimate only). Reuse the existing evaluation workflow to select one observed subjective failure class, for example a document answer that passes mechanical extraction checks but contains unsupported claims. Freeze the intended user, loss from a missed error versus a false alarm, acceptable error rates, label definitions, sample provenance, privacy limits and a stopping rule. Proposed output: `docs/releases/v2/v2.17/development/decision-eval-contract.md`. Acceptance: an actual reusable labeled workload exists, with both classes and enough independent groups for the declared split. If it does not, record HOLD and stop; do not manufacture a new evaluator job.
2. **A2, local analysis only after A1** (one to three development days, estimate only). First inspect reusable records from the existing local evaluation harnesses. If a small calculator is still needed, propose `lib/decision-eval.mjs` and a thin `scripts/evaluate-local-decisions.mjs`, not a model service. Its input contract must bind trace ID, human label, finite score in [0,1], score meaning/direction, model/prompt digest, grouping key, generation status and measured resource fields. Missing/invalid predictions remain visible in the denominator and cannot become passing judgments. The output is advisory evidence; it cannot change confirmation tiers, catalog admission or release checks.
3. **A2 verification and stop**. Freeze all data partitions before comparison; related traces from the same session stay together. Threshold selection and any learned mapping use development data only; keep a final untouched test set for a one-time result. Reject duplicate IDs, conflicting labels, nonfinite values, insufficient class counts, leaked groups and incompatible model identities. Include tiny exact-count fixtures, a deliberately infeasible case, and a test that test labels cannot influence the selected threshold. Run the actual CLI over a saved local fixture with outbound access disabled. Report unavailable or infeasible results explicitly. No universal 80% target is adopted from the article.
4. **A2 operational qualification**. Use local wall time, tokens, peak residency and evaluation overhead rather than API dollar prices. If real subjective scores do not exist, a separate preregistered pilot may use an already installed, job-qualified model through the current local adapter. It must distinguish a model's emitted numeric rating from a calibrated probability. Do not download a judge checkpoint merely to fill the table. Keep the existing exact [golden criteria](../../../../../modules/coding/evaluation/goldenCriteria.ts) and [regression gate](../../../../../modules/coding/evaluation/validationGate.ts) unchanged. A maintainer must use the report in one real release decision, or the experiment remains HOLD.
5. **A3, opportunistic store coverage** (hours, when an actual query changes). Add a meaningful prepare/execute/assert check to the relevant existing SQLite suite using its real migration/schema path and representative null/aggregate/FTS behavior. Keep every database disposable. Do not add a second schema source, wrap every statement, extract all SQL, or build a SQL parser. This is a maintenance practice, not a standalone migration project.

Any later `/plan from-comparison` should retain `Adoption target: v2.17.0`, sequence A1 before A2, and keep W1-W3/X1-X2 outside committed implementation scope unless separately selected. It should name the actual data owner and replace these effort estimates with the observed workload. Proposed-file links above are intentionally inline paths because those files do not exist yet.

## Conflicts and exclusions

- The v2.16 plan already owns the DeepSeek decline record. This comparison supplies new artifact evidence without editing that plan or quietly claiming its Phase 1 has happened.
- Patient-tier support is not equivalent to a bundled Maya engine, and the single-GPU ceiling alone is not a valid rejection of disk offloading. Admission stays conditional on a real job and measurements.
- Copying recipe into the app would add a language/runtime bridge and potentially URL fetching. Protocol conformance tests are the first sufficient step if a real need appears.
- Reylo would change compiler execution, schema availability in CI and multiple packaging paths. A production database must never become a build prerequisite. Its esbuild plugin merits inspection, not an untested compatibility assertion.
- A classifier must never authorize dangerous tools or replace deterministic checks. Subjective scoring is a supplementary maintainer aid.
- No external model ranking, token agreement statistic or datacenter benchmark establishes local user benefit. No named source is adopted for novelty alone.
