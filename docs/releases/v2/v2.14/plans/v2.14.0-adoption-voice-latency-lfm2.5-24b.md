## Overview

Two independent tracks share this release and touch disjoint files except one shared helper. The **voice track** measures the existing desktop voice loop, then removes its built-in waits. Today the sidecar receives the model's reply token by token but hands the webview the finished reply in one IPC call (`desktop/sidecar/src/chat/chatMessageHandler.ts:60-67`, `desktop/src/modules/chat/chatIpcClient.ts:104`); the webview then sends the whole reply to `audio.speak` (`ChatPage.tsx:1361`), whose Python runtime rebuilds Kokoro per call, converts samples in a Python loop and returns one WAV (`runtimes/audio/engines.py:93-137`). The audio runtime is a single blocking stdin loop with no notifications (`runtimes/audio/main.py:99-104`), and its Node client is request/response only (`core/audio/AudioRuntimeClient.ts:1-8`).

The fix moves the sentence boundary to where the stream already exists. The sidecar splits the reply into speakable sentences as tokens arrive and starts synthesis immediately. The audio runtime gains a cancellable synthesis worker and per-segment notifications, and the webview fetches ready segments by polling, the same drain pattern diffusion and OCR jobs use. Reply text still appears on screen all at once; on-screen streaming is a separate future decision.

The **model track** asks one question: does LFM2.5-24B-A2B do the 16 GB MoE worker job better than its current opt-in holder, `nemotron-lightning:30b-a3b-offload`? A Phase 1 probe can end it early. Otherwise Nexus learns to handle reasoning that opens inside the prompt, the golden runner gains the metrics, sampler control and LFM tool-call codec the comparison needs, and both models run Nexus's 28 golden tasks. Admission is opt-in only (`docs/reference/model-acceptance.md:149`) and only on a defined win; a tie, failure or early stop ends in a declined-models row, which satisfies the Goal as fully as an admission.

Voice is desktop-only today: the VS Code extension has no voice loop, speech-to-text or text-to-speech path under `src/`. The voice track does not add voice to the extension. The reasoning splitter is shared code and is exercised in the extension, desktop Chat and the headless loop. PersonaPlex (V3) is not built here; Phase 2 records whether its trigger fired.

## Goals First / Definition of Done

- **Target problem and persona**: the solo builder in [STRATEGY.md](../../../../../STRATEGY.md) who uses voice in Chat hears nothing until the model has finished the whole reply and the whole reply has been synthesized. The maintainer has no local evidence on whether a smaller, natively fitting MoE should hold the 16 GB worker job.
- **Strategy grounding**: M2 (every pillar within budget on the reference GPU) constrains both tracks; M3 (zero non-loopback connections in ordinary use) gains an explicit voice-path check; M5 (used in real work within two cycles) applies to the voice change and any admitted model. Phase 1 records the owner's current voice usage, because the Q3 grill answer is pending. These metrics remain PROPOSED in STRATEGY.md and are not promoted here.
- **Time to first audio (term used throughout)**: wall time from the end of the user's utterance (the transcription request) to the first audio sample reaching the webview's playback path, measured warm on the medium fixture (about three sentences) on the reference 16 GB tier. One definition, one name.
- **Voice done**: median time to first audio falls by at least 40% versus the Phase 1 baseline and is at most 2.0 s; p95 silent gap between segments is under 300 ms on the medium and long fixtures; time to last audio is no worse than baseline; barge-in stops playback within 150 ms and cancels synthesis within 500 ms; spoken text equals the reply's speakable projection; no non-loopback connection occurs during a voice turn.
- **Speakable projection**: the reply's visible text with reasoning and tool-call text removed (nothing spoken until reasoning ends for models whose template opens it in the prompt; nothing at all if it never ends), secrets removed by `redactSecrets` before sentence splitting, fenced code and tables replaced by a short spoken cue ("code is on screen", "table is on screen"), and links spoken by label, never URL.
- **Model done**: either an opt-in catalog entry that takes the 16 GB MoE worker job on a frozen win, with integrity-verified weights, or a declined-models row with the measured reason. No default changes in any tier.
- **Delivery done**: local gates, packaged Windows behavioral evidence, independent Goal review and final integration evidence exist. No release step precedes green merged integration.

### Sub-tasks

#### 2.1 - Make the audio runtime cancellable and streaming

- [x] T005 Make the audio runtime cancellable and streaming runtimes/audio/main.py

**Objective**: Let synthesis run on a worker that can be cancelled and stream segments, while transcription stays responsive.

**Failure modes**: Empty or oversized text (above the frozen character cap) is rejected before synthesis; missing local weights fail closed with TTS_UNAVAILABLE and never fetch; a cancel for an unknown, finished or foreign job returns the same no-op result; a new stream cancels the active one (one stream per runtime); a transcribe request arriving during synthesis is read immediately and served on its own lane; concurrent writes to stdout are serialized.

**Prompt**:
> Restructure runtimes/audio/main.py into a stdin reader thread, a synthesis worker and a transcription lane, with a lock around _emit. Add notifications by copying the diffusion runtime's _notify pattern (runtimes/diffusion/main.py:139-141). Add `speak.stream` (emits one notification per Kokoro segment, then exactly one terminal message: completed, cancelled or error) and `speak.cancel` (sets a per-job flag checked between segments). In engines.py, cache one KPipeline per process constructed from the local weights_dir model and voice files, set HF_HUB_OFFLINE=1 and TRANSFORMERS_OFFLINE=1 in the runtime environment, check whether misaki or spaCy G2P assets need provisioning, and replace float32_pcm_to_int16_le's loop with a vectorized numpy conversion (the cache and conversion are the unconditional wins). Add pytest coverage: conversion equality with the old function, caching, ordering, bounds, cancellation, transcribe during an active stream, offline failure, and serialized output.

#### 2.3 - Shared reasoning splitter and speakable projection

- [x] T007 Shared reasoning splitter and speakable projection core/chat/speakable.ts

**Objective**: One pure place that decides what text is visible and what is speakable, usable by every path.

**Failure modes**: Text with no reasoning markers passes through unchanged when the model's template does not open reasoning in the prompt; when it does, everything is withheld until the first `</think>`, and a stream that ends without one yields nothing speakable plus a reasoning-only flag; a secret split across chunks or sentences is still redacted because redaction runs on the accumulated buffer with a trailing holdback window; unterminated code fences hold back until closed or the stream ends.

**Prompt**:
> In core/chat/ add pure, dependency-free functions: an incremental reasoning splitter taking an explicit `reasoningOpensInPrompt` flag (the caller supplies it; the function does no catalog lookup) that also handles well-formed `<think>...</think>` blocks; and an incremental speakable projector that removes reasoning and tool-call text, applies core/observability redactSecrets to the accumulated buffer with a holdback of the longest pattern length, replaces fenced code and tables with "code is on screen" / "table is on screen", speaks link labels not URLs, and emits complete sentences (abbreviations and decimals do not split). Add unit and property tests, including AWS keys, GitHub PATs and JWTs split across chunks and across a period, LFM-style raw reasoning with an orphan closer, and Gemma 4 blocks unchanged. Phase 3 reuses the reasoning splitter; if the voice track is deferred before this sub-task, Phase 3 builds it instead.
