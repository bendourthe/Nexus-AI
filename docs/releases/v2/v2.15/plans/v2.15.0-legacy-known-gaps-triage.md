# Plan - Legacy known-gaps triage

**Project**: Nexus
**Version**: v2.15.0
**Filename**: v2.15.0-legacy-known-gaps-triage.md
**Slug**: legacy-known-gaps-triage
**Plan Type**: Refactor
**Created**: 2026-10-19 (UTC)
**Status**: in-progress
**Goal**: Every known-gaps ledger from v1.17 through v2.12, including the carry-forward register, parses with zero problems in the completion checker's ledger format; every open item in the register and the v2.12 release ledger carries an evidence-backed disposition (resolved, closed with the owner's sign-off, superseded, or migrated to v2.15 with provenance); and every archived-only item is inventoried exactly once and assigned to a sized follow-up triage batch, so that what is still owed is one countable, duplicate-free list.

## Overview

The v2.14 minor run shipped v2.14.2 and archived v2.14, then stopped on `BLOCKED: approval-not-covered`. The completion checker's `gaps.minor` rule requires every known-gaps ledger at or below the run's minor to have no open item and no parse problem. Measured on 2026-10-19 (UTC) with the checker's own parser (`completion_minor.load_ledgers`, checker file sha256 prefix `f1689e72b6f96835`):

- **Open items, 210 in scope**: v1.17 6, v1.18 10, v1.19 12, v1.20 2, v2.0 9, v2.1 6, v2.2 70, v2.3 10, v2.4 74, v2.7 3, v2.8 1, v2.9 1, v2.10 1, and the v2.12 release ledger 5.
- **Parse problems, 346 total**: 204 in scope (v1.17 2, v2.4 8, v2.5 15, v2.6 17, v2.7 17, v2.8 20, v2.9 21, v2.10 22, v2.11 39, the register 43) and 142 in the legacy-cutoff ledgers (v0.7 1, v1.0 66, v1.1 38, v1.2 33, v1.3 4). By kind: 206 table rows the parser cannot read as items, 140 headings that read as gap entries without an id.
- **Clean already**: v1.4 to v1.16 report no open item and no problem; v2.13 and v2.14 report only migrated items.
- **Register coverage**: the carry-forward register `docs/v2/v2.12/known-gaps.md` (43 rows, a table the checker cannot read) carries only 23 of the archived open items by id. At least 182 archived open items appear in no active ledger (v2.4 68, v2.2 65, v1.19 11, v1.18 9, v2.3 9, v2.0 8, v1.17 5, v2.1 5, v1.20 2); some may be carried under renamed ids, which the inventory resolves.

This plan builds a pinned inventory and a lossless converter, converts every in-scope ledger into the heading format the checker reads without changing a word, and triages the register and the v2.12 release ledger (about 48 items). The archived-only items are inventoried and split into follow-up triage batches of at most 60, each planned as its own v2.15 patch plan. The legacy ledgers (v0.7, v1.0 to v1.3) are left to a Nexus-Hub checker cutoff, requested in a handoff prompt for the agent that maintains Nexus-Hub. One v2.15 gap records the other checker-contract conflicts the v2.14 run hit.

Items migrated into v2.15 stay owed there: they are resolved, or carried again by the normal gap migration at the v2.15 minor close. This plan does not by itself make a v2.15 minor run reach `MINOR COMPLETE`; it makes the remaining work countable and the checker able to read it.

## Goals First / Definition of Done

- **Target problem and persona**: the maintainer (STRATEGY.md section 2, secondary persona) cannot get a truthful answer to "what is still owed" because the backlog is scattered across unparseable archives and partly double counted, and the run tooling cannot finish any minor while that holds.
- **Strategy grounding**: maintenance work. It moves no product Key Metric directly; it serves M4 (defects trend down) and M5 (capabilities used or removed) only by making the owed list trustworthy. Its justification is the run tooling's completion gate, which blocks every future minor run.
- **Maintainer outcome**: one place answers "what is still owed": the v2.15 ledger plus the follow-up batch list, with a stated count and no item listed twice.
- **Ledgers done**: the inventory (through the pinned checker adapter) reports zero problems for every ledger from v1.17 through v2.12 and for the register; the word sequence of every converted entry is unchanged apart from the allowlisted tokens the conversion adds.
- **Items done**: every open item in the register and the v2.12 release ledger is resolved (evidence named), closed (owner's sign-off recorded), superseded (pointer to the live entry), or migrated to `docs/releases/v2/v2.15/known-gaps.md` with a verbatim body and a "Migrated from" line. No item is resolved without evidence.
- **Archived-only items done**: each appears exactly once in the follow-up batch list with its source ledger, and each batch holds at most 60 items.
- **Checker handoff done**: one v2.15 `QG` entry records the checker-contract conflicts with evidence and links `docs/releases/v2/v2.15/development/v2.15.0-nexus-hub-checker-handoff.md`.
- **Delivery done**: local gates, independent Goal review and final integration evidence exist.

## Scope and cut-lines

- **In scope**: ledgers `docs/archive/v1/v1.17` to `v1.20`, `docs/archive/v2/v2.0` to `v2.11`, `docs/releases/v2/v2.12/known-gaps.md`, the register `docs/v2/v2.12/known-gaps.md`, the v2.15 ledger (as the migration target), the inventory and converter with tests, the triage record, the follow-up batch list, the handoff prompt.
- **Out of scope**: the legacy-cutoff ledgers v0.7, v1.0, v1.1, v1.2, v1.3 (owner decision 2026-10-19); triage of archived-only items (follow-up plans); any change to Nexus-Hub (handed off).
- **Small fix**: a code or doc change that resolves an item, touches one file, changes at most about 30 lines, is covered by an existing or a new test, and adds no dependency. At most 5 such fixes in this plan; anything larger is migrated with a next step.
- **Triage ceiling**: if the inventory finds more than 60 distinct items in the register and v2.12 together, the excess moves to the follow-up batch list instead of being triaged here.
- **Phase 5 scope note**: the architecture refactor (T016) and the CI/CD reconciliation (T020) cover the artifacts this plan touched; a wider finding is recorded as a gap, not acted on here. The known-gaps reconciliation (T017) covers v1.17 to v2.15 and names the legacy-cutoff ledgers as excluded.

## Phase 1: Inventory and lossless converter

**Goal**: Know exactly which items exist and where each is duplicated, and have a converter that turns the old formats into the parsed one without changing a word.
**Prerequisites**: None.
**Stability Gate**: `node scripts/known-gaps/inventory.mjs --json` lists every in-scope item with its ledger, id, title, state and register cross-reference, and reports a distinct-item count; `node scripts/known-gaps/migrations/normalize.mjs --dry-run <ledger>` produces output the checker adapter parses with zero problems and whose preservation report passes.
**Verification Expectation**: Run the dry-run converter on `docs/archive/v2/v2.4/known-gaps.md` and on the register, parse each output through the checker adapter, and observe zero problems and a passing preservation report naming the entry count. Exercise through [[functional-verification]].
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Parser-fidelity tooling across many legacy table shapes, where a silent loss of text is the main risk.
