# Nexus-Hub Checker Handoff

Prompt for the agent maintaining Nexus-Hub. Written 2026-10-19 from a Nexus-AI `/implement v2.14` run on a machine with Nexus-Hub v4.13.13 installed, which is older than the current Nexus-Hub source. Verify every finding against the current source before changing anything: some may already be fixed. Refreshed 2026-10-19 during the v2.15.0 run (same Nexus-Hub v4.13.13, `completion_minor.py` sha256 `f1689e72b6f96835`): finding 1's remaining scope is now exact, findings 7 and 9 have new evidence, and findings 14 to 17 are new.

## Prompt

> You are working on Nexus-Hub's plan-completion tooling: `scripts/check_plan_completion.py`, `scripts/completion_minor.py`, `scripts/minor_close.py`, `scripts/cleanup_merged.py`, the record/approval flow, `scripts/validate_unicode_safety.py`, and the `technical-documentation` skill's `scripts/check_handbooks.py`. A consumer project (Nexus-AI, a TypeScript/Python desktop app using semantic-release, Windows host with `core.autocrlf=true`) ran a full minor run (`/implement v2.14`). It shipped its release and archived the minor, but the completion checker could not reach `MINOR COMPLETE`, for reasons that are contract problems rather than missing work. Below are the findings, each with what happened, the evidence, and a suggested fix. For each one: confirm it against the current source (the observing machine ran v4.13.13), decide whether to fix it, and if so add a regression test that reproduces the observed case. Keep the checker's honesty guarantees: never let a change turn unproven work into `met`. Report back which findings you fixed, which were already fixed, and which you declined and why.
>
> **1. `gaps.minor` scope covers all history, and legacy ledgers can never parse.** `gaps_minor_status` requires every ledger at or below the run's minor to have no open item and no parse problem. In Nexus-AI that includes ledgers back to v0.7. Measured with `completion_minor.load_ledgers`: 346 parse problems across 15 ledgers (206 `row`, 140 `heading-without-id`), because pre-v2.12 ledgers keep gaps in tables and older ones use id-less headings. Any ledger with a problem makes the verdict `cannot-verify`, so `MINOR COMPLETE` is unreachable for any minor in that repository, no matter what the run does. The consumer has since converted v1.17 to v2.12 itself (v2.15.0): every ledger from v1.17 up now parses with zero problems, and exactly 142 problems remain, all in v0.7 (1), v1.0 (66), v1.1 (38), v1.2 (33) and v1.3 (4). It asks for a **legacy cutoff** so v0.7 and v1.0 to v1.3 stop gating: for example a per-repository setting naming the oldest in-scope minor, or a rule that a ledger whose Status is `finalized`/`closed` and that sits under an archive root is historical unless it has unmigrated open items the parser can read. Make the cutoff visible in the verdict output so it cannot hide owed work silently.
>
> **2. `tests.evidence` rejects honest failure reporting.** `_tests_status` fails any `## Full-suite testing and stabilization` section matching `\b[1-9]\d* (failed|errors?)\b`. The consumer's section truthfully reported "6,411 passed, 12 skipped, 7 failed" (7 known Windows line-ending failures present on every phase, absent in Linux CI) and "355 passed, 1 failed" (a host-specific OCR test failing identically on the untouched main checkout). The only ways to pass are hiding those numbers or restructuring prose to dodge the regex, both worse than the problem. Suggest: accept a section whose failures are each listed as pre-existing with baseline evidence (same failures on the base commit), or accept a quoted green CI run of the full suite as the passing evidence.
>
> **3. `release.changelog` expects `## [x.y.z]`.** semantic-release (and this consumer's release extractor) writes top-level `# [2.14.2](https://.../compare/v2.14.1...v2.14.2) (2026-10-18)`. Changing the heading level would break the consumer's release-notes extraction. Suggest accepting `#{1,2} \[x.y.z\]` with or without a link.
>
> **4. A re-recorded run loses the work done before it, and a plan rename reads as tampering.** The consumer renumbered its plan (v2.14.0 to v2.14.2) with `git mv` after v2.14.1 shipped first. The old record became `BLOCKED: record-tampered` (plan path and hash gone), so a new approval round was required. The new record set `start_head` to the current HEAD, and `task.T###` requires a commit after `start_head` touching each task's path, so six tasks whose code was committed before the new round can never be `met` without empty edits, which would falsify evidence. Suggest: detect a rename (same content hash at a new path, or `git log --follow`) and carry the record; or let `record create` inherit `start_head` from the record it replaces, bound by the old record's nonce and HMAC.
>
> **5. Run-owned merged branches are kept as `recently-active`.** After the run's pull requests merged, `cleanup_merged.py --apply --receipt --minor v2.14 --session <id>` removed unrelated merged branches but kept every branch the run itself created (`feat/...`, `release/v2.14.2`, `fix/...`, `chore/close-v2.14`) as `recently-active`, and the worktree as `detached`. `cleanup.branches` and `cleanup.worktree` therefore stay unmet until an idle window passes, which the run cannot wait for. Suggest: a branch the run record names (or that the run created, with a merged pull request) is removable immediately under the recorded `cleanup-merged` approval; a clean detached worktree on a merged commit likewise.
>
> **6. `record block` rejects a legitimate `approval-not-covered`.** `record block --category approval-not-covered --approval-class gap-migration` was rejected with "the approvals already answer gap-migration" although the frozen `gap-migration` list named only 7 ids and 205 other items were uncovered. The block only succeeded without `--approval-class`. Suggest: reject only when the frozen class actually covers the specific items in the evidence.
>
> **7. The blocker-answer paste was not captured.** The user pasted exactly `Continue /implement v2.14 past blocker 1 (approval VEV2CW3E)` as their whole message, as printed by `record render --action answer --blocker 1 --page`. The prompt-submit hook did not record it (blocker stayed open); the agent had to run `record answer --minor v2.14 --blocker 1 --text "<line>"`. The line starts with `/implement`, which the harness may expand as a slash command before the hook sees the raw text. Check the capture path for paste lines that begin with a slash command. In the v2.15 run every paste (the create round and two blocker answers, all beginning with `Approve /implement` or `Continue /implement`) was captured: its sha256 appears in `~/.nexus-hub/runs/prompts/`, so the v2.14 miss may have had another cause.
>
> **8. `minor_close.py archive` repairs Markdown links only.** After `ARCHIVED v2.14 ... newly_broken=0`, these still pointed at the moved tree: `docs/handbooks/handbooks.json` (six receipt paths, which broke `check_handbooks.py`), paths inside the handbook receipt JSON files, two `.gitattributes` rules for files in the moved tree, code-comment and code-span mentions, and two strings in a product JSON catalog. Suggest: report non-Markdown and code-span references (JSON, `.gitattributes`, comments) in the archive output, with an opt-in to rewrite them, so `newly_broken=0` does not read as "nothing references the old path".
>
> **9. `minor_close.py` from a worktree.** Run from a linked worktree, `migrate` reports `REFUSED: approval-not-covered (no minor record for v2.14)` because the record is keyed by the main checkout's root; `--repo <main checkout>` finds it but then writes into the main checkout's files, not the worktree's branch. Suggest: key the record lookup by the common git dir so any worktree of the repository finds it, and write to the current worktree. The v2.15 run hit the same cause with `record block --minor v2.15` run from the plan's worktree: `no minor run record for this scope and session`; it succeeded from the main checkout.
>
> **10. `check-minor` hides detail when blocked.** Once any blocker is open, `check-minor` and `minor_close.py status` print only the `BLOCKED:` line, so diagnosing which ledgers and items keep `gaps.minor` unmet required importing `completion_minor` by hand. Suggest a `--detail` flag (or keep predicate notices under the blocked line).
>
> **11. `check_handbooks.py` hashes working-copy bytes.** On a Windows checkout with `core.autocrlf=true`, every receipt reads `stale evidence` because inputs and evidence are hashed as CRLF while receipts were produced from LF bytes. `generate_manifest.py` already hashes git-normalized blob bytes; the handbook checker should do the same (or normalize line endings for text inputs).
>
> **12. `validate_unicode_safety.py --strict --fix` rewrites raw evidence.** Run on a release folder as the release flow's Unicode gate directs, it stripped a UTF-8 byte-order mark from a captured log (`development/evidence/egress-pass2.txt`), altering evidence. Suggest excluding `evidence/` folders (or non-Markdown files) from `--fix` by default.
>
> **13. Small items.** `completion_minor.load_ledgers(Path("."))` raises `ValueError` from `relative_to` with a relative root (works with `Path(".").resolve()`). The approval page's "Fixed: 217 known problems" counts every older ledger's open gaps as work the run will fix, and its time estimate ("about 5.5 h") is computed when the member has 0 open tasks; both misled the reader. Consider wording the gap line as "open gaps in scope" and suppressing the build estimate when no task is open.

> **14. `record answer --text` spends the round on any text that is not the pasted line.** The help says only `--text TEXT`. In the v2.15 run the agent passed a note there (the reason for continuing); the checker refused with `approval-not-captured` and, as its source comment says, "the round is spent either way", so the owner had to paste a fresh line. Suggest naming the option `--pasted-line` or documenting it in `--help`, and not spending the round when the text does not match.
>
> **15. The turn-end gate reads the plan from the main checkout and opens `no-progress` while a run waits.** A full run works in a linked worktree on its own branch, so the plan's ticked tasks reach the main checkout only at merge. The gate kept reporting `task.T001` to `task.T008` unmet after those phases were committed in the worktree, and after three such refusals, while background research agents ran, it opened a `no-progress` blocker that the owner then had to answer. Suggest reading the plan from the branch recorded for the member (`source_branch`) or its worktree, and not counting refusals while the agent is waiting on its own background work.
>
> **16. No tool migrates a gap from an older minor into the current one.** `minor_close.py migrate` moves an item into the next patch of its own minor. The v2.15.0 plan moved 44 items from the v2.12 register and release ledger into v2.15.0; the consumer wrote a one-time tool that copies each entry through `minor_close.rewrite_links` and verifies it with `migration_copy_status` (`scripts/known-gaps/migrations/apply-dispositions.mjs` at commit `f27021de`; removed after v2.15.0 with the other one-time tools). All 44 verify. Suggest a `migrate --to vX.Y.Z` option with the same id assignment.
> **17. A task whose path a later phase deletes reads unmet after the merge.** `_task_status` runs `git log <start>..HEAD -- <path>` without `--full-history`. v2.15.0's T003 and T004 name the one-time converter and its test, which the plan's own T017 removes. Once the branch merges, default history simplification follows `develop`'s first parent, where the file never existed, and prunes the branch's commits. So `check-minor` reports `task.T003` and `task.T004` unmet, while `check <plan>` reports them met. Measured: `git log --format=%h 169d8b3b..HEAD -- scripts/known-gaps/migrations/normalize.mjs` prints nothing; with `--full-history` it prints the branch commits. Suggest adding `--full-history` (or `--follow`) to the task-path log.
