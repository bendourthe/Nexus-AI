## Decisions

### 1. Reference rows are qualified, not converted

A table row outside the register is a **reference** when its id already has an entry in another place:

- the known-gaps ledger its `Archived record` cell names, when that ledger holds the id, or otherwise
- the same file (an index row), or otherwise
- exactly one earlier in-scope ledger that holds the id as an entry that is not resolved. A resolved entry is a different, closed gap that reuses the short id: v2.2's and v2.3's `BG-2` are not v2.4's `BG-2`.

Rows of the register (`docs/v2/v2.12/known-gaps.md`) are never references: the register is where carried items live (decisions 4 and 6). A bullet with its own fields is never a reference either, because it is the item's full record. v2.4's `DF-1` bullet shares its short id with a still-open `DF-1` in an earlier minor.

A reference row stays in its table. Its id cell gains the minor of the ledger that holds the entry, for example `BG-2` becomes `v2.4#BG-2`. This is the checker's own `vX.Y#ID` label. The row no longer starts like an id, so the checker reads it as text, and the item is counted once, where it is recorded. If more than one earlier ledger holds the id and the cell names none of them, the converter refuses the file and names the candidates.

The plan said "rewrites tables into parsed headings". That wording does not separate a copy from an original. Converting the copies would add 120 open entries (the dry-run reference count for v2.5 to v2.11) that repeat items already recorded, which breaks the Goal's "duplicate-free". This is a plan delta of kind **Incomplete**, recorded in the Phase 1 session history.

### 2. Original rows become entries

A row that is not a reference becomes one entry, placed where the row was:

- **Heading**: `ID - <first sentence of the title cell>`. The title cell is the first column after `ID` when its header is `Why it is still open`, `Title`, `Item`, `Gap` or `Summary`. Otherwise the heading is the id alone (shape 2).
- **Level**: one deeper than the enclosing heading, clamped to 3 to 6.
- **Body**: the rest of the title cell as a plain paragraph, then one `- **<column header>**: <cell>` line for each remaining cell, in column order.
- **Links and code spans** are copied byte for byte. Each entry stays in its own file, so relative links keep their targets.
- When a table mixes reference rows and original rows, it is split at each original row. Each remaining table segment repeats the header and separator rows.

Bullet items (shape 4) become `ID - <first sentence>` headings one level below their subsection. The rest of the bullet becomes a paragraph. Its indented sub-bullets follow, de-indented to the entry's own list. Inline labels such as `Source phase:` stay as written, not as fields.

Cells split on unescaped pipes outside code spans. GFM would also split inside a code span, but the one ledger that writes such a pipe (v2.11's `` `<|tool_result>` `` row) means one cell, and its rendered table is already broken there.

Nothing changes order, so a reader sees the same entries in the same sequence. The first sentence ends at the first `. ` outside a code span, link or parenthesis, and only when that sentence is at most 160 characters. Otherwise the whole cell is the heading.

### 3. Allowlisted tokens

Apart from these, the word sequence of a converted ledger must equal its source:

- heading markers (`#` runs), the ` - ` between id and title, and list markers (`-`);
- `**<column header>**:` field labels, and repeated table header and separator rows;
- a `vX.Y#` prefix on a reference id;
- an inserted `### Resolved` heading (decision 5);
- a changed number on an existing `**Open items**:` line;
- on a superseded entry, a ` - CLOSED <date>` marker and its `- **Superseded by**:` line (decision 6).

Table pipes, separator rows and `**` emphasis are formatting, not words, and the preservation check ignores them on both sides. Every link target in the source must still appear in the output.

### 4. Ids across the two v2.12 files

The register `docs/v2/v2.12/known-gaps.md` and the release ledger `docs/releases/v2/v2.12/known-gaps.md` both migrate under the `v2.12#ID` label, so an id must be live in only one of them. Four ids appear in both files:

- `DF-v212-4` is an open entry in the release ledger. The register row's record cell links there as its "Canonical Phase 3 record", so the release ledger owns it, and the register converts it to a superseded entry (decision 6).
- `DF-v211-4`, `DF-v211-5` and `WN-v211-5` are rows in the release ledger's `### Resolved` table, not entries, so the checker sees no second item. The register converts them as open entries, as written. Phase 3 triage resolves them, citing that table.

The converter refuses any other collision with a live entry.

### 5. Already-closed rows

A table under a heading that says `Closed` or `Resolved` stays a table. When it is not already under a `### Resolved...` subsection, a `### Resolved` heading is inserted directly above it. The checker exempts rows there. This applies to v2.5's `## Closed in v2.5` table.

### 6. Superseded marker

A superseded entry keeps its id and text, ends its heading with ` - CLOSED <date>` (accepted by `_RESOLVED_END_RE`), and carries `- **Superseded by**: <ledger path> <ID>` naming the live entry. Phase 2 uses it only for the register's `DF-v212-4`. Phase 4 uses it for archived originals that a register or v2.12 entry carries.

### 7. Ids for id-less headings

Not needed in scope: no in-scope ledger has a `heading-without-id` problem (evidence above). The 140 such headings are in the legacy-cutoff ledgers, left to the Nexus-Hub checker cutoff.

### 8. Open counts before and after

Conversion changes format, not state. Original rows were open items the checker could not read, so the before count for each ledger is its parsed open items plus its original open rows. The after count must equal it. Reference rows and closed-table rows add nothing to either count. An `**Open items**:` header line is updated to the parsed open count.
