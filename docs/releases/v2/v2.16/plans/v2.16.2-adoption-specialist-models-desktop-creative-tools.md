**Goal**: A Nexus agent can create and reuse a user-approved local creative brief without a hosted generation service, and a maintainer can run one repeatable Windows packaged-app check that edits a fixture image through the ordinary viewer, restarts the app, proves the edit persisted, and verifies that the original PNG and the maintainer's real data were preserved.

## Overview

This plan adopts A1 (local brief guidance) and A2 (stronger existing desktop verification). It preserves the local multi-model architecture and deterministic approval/storage owners already present in Nexus. The skill produces an ordinary workspace document containing approved invariants, local reference identities and per-image changes. The test uses the current image viewer and storage contract, an isolated process profile and a known PNG; it does not require diffusion or another inference runtime.

The proposed distribution is one additional bundled creative-brief skill, bounded desktop asset/command discovery plumbing (confirmed D1), a small reusable packaged-test helper, and focused evidence/report changes. It does not add a brand-profile database, asset manager, generalized desktop tool, public eval endpoint, cloud MCP, model or Zig framework. A3 (Windows OS accessibility) and A4 (persistent profile-to-generation bridge) are parked, not silently authorized if implementation becomes difficult. If the real viewer cannot be exercised under these constraints, report HOLD and return with the exact missing capability.

Four phases are planned. Phase 2 carries the most risk because storage roots, child process ownership, WebView2 debugging and fixture ABI compatibility must all be proved before a write. The base scope targets Windows x64 packaged desktop. Skill loading should retain both current coding delivery paths; this is not a new macOS/Linux packaged-app support claim.

## Acceptance and Reporting Contract

The proposed packaged command is `node desktop/tests/packaged/image-edit-flow.mjs --exe <literal candidate executable> --out <new owned output directory>`. The implementer resolves the concrete executable from the recorded build/installer manifest; no angle-bracket command is handed to a user as runnable. It emits one JSON result to stdout, diagnostic detail to a private artifact directory, exit 0 only for a fully observed pass, 1 for failed observations and 2 for unavailable/malformed prerequisites. JSON includes schema version, run ID, executable hash, candidate commit, owned profile identity, observation timestamps, phase statuses, fixture hash, expected/observed recipe state and render comparison. Do not include tokens, unrelated UI text or full prompts in a public report. Local artifacts retain explicit unsupported/unobserved states.

Pre-register startup, action, save and shutdown timeouts before behavioral runs; total automatic retries are at most one fresh observation of an explicitly safe/read-only step. Never retry a potentially delivered write on timeout without reconciling state. Bind reports to the current run/artifact and observations; the judge's negative tests must reject missing/mismatched identity and a synthetic success body lacking required observations. These are diagnostic/test-integrity checks, not a cryptographic attestation claim.

Fixtures use non-sensitive synthetic art and neutral mock brand facts explicitly labeled as test data. Missing brand facts require a question or incomplete-brief status; never invent the user's approval. An approved reference is data, not instructions, and its path/hash is checked before reuse. Local files stay inside the selected workspace; no network references, external uploads or persistent model memory is required. Skills must use existing guarded read/write tools and stop on conflicting user edits.
