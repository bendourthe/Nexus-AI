## Source Verification

**S1, local article.** The PDF has no reliable author/date citation in its extracted body, so its identity is the local filename, hash and page numbers. Its principal recommendation is task decomposition: reason with an LLM, predict with a suitable specialist, and enforce rules in application code (pages 4-6). [Mistral's October 15 announcement](https://mistral.ai/news/timestral/) confirms a local-capable Timestral family with numerical and quantile outputs, and labels its license "Modified MIT". Its benchmark and server-CPU performance figures are vendor-reported, not Nexus measurements; an actual model license would still need review. The PDF's TabPFN, Kumo Relational and Jev examples are article-described capabilities, not locally qualified integrations.

**S2, desktop controller.** [Pinned README][D-readme], [Windows support][D-windows], [reference contract][D-refs] and [sessions][D-sessions] substantiate a Rust CLI/C library using OS accessibility APIs, Apache-2.0 licensing and platform adapters. They also qualify the supplied promotional description:

- A ref identifies an element within a saved snapshot and session namespace. It is not a permanent cross-snapshot or cross-session identifier. `STALE_REF`, ambiguous identity and incomplete snapshots require explicit recovery rather than blind retry.
- Accessibility can avoid a vision model for exposed semantic controls. Custom canvases, media pixels and visual quality still need screenshots or another renderer-aware check. A successful click does not prove the user's intended outcome.
- Parallel agents can have distinct overlay cursors. The session contract says their actions take turns through an interaction lease. A cursor overlay is not another physical mouse, an isolation boundary or permission for simultaneous writes to the same app.
- On Windows, `set-value` can be semantic/background input, whereas `type`, focus and several pointer actions require headed mode. An interactive signed-in desktop is required; locked sessions, Session 0 and secure desktops are unsupported. Headless here does not mean no graphical session.
- Cross-platform adapters exist, but their capabilities differ. Upstream Windows documentation explicitly describes source/test inspection rather than a live run for that page. No cross-platform Nexus support is established here.

**S3, creative skills.** The [pinned README][S-readme] distinguishes Scenario-connected generation skills from local expert families for installed DCC applications and game engines. The former require Scenario MCP and account authentication; the latter do not inherently require Scenario MCP, but have their own scripts, bridges, application requirements and verification limits. [Brand-kit guidance][S-brand] separates a written identity specification from rendering; [consistency guidance][S-consistency] distinguishes baseline prompts, subject/style references, control maps and trained adapters. Reusing a seed alone is not their proposed consistency solution. These are useful workflow distinctions, not evidence that a Nexus model supports the same reference fields or quality.

**S4, desktop toolkit.** [NanoUI's pinned README][N-readme] and [CI definition][N-ci] describe Zig 0.17, native immediate-mode controls or an OS webview, offscreen widget tests, scripted snapshots and a JSON-capable `nui` CLI. Its platform table says Windows rendering is CPU drawing presented through Direct3D/GDI, while other backends differ; "GPU-drawn UI everywhere" overstates this pinned version. Native accessibility is listed as not yet available on Windows and Linux, and the README's accessibility prose is less current than its platform table about macOS. Web pages use WebView2/WebKit platform dependencies. Small example-binary sizes do not include Nexus's models, inference runtimes or provisioning burden. No NanoUI build, performance test or screenshot was run here.

## Desktop and Testing Gaps

The source-only difference is OS accessibility control: no general desktop snapshot/ref/action tool was found in the reviewed Nexus tool and native surfaces. Nexus-only strengths are model-aware scheduling, local inference and established authorization boundaries. Both projects support machine-readable automation, but at different boundaries.

Nexus already has [packaged launch/probe code](../../../../../desktop/tests/packaged/launch-probe.mjs), its [judge](../../../../../desktop/tests/packaged/smoke.mjs), [headless Edge image-edit checks](../../../../../desktop/tests/webview/image-edit-pixels.mjs), a [loopback window capture client](../../../../../desktop/sidecar/src/controlSurface/windowCaptureClient.ts) and [native capture implementation](../../../../../desktop/src-tauri/src/window_capture.rs). The packaged probe navigates pillar routes and collects selector/network observations. That is meaningful existing coverage, but not proof that each pillar completes a workflow, a native file dialog is operable, or the screen remains visually correct. WebView network events alone also do not measure all Node-sidecar/native process connections.

Adoption should begin with one disposable-profile flow through the current packaged harness: navigate, perform a meaningful semantic action, observe changed state, and check a durable result after reopening. Use an existing local image fixture and authenticated image-edit command where suitable, avoiding GPU generation as a prerequisite. Keep rendered-pixel evidence separate from state assertions. A test-only debugging port must remain confined to the isolated test launch; do not expose a new production eval/debug service.

Only if a required control is outside that coverage should a Windows-only UIA feasibility probe follow. Start with read-only inspection of the Nexus process/window at ordinary user privilege. A positive read is not permission to act. Action scope must name the allowed process/window, operation and disposable fixture. Reject stale/ambiguous references, redact sensitive fields before persistence, serialize writes to a shared surface, and verify the actual postcondition. Window ownership and recovery need evidence before widening the scope. Do not claim support for external applications, Linux/macOS, secure desktops or parallel action delivery on this report.

## Creative Workflow Gaps

Nexus already records image prompt/model/seed/LoRA/ControlNet metadata in [WorkflowMetadata](../../../../../core/image/WorkflowMetadata.ts), video inputs and source hashes in [video metadata](../../../../../core/video/WorkflowMetadata.ts), durable edit state in [ImageEditRecipe](../../../../../core/image/ImageEditRecipe.ts) and [ImageEditRecipeStore](../../../../../core/generations/ImageEditRecipeStore.ts), and scoped agent actions in the image-edit routes. It also has [local audio runtimes](../../../../../core/audio/audioRuntimeFactory.ts) and a [host-gated splat-generation path](../../../../../core/image/SplatGenerate.ts). Speech is not a full music/sound-design stack, and splats are not universal editable meshes. Scenario's broader modality list does not establish a missing requirement for every modality.

The useful difference is reusable creative intent: an approved baseline, named invariant attributes, approved local references, model-specific conditioning capabilities, and a deliberate per-output delta. Nexus's app CSS tokens and installer brand tests describe Nexus's own appearance; they do not prove that generated assets follow a user brand. Existing image-edit recipes describe edits to a particular output, not a cross-output identity guarantee.

Begin with the already available Nexus-Hub `brand-styling` token pattern and local creative skills, not an imported Scenario catalog. A skill can keep a written brief, approved local asset paths/hashes and baseline-plus-delta prompts. It cannot make an unsupported model obey multiple references, preserve a character perfectly or render a precise logo through diffusion. Exact logos/text should reuse approved assets and deterministic composition where available. A seed is useful run metadata, not an identity contract across different prompts/models.

Only after a small image-series pilot demonstrates repeated work should a durable profile-to-generation bridge be considered. Its minimal data would be a versioned brief and reference identities linked from existing generation metadata, not another job queue, asset database or universal creative orchestration layer. Use each runtime's real schema and fail clearly on unsupported conditioning; do not silently substitute img2img for a subject/style-reference input. Cross-image/video consistency remains a measured candidate, never an inferred capability. Local DCC expert material may inform a later specific user task, but no Blender/Maya/engine bridge is introduced by this adoption.

## Prioritized Adoption Sequence

Sequence is skill-native first, then internal implementations. Priority ranks within those buckets. Effort estimates are planning ranges, not measured delivery times. No implementation is authorized by this comparison.

1. **A1, P1, roughly half to one day:** use the existing local brand/creative skills for one approved brief and a three-image pilot. Record which attributes must stay fixed and the delta for each output; preserve reference hashes and exact prompt/run metadata. Target existing user/Hub skill discovery through `core/skills/SkillCatalog.ts`; do not create another brand schema until the current one has been tried. Acceptance: the same approved brief can be reused without re-entering invariants; unsupported reference conditioning is stated; quality is human-reviewed and failures retained. A visual identity guarantee is outside this gate.
2. **A2, P1, roughly two to four days:** extend `desktop/tests/packaged/launch-probe.mjs`, its judge/tests and existing image fixtures with one action/postcondition/reopen flow. Target disposable profiles and the ordinary packaged shell. Acceptance: a broken handler or lost persisted result fails the check; exact bundle identity and result artifacts are recorded; visual claims have pixel/capture evidence. Reuse `desktop/tests/webview/image-edit-pixels.mjs` rather than rebuilding an offscreen renderer. CI files change only if a separately scoped final phase actually requires it.
3. **A3, conditional P2, roughly one to three days for feasibility only:** after A2 identifies a named unreachable native control, inspect only the Nexus window using native Windows UIA, then attempt one explicitly scoped fixture action if permitted. Proposed home is a test-side Windows helper beside the existing packaged probe, with native access isolated from `core/`. Acceptance: missing capability, stale ref, ambiguous target, denied action and timeout all produce distinct machine-readable outcomes; no unrelated app/clipboard data is retained; a state postcondition proves action success. Stop if Windows WebView2 does not expose the required tree. General desktop automation remains outside this timebox.
4. **A4, conditional P2, roughly two to five days:** only if A1 shows recurring manual setup, add the smallest versioned brief/reference linkage through existing studio storage, metadata and command adapters. Acceptance: reopen preserves the brief version and approved asset identities; changed/missing references fail explicitly; UI and agent use the same validated request; image-to-video claims require separate local output evidence. No new asset store, cloud processor or model admission is included.

A3 and A4 have no demonstrated semantic dependency on each other, but parallel implementation is not authorized or recommended from this source-only assessment. Their complete read/write ownership inventories would be required before concurrent work. Shared tracker, release and evidence metadata remains coordinator-owned. Conservative fallback is serial work in the order above. Product-integration work should be a new phased plan, with an installer/release decision based on its eventual scope.

## Risks and Exclusions

- Keep the current shell, local model/job map, GPU scheduler and confirmation owners. New model defaults would require the separate model-acceptance process and catalog/job-map updates together.
- Do not register agent-desktop or Scenario in a global MCP configuration, install their skills, fetch NanoUI submodules or run source-provided setup/cleanup commands as part of this report.
- Do not treat OS accessibility output, window titles, image metadata or a skill's text as trusted instructions or approval. Retain privacy filters and action ownership at the actual execution boundary.
- Do not copy upstream source wholesale. An independently implemented internal subset can use generic names; any copied MIT/Apache code must retain its required license/copyright/NOTICE material. Local-first policy does not remove those obligations.
- A later durable brand bridge changes existing storage and UI/command contracts, which costs more than a prompt-only pilot. Prefer the pilot and stop if it is sufficient.
- No new forecasting, relational ML, generic 3D, music-generation pillar, universal desktop agent, multi-agent cursor system or Zig toolchain is justified by this comparison alone.
